## Key question 1: TigerBeetle — deterministic state machine, VOPR, storage fault model, static allocation, Protocol-Aware Recovery, measured throughput, what durability requires

### Takeaway
TigerBeetle is the closest shipped analogue to RCEdb: a single-threaded deterministic state machine replicated with Viewstamped Replication, hash-chained and checksummed on disk, tested by a deterministic simulator (VOPR) that stubs clock, network and disk and runs at a claimed ~1000x wall-clock on 1,024 cores; its design explicitly assumes the disk lies and that fsync of a single disk is not durability. Independently measured single-node throughput is tens of thousands of TPS with batching, not the 1M design target.

### Cited Findings
- VOPR runs the real cluster code with the clock, network and disk stubbed out; it is also a state checker that hooks into all replicas and checks state transitions as they happen; runs are deterministic given a seed and a Git commit so bugs can be replayed exactly — [TigerBeetle docs: VOPR](https://docs.tigerbeetle.com/about/vopr)
- The in-memory storage simulator injects storage faults and can corrupt reads and writes to the "disk"; the most severe mode uses up to 8% corruption probability on the read path and 9% on the write path, per replica (2023 blog; not re-verified against current simulator) — [TigerBeetle blog, 2023-07-11](https://tigerbeetle.com/blog/2023-07-11-we-put-a-distributed-database-in-the-browser)
- Official safety docs: the VOPR runs cluster code under network, storage and process faults at 1000x speed, 24/7 on 1024 cores; an investor write-up estimates ~700x, "nearly two millennia of simulated runtime per day" (outside estimate) — [TigerBeetle docs: Safety](https://docs.tigerbeetle.com/concepts/safety/); [Amplify Partners](https://www.amplifypartners.com/blog-posts/why-tigerbeetle-is-the-most-interesting-database-in-the-world)
- TigerBeetle adopts an explicit storage fault model instead of the traditional crash-consistency model, citing Fsyncgate and Protocol-Aware Recovery; durability is cluster-wide: a record would have to be corrupted on all replicas to be lost, and even then the system halts safely — [TigerBeetle docs: Safety](https://docs.tigerbeetle.com/concepts/safety/)
- DESIGN.md (mirror): the system detects and repairs disk corruption and misdirected writes, uses hash-chained checksums to guard against tampering, and "exceeds the fsync durability of a single disk and the hardware of a single server because disk firmware can contain bugs and because single server systems fail" — [DESIGN.md mirror](https://github.com/tbg/tigerbeetle/blob/main/docs/DESIGN.md)
- March 2025 newsletter: the storage fault model follows the end-to-end principle, "assumes little from the hardware and software storage stack"; adding misdirected-write fault injection found two correctness bugs; byte-level (not just sector-level) corruption injection surfaced padding bugs, now repaired by re-reading the whole block if padding reads non-zero — [TigerBeetle newsletter 2025-03-05](https://tigerbeetle.com/newsletters/2025-03-05-february-in-tigerland)
- Static allocation: TigerBeetle computes the worst-case upper bound of objects from CLI arguments and allocates exactly that at startup; TigerStyle forbids dynamic allocation after initialization; applies NASA's Power of 10 rules with "6,000+ assertion tripwires" — [ARCHITECTURE.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/ARCHITECTURE.md); [TIGER_STYLE.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md)
- Consensus: builds on Viewstamped Replication to offer Strong Serializability; throughput "is bounded by a single node... firmly scale-up, not scale-out" — [Jepsen: TigerBeetle 0.16.11 (June 2025)](https://jepsen.io/analyses/tigerbeetle-0.16.11)
- Jepsen 0.16.11–0.16.30: seven client/server crashes, two safety issues (missing results for multi-predicate queries; a debug API returning wrong timestamps); "exceptional resilience to disk corruption, including damage to every replica's files"; no way to handle total loss of a node's data; requests retried forever; as of 0.16.45 every issue addressed except indefinite retries; a bit-flip in the superblock region (not padding) crashed with "reached unreachable code" — [Jepsen: TigerBeetle 0.16.11](https://jepsen.io/analyses/tigerbeetle-0.16.11); [jepsen-io/tigerbeetle repo](https://github.com/jepsen-io/tigerbeetle/) (snapshot-and-restore faults against the superblock can make 0.16.27 panic on every startup; "helical faults in the WAL can permanently disable a TB cluster")
- Third-party chaos test of 0.17.9: "a power loss and one bad sector on each of two disks leaves the cluster down for good" — [dotnwat/torx issue #32](https://github.com/dotnwat/torx/issues/32) (not Jepsen; single tester)
- Measured throughput (SoftwareMill, local single node): ~42k TPS long-running in max-throughput mode (~2.8x best batched PostgreSQL at ~15k), 60k TPS in quick tests, achieved with much higher client concurrency so batches are larger; cloud fixed-rate at 5k req/s: ~4,097–4,461 TPS, p50 ~32 ms — [SoftwareMill local](https://softwaremill.com/tigerbeetle-vs-postgresql-performance-benchmark-setup-local-tests/); [SoftwareMill cloud](https://softwaremill.com/tigetbeetle-vs-postgresql-performance-benchmark-harness-cloud-tests)
- Community benchmark (kizzx2): TigerBeetle "1–2 orders of magnitude slower than Redis/Postgres except when batching 1000 transactions per batch" — [kizzx2/tigerbeetle-benchmarks listing](https://awesome.ecosyste.ms/projects/github.com%2Fkizzx2%2Ftigerbeetle-benchmarks)
- "1M transactions per second" is a design target (investor statement), not a published benchmark — [Amplify Partners investment post](https://amplifypartners.com/blog-posts/our-investment-in-tigerbeetle); Greef attributes the "1000x" marketing figure to concurrency-control redesign, not Zig or static allocation — [Changelog #635](https://changelog.com/podcast/635)

### Inferences
- TigerBeetle's durability stance contradicts RCEdb's HS-1..HS-5 as written: it treats a single disk's fsync as insufficient and makes replication (HC-18..HC-20 in RCEdb terms) the durability primitive. **(judgement)** RCEdb should ADOPT the framing "durable append per OS is a necessary host obligation, not sufficient for durability; durability claims must name the replica count" and keep HS-1..HS-5 as the per-host floor. Replicated D with admitter failover already exists in the host contract, so this is a wording and labelling change, not a redesign.
- VOPR's state checker is exactly RCEdb's T3 (two replays give identical state hashes) turned into a runtime invariant. **(judgement)** ADOPT: a deterministic simulator for RCEdb hosts that stubs clock, network and durable-append and checks that every replica's fold of D yields the same state hash; the Lean theorem covers delta, the simulator covers the host contract (HS-1..HS-9), which no theorem covers.
- The 8%/9% corruption rates and the byte-level/padding findings show that "verify on open" (HS-5) by hash chain alone is weaker than per-block checksums plus repair from replicas. **(judgement)** OPEN: whether RCEdb's verify-on-open halts (TigerBeetle halts safely only if all replicas corrupt; otherwise repairs). The Jepsen "helical WAL faults permanently disable a cluster" and "cannot handle total loss of a node's data" findings show repair-from-replica is itself hard; RCEdb's simpler halt-on-mismatch is defensible but must be labelled as availability loss, not data loss.
- Static allocation and NASA Power-of-10 are properties of the host implementation, not of the P = (S,E,delta,D,lambda) model. **(judgement)** OPEN for the reference host; REFUSE as a language-level requirement.
- Throughput: single-admitter, single-threaded RCEdb will be bounded as TigerBeetle is; the measured 40–60k TPS with batching (not 1M) is the realistic reference class **(estimate)**; batching at the admitter is the lever, and RCEdb's "one admitter per log" matches TigerBeetle's primary.

### Gaps
- Could not fetch the VOPR or Safety docs directly to confirm the exact current corruption-injection rates, fsync policy (whether TigerBeetle fsyncs every prepare), or the stated "1000x" derivation.
- No published TigerBeetle energy figure of any kind was found.

## Key question 2: FoundationDB (SIGMOD 2021, Flow, simulation), Antithesis, and what simulation found that tests did not

### Takeaway
FoundationDB's single-process deterministic simulator (Flow, BUGGIFY, randomized swarm configurations) is credited by its authors with the system's stability and with catching deep crash/restart-sequence bugs; Antithesis generalised it into a deterministic hypervisor and reports bugs (etcd stale read once per ~19 days of simulated testing; Ethereum Merge: 13 crash/DoS + 22 performance bugs) that conventional and chaos testing did not reproduce. The paper itself states simulation cannot reliably detect performance problems.

### Cited Findings
- Paper: "FoundationDB: A Distributed Unbundled Transactional Key Value Store", Zhou et al., SIGMOD 2021, DOI 10.1145/3448016.3457559 — [dbscholar listing](https://rmarcus.info/dbscholar/papers/h9e2e688f976c0e71); [PDF](https://www.foundationdb.org/files/fdb-paper.pdf)
- The simulator runs a network of interacting processes plus disk, process, network and request-level failures inside a single physical process; Flow is a C++ syntactic extension built for it; the authors credit it with stability and fast release cadence and say it catches deep bugs that appear only after particular sequences of crashes/restarts — [CACM Research Highlight, 2023](https://cacm.acm.org/?p=227399)
- BUGGIFY: the simulator injects "unusual (but not contract-breaking) behavior such as unnecessarily returning an error from an operation that usually succeeds"; each run uses random cluster size, configuration, workloads, fault-injection and tuning parameters — [CACM 2023 fulltext](https://m-cacm.acm.org/magazines/2023/6/273229-foundationdb-a-distributed-key-value-store/fulltext); secondary: each BUGGIFY point fires 25% of the time, deterministically, with simulated timeouts far shorter than production (0.1 s vs 60 s) — [pierrezemb.fr](https://pierrezemb.fr/posts/diving-into-foundationdb-simulation/) (25% figure not verified against primary)
- Limitations section opens "simulation is not able to reliably detect perfor[mance]..." (snippet truncated) — [fdb-paper.pdf via search](https://www.foundationdb.org/files/fdb-paper.pdf)
- Historical claims: FoundationDB was built exclusively in simulation for its first 18 months before sending a real network packet; "the equivalent of a trillion CPU-hours of simulated stress testing"; Antithesis (founded by ex-FDB engineers) claims only one user-reported bug shipped before the 2015 Apple acquisition (self-reported marketing) — [Strange Loop 2014 talk](https://thestrangeloop.com/2014/testing-distributed-systems-w-slash-deterministic-simulation.html); [Antithesis about](https://antithesis.com/company/about/)
- Third-party: Clever Cloud, testing a layer on FDB, found the `commit_unknown_result` double-apply edge case on the first simulation seed; "in production you might see this once every few months" — [letsdatascience report on Clever Cloud](https://letsdatascience.com/news/clever-cloud-integrates-simulation-testing-for-materia-6534a269)
- Antithesis runs the whole system in a deterministic hypervisor controlling network, thread scheduling and clocks; etcd adopted it (CNCF post 2025-09-25; etcd.io post 2025-10-03) to replace a robustness framework that "relied heavily on random chance and was difficult to reproduce" — [etcd.io blog 2025](https://etcd.io/blog/2025/autonomus_testing_with_antithesis/); [CNCF](https://www.cncf.io/blog/2025/09/25/autonomous-testing-of-etcds-robustness/)
- Antithesis found an etcd stale-read bug (stale data returned to a client requesting the latest value) "only once in about every 19 days of testing"; "traditional chaos testing would likely never reproduce it" — [Antithesis causality analysis, 2026](https://antithesis.com/blog/2026/causality_analysis/)
- Ethereum Merge testing: 13 bugs in "Panics, Crashes, or Denials of Service" plus 22 performance bugs; MongoDB reportedly "100+ critical bugs since 2021", "1 bug per 2,500 hours" (secondary news; no primary found) — [jwatte blog](https://jwatte.com/blog/blog-antithesis-deterministic-testing/); [byteiota](https://byteiota.com/antithesis-raises-105m-series-a-testing-tool-that-validated-ethereums-merge/)

### Inferences
- **(judgement)** ADOPT the FoundationDB pattern that the simulator and the production host are the *same code* with only the I/O layer swapped. RCEdb's host contract is already an interface (durable append, sync-result event); a simulated host implementing HS-1..HS-5 with injected failed/lying appends is cheap relative to TigerBeetle's full VOPR because delta is already pure and total.
- **(judgement)** ADOPT BUGGIFY-style "contract-permitted but unusual" injections at the host boundary: append returns success late, sync-result event reorders, verify-on-open finds a truncated tail. These exercise the parts of RCEdb no theorem covers.
- **(judgement)** OPEN: Antithesis-style whole-VM determinism is only needed if the host language runtime or OS is in scope; for a Rust/WASM host with a narrow I/O surface, FDB-style in-process simulation suffices. Note the SIGMOD paper's own caveat: performance (and hence energy) cannot be found by simulation; energy figures must remain reported_j/measured_j.

## Key question 3: Deterministic transaction processing — Calvin, Fauna, VoltDB/H-Store command logging, Aria, Bohm; does determinism remove 2PC and at what measured cost

### Takeaway
Calvin (SIGMOD 2012) showed that fixing transaction order before execution eliminates distributed commit protocols and sustained ~500k TPC-C tps on ~100 commodity EC2 nodes, at the cost of declared read/write sets and a ~10 ms batching latency floor; Aria (VLDB 2020) removed the declared-set requirement and reports up to 2x over both nondeterministic and prior deterministic systems on 8 nodes; command logging (H-Store/VoltDB) gave ~1.5x throughput over main-memory ARIES with slower recovery, which is the exact trade RCEdb makes with "the log is the database".

### Cited Findings
- Calvin: "a deterministic locking mechanism that enables the elimination of distributed commit protocols"; "it is possible to run half a million TPC-C transactions per second on a cluster of commodity machines"; scales near-linearly; no single point of failure — [Calvin PDF (Princeton mirror)](https://www.cs.princeton.edu/courses/archive/fall19/cos418/papers/calvin.pdf); 100-node EC2 detail from secondary — [Morning Paper](https://blog.acolyer.org/2019/03/29/calvin-fast-distributed-transactions-for-partitioned-database-systems/)
- Calvin's cost model: synchronous replication "is intrinsically a latency cost only, and need not necessarily affect contention or throughput"; the sequencer's 10 ms epoch gives a 10 ms latency floor; with Paxos replication latency "in the 100ms+ range" (secondary) — [Calvin PDF](https://www.cs.princeton.edu/courses/archive/fall19/cos418/papers/calvin.pdf); [highscalability summary](https://highscalability.com/paper-calvin-fast-distributed-transactions-for-partitioned-d/); the partitioned sequencer costs O(n^2) messages (Styx blog) — [mohakchugh Styx summary](https://mohakchugh.is-a.dev/blog/styx-deterministic-transactional-stateful-functions-dataflow)
- Thomson & Abadi 2010 "The Case for Determinism" argues deterministic concurrency control can eliminate 2PC even for distributed transactions — [dbscholar entry](https://rmarcus.info/dbscholar/papers/h8f566535eb5e9c5c)
- Aria (Lu, Yu, Cao, Madden, VLDB 2020): deterministic OLTP without knowing read/write sets in advance; commit decisions made deterministically without replica-to-replica communication; eight-node experiments report up to 2x over nondeterministic systems and earlier deterministic databases on YCSB and TPC-C; its paper describes 2PC as adding latency and hurting availability on coordinator failure — [Aria PDF](https://www.cs.arizona.edu/~caolei/papers/Aria.pdf); [MIT DSpace](https://dspace.mit.edu/handle/1721.1/133983)
- Bohm (Faleiro & Abadi, PVLDB 8(11), 2015): serializable multi-version protocol where readers never block writers and reads keep no bookkeeping; pessimistic rather than validation-based; "substantially outperforms existing multiversion and single-version schemes" (no numbers in retrieved text) — [arXiv 1412.2324](https://ar5iv.arxiv.org/html/1412.2324)
- Command logging (Malviya, MIT thesis 2012; later ICDE 2014): on TPC-C in VoltDB, command logging reached ~1.5x the throughput of a main-memory-optimised ARIES implementation, with higher recovery times — [MIT DSpace thesis](https://dspace.mit.edu/handle/1721.1/75716)
- Adaptive logging (Yao et al., SIGMOD 2016): command logging's recovery bottleneck in distributed settings is dependency synchronisation, "every transaction must be redone one by one"; adaptive logging reaches ~10x faster recovery while keeping throughput close to command logging — [SIGMOD 2016 PDF](https://www.comp.nus.edu.sg/~ooibc/alogging-sigmod16.pdf); [arXiv 1503.03653](https://arxiv.org/pdf/1503.03653)
- VoltDB docs: command logging records each stored-procedure invocation; recovery restores the last snapshot and replays later logs — [VoltDB docs ch. 14](https://docs.voltdb.com/UsingVoltDB/ChapCmdLog.php)
- Harding et al. (Deneva, PVLDB 10, 2017) evaluated six protocols apples-to-apples; a machine summary says deterministic protocols win under high contention for simple transactions but "do not scale with" more complex ones (unverified) — [p553-harding.pdf](https://www.vldb.org/pvldb/vol10/p553-harding.pdf)

### Inferences
- RCEdb's single-admitter sequencing is Calvin's sequencer with one partition, so the O(n^2) sequencer cost and the declared-read/write-set problem do not arise; what remains is the batching latency floor. **(judgement)** ADOPT an explicit admitter batch window as a host parameter with its latency floor stated (Calvin's 10 ms is the reference).
- The 2PC-removal claim holds for RCEdb trivially (one admitter, one log) but the cost moves to admitter failover (HC-18..HC-20), which is a view change, not a commit protocol. **(judgement)** ADOPT the Calvin framing "latency cost only" with the caveat that it is replication latency, and REFUSE any claim of throughput benefit without measurement.
- "The log is the database" is command logging. The measured penalty is recovery time (refold of D; Malviya: higher than ARIES; Yao: one-by-one redo). **(judgement)** ADOPT checkpointing of S (snapshot + replay suffix, as VoltDB) as the standard mitigation, and make HS-9 (as-of by folding a prefix) and HS-7 (refold indexes) cost-labelled as O(|D|) unless a checkpoint exists. This is the single largest open cost in RCEdb's design.
- Aria shows read/write sets need not be declared if execution is batched then deterministically validated; RCEdb's delta is already a total pure function per event, so it has no concurrency to resolve. **(judgement)** REFUSE Aria/Bohm-style intra-batch parallelism for the reference host (single-threaded like TigerBeetle); OPEN for future hosts, only if parallel execution is proven equivalent to the sequential fold.

## Key question 4: Verified storage and file systems — FSCQ, DaisyNFS/GoJournal, Verus storage (PoWER/CapybaraKV), seL4-style refinement, CompCert-like TCB statements; what they prove and person-years

### Takeaway
Verified storage work proves crash-safety specs (FSCQ's Crash Hoare Logic; DaisyNFS isolates crash+concurrency reasoning into a transaction layer so the rest is sequential with ~2x proof-to-code; PoWER/CapybaraKV, OSDI 2025, verifies crash consistency and provable corruption detection in Verus in under a minute of verifier time), always with an explicit unverified TCB (extraction, compiler, runtime, hardware); the only hard person-year figure found is seL4's ~25 person-years for ~10k lines, with FSCQ saying only that proofs took "significantly more work than the implementation" but were "manageable for a small team".

### Cited Findings
- FSCQ (Chen et al., SOSP 2015, Best Paper): certified with Crash Hoare Logic in Coq; "specifications and proofs required significantly more work than the implementation, but the work was manageable even for a small team of a few researchers" — [SOSP 2015 abstracts](https://sigops.org/s/conferences/sosp/2015/archive/abstracts.html); [FSCQ project page](https://pdos.csail.mit.edu/projects/fscq.html)
- Extraction is in the TCB: "the extraction process is part of the trusted code base (TCB), as are Coq's kernel and the compiler used to compile the extracted code" — [Verified Extraction from Coq to OCaml, PLDI 2024](https://rocq-prover.org/papers/verified-extraction-from-coq-to-ocaml); conventional extraction includes unproven pretty-printers and the unverified target compiler/runtime — [CakeML ITP 2018 short](https://cakeml.org/itp18-short.pdf); CoqGo optimised an FSCQ syscall 19% over extracted Haskell — [MIT thesis 2017](https://dspace.mit.edu/handle/1721.1/113460)
- DaisyNFS (Chajed et al., OSDI 2022): crash safety and concurrency isolated to GoTxn (GoJournal + two-phase locking + allocator, proved in Coq/Perennial); NFS operations verified sequentially in Dafny; "only 2x as many lines of proof as code" for the file system vs 22x for the transaction system; ≥60% of Linux NFS/ext4 throughput — [OSDI 2022 page](https://www.usenix.org/conference/osdi22/presentation/chajed); [PDF](https://pdos.csail.mit.edu/papers/daisy-nfs:osdi22.pdf)
- GoJournal: "while verifying GoJournal, we found one serious concurrency bug, even though GoJournal has many unit tests"; GoNFS ≥90% of Linux NFS throughput on NVMe — [NSF PAR entry](https://par.nsf.gov/biblio/10311895)
- PoWER (LeBlanc, Lorch, Hawblitzel, Huang, Tao, Zeldovich, Chidambaram, OSDI 2025, Distinguished Artifact): crash-consistency requirements placed in preconditions of storage API methods (Preconditions on Writes Enforcing Recoverability); a new media-corruption model giving provable corruption detection on any storage device; a "corruption-detecting Boolean" primitive for atomic checksum updates; CapybaraKV (Verus) and CapybaraNS (Dafny) both verify in under a minute; CapybaraKV competitive with unverified PM KV stores; uses only Hoare logic, ghost variables and quantifiers — [USENIX OSDI 25](https://www.usenix.org/conference/osdi25/presentation/leblanc); [PDF](https://jaylorch.net/static/publications/power.pdf); [LeBlanc dissertation, May 2025](https://www.cs.utexas.edu/~hleblanc/pdfs/dissertation.pdf)
- seL4 effort: "design, documentation, implementation and verification of the seL4 kernel come to about 25 person years... If we were to do it again... less than 10"; ~200,000 lines of Isabelle for ~7,500 lines of C — [Trustworthy Systems numbers page](https://trustworthy.systems/projects/OLD/l4.verified/numbers); seL4 tried CompCert but found performance degradation and a logic mismatch; "gcc is not part of the TCB, thanks to our binary verification toolchain" (ARMv7-A) — [seL4 Discourse](https://sel4.discourse.group/t/compiling-sel4-with-compcert/115)

### Inferences
- RCEdb's T3 (replay determinism) is a theorem about delta, not about storage; PoWER shows the storage-side property worth proving is "every write sequence allowed by the API precondition leaves a recoverable state, and corruption is detected". **(judgement)** ADOPT a PoWER-style statement of HS-1..HS-5 as preconditions on the host's append/sync API, so the host contract is a spec a Verus/Dafny host could discharge, and ADOPT an explicit corruption model (hash mismatch is detectable; silent undetected corruption is out of model).
- **(judgement)** ADOPT a CompCert/seL4-style written TCB statement for RCEdb: Lean kernel, SHA-256 implementation, extraction/compiler, OS durable-append semantics, disk firmware, replica count. Verified systems all publish one; RCEdb's "board_synth_claimed=false"-style honesty should extend to "verified_host=false".
- Effort: DaisyNFS's 22x proof-to-code for the transaction layer vs 2x for the rest is the right expectation—the small host contract is where proof cost concentrates. **(estimate)** A verified reference host in Verus is plausible at months, not person-decades, because the API surface (append, sync, open-verify) is tiny; but no person-year figures exist for Verus storage work.
- REFUSE: claiming the Lean theorem makes the database "verified"; by the sources' own TCB statements that claim requires the host too.

### Gaps
- FSCQ lines-of-proof, person-years, and DaisyNFS absolute line counts not retrieved; PoWER proof effort not published in retrieved text.
- No 2026 Verus storage paper found beyond PoWER (OSDI 2025).

## Key question 5: Durability primitives — fsync semantics per OS, Linux fsync error reporting, Rebello ATC 2020, ALICE OSDI 2014, torn writes, power-loss results, and cost of verify-on-open at 1 GB–1 TB

### Takeaway
fsync is not a portable durability primitive: Linux fsync flushes the drive cache but reported writeback errors only once and could lose them (fixed in 4.17 to report once per descriptor opened before consumption); macOS fsync does not flush the drive cache and needs F_FULLFSYNC; Windows FlushFileBuffers does; after a failed fsync all three Linux filesystems mark pages clean so retrying is unsafe (Rebello); 13 of 15 SSDs tore, corrupted or lost writes under power fault (FAST 2013); and 60 crash vulnerabilities in 11 applications came from assuming ordering/atomicity the filesystem does not promise (ALICE). Verify-on-open by SHA-256 chain is read-bandwidth bound: ~1 s/GB at SHA-NI speeds, so ~1 TB ≈ 10–20 minutes (estimate).

### Cited Findings
- Fsyncgate (2018): PostgreSQL assumed fsync would report an earlier I/O error and keep reporting until resolved; Linux did not; the errseq_t change dropped error visibility for descriptors opened after an error; Wilcox's fix ("errseq: Always report a writeback error once", v4.17) reports to any descriptor opened after the error but before it was consumed; PostgreSQL now PANICs on fsync failure (PG 12, backpatched to 9.4) — [LWN 752613](https://lwn.net/Articles/752613/); [LWN 752063](https://lwn.net/Articles/752063/); [PostgreSQL wiki: Fsync Errors](https://wiki.postgresql.org/wiki/Fsync_Errors); [errseq v4.17 branch](https://kernel.googlesource.com/pub/scm/linux/kernel/git/jlayton/linux/+/errseq-v4.17)
- Rebello et al., ATC 2020 (also ACM TOS 17(2), 2021): three file systems (ext4, XFS, Btrfs), five applications (PostgreSQL, LMDB, LevelDB, SQLite, Redis); "pages are always marked clean after a failed fsync"; ext4/XFS keep the new (unpersisted) data in the page cache, Btrfs reverts in-memory state to on-disk; none retry data/journal writes, only XFS retries metadata writes; "although applications use many failure-handling strategies, none are sufficient: fsync failures can cause catastrophic outcomes such as data loss and corruption"; root cause: recovery relies on the page cache, which "does not reflect the persistent state"; recommendation: recover from on-disk state only; SQLite WAL showed false failures only with App=Restart, BufferCache=Keep — [USENIX ATC20](https://www.usenix.org/conference/atc20/presentation/rebello); [PDF](https://www.usenix.org/system/files/atc20-rebello.pdf); OpenLDAP developers dispute the LMDB scenarios produced by the CuttleFS simulator — [openldap-devel thread](https://lists.openldap.org/hyperkitty/list/openldap-devel@openldap.org/thread/YUUKXVYXA347IWW3UKRS6NJHBU4FEE6M/)
- ALICE (Pillai et al., OSDI 2014): eleven systems, 60 crash vulnerabilities, "many of which lead to severe consequences"; companion tool BOB showed persistence properties vary widely across six Linux file systems — [ADSL page](https://research.cs.wisc.edu/adsl/Publications/alice-osdi14.html); [PDF](https://pages.cs.wisc.edu/~remzi/Classes/739/Fall2016/Papers/alice-osdi14.pdf)
- SSD power fault (Zheng et al., FAST 2013; TOCS 2016): fifteen SSDs, five vendors, >3,000 fault-injection cycles; "thirteen out of the fifteen... exhibited surprising failure behaviors under power faults, including bit corruption, shorn writes, unserializable writes, metadata corruption, and total device failure"; recommends not using SSDs for durable data or testing the exact model under real power loss — [USENIX FAST13](https://www.usenix.org/conference/fast13/understanding-robustness-ssds-under-power-fault); [PDF](https://www.ece.iastate.edu/%7Emai/docs/papers/2013_FAST_SSD.pdf)
- Torn writes: historic atomicity unit is the 512-byte sector; PostgreSQL (8 KB pages) and MySQL (16 KB) still assume 512 B atomicity and use full-page writes / doublewrite; NVMe has no atomic-write command, writes are atomic only within advertised unit/boundary; Linux statx exposes atomic_write_unit_min/max (power-of-two, aligned); in one 2025 database test double-buffered writes still beat atomic writes — [PostgreSQL wiki AtomicIO](https://wiki.postgresql.org/wiki/FreeBSD/AtomicIO); [LWN 933015 (2023)](https://lwn.net/Articles/933015/); [LWN 1016406 (2025)](https://lwn.net/Articles/1016406); [block atomic writes v6 thread](https://lists.infradead.org/pipermail/linux-nvme/2024-April/046633.html)
- macOS: fsync "only flushes writes to the drive", F_FULLFSYNC flushes the drive cache; Apple: F_FULLFSYNC "will be significantly slower"; secondhand benchmark: Apple's NVMe "more than 3 times slower than a lowly SATA SSD at flushing its cache"; many non-Apple SSDs "don't actually flush their cache... they lie"; SQLite forum: "with all the drives we tested F_FULLFSYNC slowed things down a lot" (old hardware) — [mjtsai 2022-02-17](https://mjtsai.com/blog/2022/02/17/apple-ssd-benchmarks-and-f_fullsync); [Apple dev forums](https://developer.apple.com/forums/thread/800906); [SQLite forum](https://sqlite.org/forum/info/b94afa45dda82aae8cbf49f9d511a00b332870fc926cba18954acd889bbfb7cd)
- Windows: NTFS FILE_FLAG_WRITE_THROUGH sends FUA which driver/drive may ignore, whereas Linux checks FUA support and falls back to a full cache flush; PostgreSQL removed its Windows fsync_writethrough option because "fsync" (FlushFileBuffers) and "fdatasync" already flush drive write caches on Windows; the option remains only for macOS — [pgsql-hackers (Munro)](https://www.postgresql.org/message-id/CA%2BhUKG%2Ba-7r4GpADsasCnuDBiqC1c31DAQQco2FayVtB9V3sQw%40mail.gmail.com); [PostgreSQL commit d0c28601 mirror](https://git.sharpetronics.com/sharpetronics/PostgreSQL/commit/d0c28601efaa8b04f11a19506f3371bba8438acc); library mapping FlushFileBuffers / F_FULLFSYNC / fsync — [D std.stdio.File.sync](https://opendlang.org/library/std.stdio.File.sync.html)
- SHA-256 throughput: BoringSSL on an AMD EPYC VM, 16 KB inputs: ~438 MB/s → ~1.57 GB/s with SHA-NI; secondary: ~500 MB/s → ~1.8 GB/s on i7-10700K — [BoringSSL commit](https://boringssl.googlesource.com/boringssl/+/17c8c811049a82d6c34897c718503444529c8d8b); [codegenes write-up](https://www.codegenes.net/blog/are-there-in-x86-any-instructions-to-accelerate-sha-sha1-2-256-512-encoding/)

### Inferences
- **(estimate)** Verify-on-open cost (HS-5) for a SHA-256 chain, single core with SHA-NI at ~1.5 GB/s and assuming read bandwidth is not the bottleneck: 1 GB ≈ 0.7 s; 100 GB ≈ 70 s; 1 TB ≈ 11–12 min (≈ 40 min without SHA-NI at ~0.44 GB/s). A hash chain cannot be parallelised across the chain, but per-event payload hashes can be computed in parallel and only the chain step is sequential, so multi-core brings it toward disk read bandwidth. Energy for this would be est_j only until measured.
- **(judgement)** ADOPT: (a) PostgreSQL's post-fsyncgate rule — HS-2's "fatal storage barrier" must mean the host process exits on any failed append/sync and recovers only from D on disk, never from memory (Rebello's recommendation); (b) per-OS mapping in HS-1: Linux fdatasync/fsync (both flush cache), macOS F_FULLFSYNC (fsync is insufficient), Windows FlushFileBuffers; (c) sector-torn-tail tolerance in verify-on-open: the last record may be torn and must be truncated, not treated as tampering, because the unit of atomicity is 512 B–4 KiB and NVMe atomic units vary.
- **(judgement)** ADOPT labelling in the host contract that a single-host durable append is "durable per OS" only; FAST 2013's 13/15 drives and the "drives lie" evidence mean a single-replica durability claim is an est-class claim, aligning with the est_j/reported_j/measured_j discipline (perhaps "durable_claimed=per_os|replicated|power_tested").
- **(judgement)** OPEN: whether RCEdb should checkpoint the chain head (so verify-on-open validates only the suffix after a trusted checkpoint) — this is what makes 1 TB logs openable in seconds; see question 6 for how transparency logs do it.

### Gaps
- No measured joules-per-fsync figure exists in any retrieved source (see question 8). No controlled F_FULLFSYNC vs fsync latency table on Apple Silicon was found.
- ALICE's per-application vulnerability list not retrieved.

## Key question 6: Tamper-evident and hash-chained logs — CT/Trillian, immudb, QLDB, Hyperledger Fabric, Git; proof sizes, verification cost, compaction/checkpointing

### Takeaway
A pure hash chain (RCEdb's D, Git, Fabric) gives O(N) verification and no sub-linear inclusion proof; Merkle logs (RFC 6962/9162, Trillian) give O(log N) inclusion and consistency proofs (kilobytes in practice) and let a signed tree head act as a checkpoint so a verifier re-checks only the suffix; immudb combines a Merkle tree with a linear tail and had a client-side consistency-proof bug (CVE-2022-36111); QLDB was retired 31 July 2025; Git is migrating from SHA-1 to SHA-256 after SHAttered.

### Cited Findings
- RFC 9162 (CT v2.0, Dec 2021): Merkle trees support efficient checks that a later log state extends an earlier one; a misbehaving log can show different views to different clients (split view), so logs are still trusted third parties; v2 adds get-all-by-hash returning inclusion + consistency proof together — [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html)
- Inclusion proof O(log N), consistency (append-only) proof O(log N); Trillian's logverifier exposes VerifyInclusionProof and VerifyConsistencyProof — [transparency.dev](https://transparency.dev/verifiable-data-structures/); [Trillian logverifier docs](https://godocs.io/github.com/google/trillian/merkle/logverifier@v1.4.0)
- Measured over the wire (software-distribution transparency study, 2017): inclusion-proof request ~1.3 kB sent / 2.9 kB received; consistency proofs ~2.6 kB (includes TLS handshake) — [arXiv 1711.07278](https://arxiv.org/pdf/1711.07278)
- A 2023 non-peer-reviewed design claims consistency proofs ~95% the size of Trillian's and constant-size inclusion proofs — [Trillian issue #3078](https://redirect.github.com/google/trillian/issues/3078)
- immudb: Merkle tree "enhanced with additional linear part" from the last Merkle leaf to compensate for transactions not yet consumed by the tree; client tracks server state and checks each verified read/write against a trusted state; optional server signing key; CVE-2022-36111 / GHSA-672p-m5jq-mrh8: client SDKs checked only the first and last elements of the linear chain, patched in client SDK 1.4.1 — [immudb how-it-works 0.8.1](https://docs.immudb.io/0.8.1/how-it-works.html); [immudb SDK docs 0.9.1](https://docs.immudb.io/0.9.1/sdks-api.html); [GHSA-672p-m5jq-mrh8](https://github.com/codenotary/immudb/security/advisories/GHSA-672p-m5jq-mrh8)
- Amazon QLDB: announced retirement July 2024, shut down 31 July 2025, AWS recommends Aurora PostgreSQL; QLDB chained blocks with hashes and exposed a journal digest plus Merkle audit proofs — [awsglossary QLDB](https://awsglossary.org/terms/qldb); [oneuptime QLDB history](https://oneuptime.com/blog/post/2026-02-12-verify-qldb-document-history/view)
- Hyperledger Fabric used as an integrity-proof ledger (hash chain + consensus), e.g. criminal-evidence integrity proofs (2025, Springer LNNS) — [Tecnalia publication](https://scienceportal.tecnalia.com/en/publications/leveraging-hyperledger-fabric-for-criminal-evidence-integrity-pro/)
- Git: SHAttered (Feb 2017) produced a practical SHA-1 collision; Git ≥2.13 uses hardened SHA-1 that detects the attack; transition to SHA-256 designed per-repository with interoperability; Git 2.29 (2020) first operable in SHA-256 mode; as of a 2025 LWN article GitHub and other forges had no SHA-256 support; LWN argues SHA-1 object IDs mainly serve as bit-flip checks with GPG signatures/HTTPS for security — [hash-function-transition.txt](https://code.googlesource.com/git/+/HEAD/Documentation/technical/hash-function-transition.txt); [devclass on Git 2.29](https://devclass.com/?p=3146); [LWN 1057561](https://lwn.net/SubscriberLink/1057561/bddc1e61152fadf6/)
- GlassDB (2022) is a verifiable ledger database built on transparency-log ideas — [arXiv 2207.00944](https://arxiv.org/pdf/2207.00944)

### Inferences
- RCEdb's D is a Git/Fabric-style linear chain: tamper-evident on full replay only. **(judgement)** ADOPT a Merkle tree over D's event hashes alongside the chain (CT/Trillian shape): the chain stays the canonical definition for T3 and replay, the tree gives O(log N) inclusion and consistency proofs so a client can verify "event e is in D" and "D' extends D" without refolding. Expected proof size is low kilobytes at any log size (sourced figures above).
- **(judgement)** ADOPT signed tree heads / chain-head checkpoints as the compaction mechanism: verify-on-open checks the suffix after the last checkpoint and the checkpoint's consistency with the previous one; this turns the O(|D|) open cost (question 5) into O(suffix). Split-view (RFC 9162) is the residual risk; with one admitter per log and replicated D (HC-18..20), the replicas are the auditors.
- **(judgement)** REFUSE immudb's linear-tail shortcut without the CVE-2022-36111 lesson: any verifier must check every intermediate link, and the verifier is itself a thing to test under the simulator.
- **(judgement)** RCEdb's SHA-256 choice is already what Git is migrating to; no change needed. Keep hash algorithm as a versioned field in the log header (Git's transition shows the cost of not doing so).

### Gaps
- No measured CPU cost per proof verification (microseconds) was found for Trillian; sizes only.
- Hyperledger Fabric ledger internals (block hash chain structure, compaction) not retrieved from primary docs.

## Key question 7: State machine replication — Raft, VR (TigerBeetle), Paxos variants; divergence detection by state hashes; Jepsen findings

### Takeaway
VR Revisited (2012) and Raft are near-equivalent crash-stop SMR protocols differing mainly in view change/leader election; TigerBeetle's VR plus hash-chained log and Protocol-Aware Recovery is the model closest to RCEdb's "one admitter, replicated D, failover". Divergence detection by state hash is practised in production (CockroachDB SHA-512 consistency checker, per range, 24 h cycle; VoltDB per-transaction hash compare) but cannot say which replica is wrong. Jepsen has found majority-committed-write loss in MongoDB, membership bugs in RethinkDB, 23 issues in Dgraph, and crashes/retry problems but near-clean safety in etcd 3.4.3 and TigerBeetle.

### Cited Findings
- VR Revisited (Liskov & Cowling, 2012): crash failures in an asynchronous network; adds reconfiguration; separates the protocol from the state machine; avoided disk I/O during normal operation unlike Paxos — [vr-revisited.pdf](https://www.cs.princeton.edu/courses/archive/fall19/cos418/papers/vr-revisited.pdf); [Morning Paper](https://blog.acolyer.org/2015/03/06/viewstamped-replication-revisited/)
- Raft vs VR: commenters (informal) describe Raft as largely the same protocol with different leader election (longest-log candidate vs round-robin view change); Raft paper credits Oki & Liskov's VR — [HN thread](https://hn.svelte.dev/item/44886202)
- CockroachDB: background consistency checker scans local replicas over a 24 h cycle for ranges where it is Raft leader; leader and replicas compute SHA-512 over an agreed snapshot and compare; mismatch is logged and the node may panic; "it is not possible for the system to identify whether the Raft leader or its replica is responsible" — [Cockroach Labs blog](https://www.cockroachlabs.com/blog/trust-but-verify-cockroachdb-checks-replication/); [netdata guide (third party)](https://www.netdata.cloud/guides/cockroachdb/cockroachdb-data-consistency-check-failure/)
- VoltDB patent: run a hash alongside each transaction's operations and compare at the coordinator; requires deterministic sub-operations — [US 9600514](https://patents.google.com/patent/US9600514)
- Paxos with state checksum in votes: divergence inside a window is detectable only after the window closes — [arXiv 2002.07509](https://arxiv.org/pdf/2002.07509)
- Jepsen etcd 3.4.3: strict-serializable key-value behaviour under process pauses, crashes, clock skew, partitions and membership changes; "Jepsen never passes software" — [etcd blog](https://etcd.io/blog/jepsen-343-results/)
- Jepsen Dgraph 1.0.2–1.0.6: 23 issues (deadlocks, crashes, duplicate upserts, snapshot-isolation violations), 4 unresolved including data corruption in healthy clusters; Raft per shard — [Jepsen Dgraph](https://jepsen.io/analyses/dgraph-1-0-2)
- Jepsen RethinkDB 2.2.3: membership-change flaw causing stale reads, lost updates, crashes; fixed in 2.2.4/2.1.6 — [Jepsen RethinkDB PDF](https://jepsen.io/analyses/rethinkdb-2-2-3-reconfiguration.pdf)
- Jepsen MongoDB: design flaws in v0 and implementation bugs in v1 replication protocol lost majority-committed writes; v1 fixed in 3.2.12/3.4.0, v0 left broken — [aphyr tag page](https://aphyr.com/tags/databases)
- Jepsen TigerBeetle 0.16.11: see question 1 (strong serializability met at 0.16.30; indefinite retries; no total-node-loss handling)
- "As these systems are implemented and optimised for production, they accumulate many divergences from the original specification" (Cambridge talk abstract) — [talks.cam.ac.uk](https://talks.cam.ac.uk/talk/index/159961)

### Inferences
- RCEdb's T3 makes state-hash comparison exact: any two replicas at the same log length must have identical state hashes, so divergence is a host bug or corruption, never legitimate. **(judgement)** ADOPT periodic state-hash exchange (CockroachDB shape) and, better, carry the post-fold state hash in each replica's acknowledgement (VoltDB/Paxos-checksum shape) so divergence is detected per batch, not per 24 h. Because D is hash-chained, the pair (log head hash, state hash) identifies which replica diverged from the log, which CockroachDB cannot do — a genuine advantage worth stating.
- **(judgement)** OPEN: VR vs Raft for admitter failover (HC-18..20). Sources show them near-equivalent; TigerBeetle's reason for VR (no disk I/O in normal path; Protocol-Aware Recovery of a corrupt log) matters only if RCEdb repairs logs from replicas rather than halting.
- Jepsen's pattern (crashes and retries are the common findings even in good systems) suggests RCEdb's host contract should specify client-visible retry/timeout semantics for sync-result events. **(judgement)** ADOPT bounded retries with an explicit failure event; REFUSE TigerBeetle's indefinite retry.

### Gaps
- No Jepsen finding retrieved that specifically concerned Raft *log* divergence undetected by state hashing; the Cambridge "divergence from specification" claim is generic.
- TiKV/Consul/Redpanda Jepsen details not retrieved.

## Key question 8: Energy — published joules per transaction/query, TPC-Energy, SPECpower, RAPL studies, ARM vs x86, energy of fsync, whether any database reports energy per operation

### Takeaway
The only standardised database energy metric is TPC-Energy (2009/2010), expressed as watts per unit of performance; the first results (HP, 2010) were 5.93 W/KtpmC on TPC-C and 5.84–6.72 W/tpsE on TPC-E, i.e. about 5.9 mJ per TPC-C transaction-minute unit (derived). Academic work reports energy via RAPL (microjoule counters, = reported_j in RCEdb terms) or wall meters (= measured_j): replication costs 40%+ of standalone energy efficiency (DSN 2014), index scans cut per-query energy ~72% (2026), ARM beat x86 on database queries by 2.6–9.5x (2012) and ARM64 used ~1/3 the energy on big-data workloads (2017). No shipped database reports energy per operation, and no source gives joules per fsync.

### Cited Findings
- TPC-Energy: approved late 2009; optional add-on to TPC-C/E/H; metric = energy consumed by all subsystems ÷ work completed over the interval, reducing to watts per performance; lower is better — [TPCTC 2010 paper](https://www.tpc.org/tpctc/tpctc2010/TPCTC2010-01.pdf); [TPC press 2010-02-02](https://www.tpc.org/information/press/tpcpress20100202.asp)
- First results (HP, July 2010): ProLiant DL585 G7 TPC-C 5.93 W/KtpmC at 1,193,472 tpmC ($0.68/tpmC); TPC-E 6.72 W/tpsE (DL585 G7) and 5.84 W/tpsE at 2,001 tpsE (DL580 G7); TPC-H 9.58 W/KQphH@300GB at 107,561 QphH — [TPC press 2010-07-07](https://www.tpc.org/information/press/tpcpress20100707.asp); [eepower news](https://eepower.com/news/transaction-processing-performance-council-announces-first-results-for-its-tpc-energy-specification/)
- TPC-C results page (dated May 2026) still offers Watts/KtpmC sort — contents not retrieved — [tpc.org TPC-C results](https://www.tpc.org/tpcc/results/tpcc_advanced_sort5.asp)
- Harizopoulos, Shah, Meza, Ranganathan, CIDR 2009: energy costs "projected to overtake the cost of hardware"; calls for DBMS-level energy research — [arXiv 0909.1784](https://arxiv.org/abs/0909.1784)
- Tsirogiannis, Harizopoulos, Shah, SIGMOD 2010: common operators exercise the full dynamic power range; CPU power at the same utilisation can differ by as much as 60%; CPU power is not linear in utilisation; (machine summary, unverified) "the energy-optimal configuration is usually the top performer" within a single node — [Unpaywall DOI 10.1145/1807167.1807194](https://unpaywall.org/10.1145%2F1807167.1807194); [dbscholar](https://rmarcus.info/dbscholar/papers/h71017401299a604a)
- Schiper, Pedone, van Renesse, DSN 2014: energy efficiency = committed transactions per joule (= throughput per watt); most efficient replication protocol achieves <60% of a standalone server's efficiency on TPC-C; primary-backup variant keeping the log on low-power backups reaches 79% — [DSN 2014 PDF](https://www.inf.usi.ch/pedone/Paper/2014/2014DSNb.pdf)
- SPECpower + RAPL power limiting (ICPE 2013): effect of RAPL caps on per-transaction response time and efficiency under varying load — [ICPE 2013 p15](https://research.spec.org/icpe_proceedings/2013/p15.pdf)
- Prokhorenko & Babar, Informatica 2024: RAPL + YCSB on Cassandra, MongoDB, Redis, MySQL; Redis and MongoDB more energy-efficient in most scenarios; weaker CPUs sometimes better J/op; RAPL less accurate when idle or with a discrete GPU active — [Informatica INFOR567](https://informatica.vu.lt/journal/INFORMATICA/article/1343)
- Vestnik RSREU 2026 (PostgreSQL, RAPL): index scan vs sequential scan at 1% selectivity cut energy ~72%; cache warming dropped one run from ~192 J to ~69 J; four workers gave best energy-delay product — [vestnik.rsreu.ru 2026 no.95](https://vestnik.rsreu.ru/en/archive/2026/issue-95/1824-1995-4565-2026-95-66-72)
- Bachras & Jacobsen, arXiv 2504.18980 (Apr 2025): ATLAS methodology for operational + embodied footprint of DuckDB, MonetDB, Hyper, StarRocks; RAPL reports energy natively in microjoules; architecture and deployment location drive differences; companion VLDB 2025 vision paper — [arXiv 2504.18980](https://arxiv.org/abs/2504.18980); [PVLDB 18 vision](https://vldb.org/pvldb/volumes/18/paper/Environmental%20Footprints%20of%20Query%20Processing%3A%20A%20Vision%20for%20Sustainable%20Database%20Architectures)
- ARM vs x86: Ou et al., CCGrid 2012 — ARM cluster energy-efficiency advantage 2.6–9.5x for in-memory database work, ~1.3x web, 1.21x transcoding — [VTT entry](https://cris.vtt.fi/en/publications/energy-and-cost-efficiency-analysis-of-arm-based-clusters/); VLDB 2015 (NUS): ARM big.LITTLE more energy-efficient for MySQL/Shark queries with a small throughput penalty, Xeon better for I/O-heavy MapReduce; limited memory/I/O bandwidth and immature software offset ARM — [VLDB 2015 PDF](https://www.comp.nus.edu.sg/~ooibc/vldb2015-small.pdf); ARM64 vs AMD Opteron (arXiv 1701.05996): ~1/3 the energy, energy-delay product 50–71% lower on HiBench — [arXiv 1701.05996](https://ar5iv.labs.arxiv.org/html/1701.05996)
- Storage energy fragments: SSD idle 0.519–1.075 W (HotPower 2008); NAND page-write current 17–35 mA depending on NAND model (HotStorage 2011); CloudCom 2025 measured bytes/joule per filesystem on NVMe with a power meter (Linux 6.16): f2fs best for low-intensity random writes, xfs best under high concurrency; no source isolates fsync — [Seo HotPower08](https://static.usenix.org/events/hotpower08/tech/full_papers/seo/seo.pdf); [Yoo HotStorage11](https://static.usenix.org/legacy/events/hotstorage11/tech/final_files/Yoo.pdf); [CloudCom 2025](https://faculty.cse.louisville.edu/nihat/papers/CLOUDCOM2025.pdf)
- fsync latency: SSDs without power-loss protection have slow fsync; with PLP, consistent (blog, no energy) — [feedbagel post](https://feedbagel.com/post/performance-analysis-fsync-latency-on-ssds-with-and-without-power-loss-protectio)
- Permissioned-blockchain energy on FPGAs and energy-efficient BFT-SMR are the nearest "energy per committed entry" literature for hash-chained replicated logs — [arXiv 2210.11839](https://arxiv.org/pdf/2210.11839); [EESMR](https://cdnjs.deepai.org/publication/eesmr-energy-efficient-bft-smr-for-the-masses)

### Inferences
- **(estimate, derived)** HP 2010: 5.93 W/KtpmC means 5.93 W sustains 1,000 tpmC = 16.7 tx/s, i.e. ≈0.36 J per TPC-C New-Order transaction, whole-system wall-meter (measured_j class). That is the only standardised, audited per-transaction energy figure found anywhere, and it is 16 years old.
- The three-way labelling RCEdb already mandates maps exactly onto the literature's three instruments: TPC-Energy/DSN 2014/CloudCom 2025 (wall meter → measured_j), RAPL studies (on-chip counter → reported_j, with the Informatica caveats on idle/GPU accuracy), and modelled footprints like ATLAS (→ est_j). **(judgement)** ADOPT the TPC-Energy convention of reporting energy as a ratio to a stated performance metric *and* the raw interval, and ADOPT the DSN 2014 metric "committed events per joule" for the replicated case, because replication's >40% efficiency loss is the single largest sourced energy effect relevant to HC-18..HC-20.
- **(judgement)** RCEdb can be the first database to report energy per operation with provenance, because its events are the unit of work and its host contract already names the instrument; REFUSE any per-event figure derived by dividing a whole-system measurement by event count unless the idle baseline is subtracted and stated (Tsirogiannis: power is non-linear in utilisation; Informatica: RAPL idle inaccuracy).
- fsync energy: no source; **(estimate)** must be measured, and a durable append's energy will be dominated by the device flush and the admitter's wait, so batching (question 3) is also the energy lever. OPEN until a measured_j number exists.

## Cross-cutting summary of recommendations (judgement, for the report writer)

ADOPT:
1. Durability wording: per-OS durable append (HS-1..5) is the host floor; durability claims name replica count; map fsync per OS (Linux fdatasync/fsync, macOS F_FULLFSYNC, Windows FlushFileBuffers). [Q1, Q5]
2. Fatal barrier semantics = PostgreSQL post-fsyncgate: exit on failed sync, recover from on-disk D only; tolerate a torn tail record on open. [Q5]
3. A deterministic host simulator (FDB/VOPR pattern, same code, swapped I/O, BUGGIFY-style contract-permitted anomalies) checking T3 across replicas. [Q1, Q2]
4. Merkle tree over D plus signed/chained checkpoints for O(log N) proofs and O(suffix) verify-on-open. [Q6]
5. State hash carried in replica acknowledgements for per-batch divergence detection; pair with log-head hash to attribute fault. [Q7]
6. Checkpoints of S for recovery/as-of (command-logging mitigation); cost-label HS-7/HS-9 as O(|D|) without them. [Q3]
7. PoWER-style preconditions and a written TCB statement for the host; "verified_host=false" until discharged. [Q4]
8. Energy: report ratio-to-work and raw interval; "committed events per joule" for replicated deployments; subtract stated idle baseline. [Q8]

REFUSE:
- Claiming "verified database" on the strength of the Lean theorem alone. [Q4]
- Per-event energy derived without idle baseline/instrument label. [Q8]
- Indefinite client retries. [Q7]
- Static allocation / Power-of-10 as language-level requirements (host-level only). [Q1]
- Intra-batch parallel execution (Aria/Bohm) in the reference host. [Q3]

OPEN:
- Halt vs repair-from-replica on verify-on-open mismatch. [Q1]
- VR vs Raft for admitter failover. [Q7]
- Whole-VM (Antithesis) vs in-process simulation. [Q2]
- Energy of a durable append (needs measured_j). [Q8]
