## KQ1. Embedded engines as index holders: SQLite, RocksDB/LevelDB, LMDB, DuckDB-WASM, sled, redb, Turso/libSQL/Limbo

### Takeaway
Every mature embedded engine converges on one writer at a time plus many readers, buys crash-safety with a handful of explicit media assumptions (fsync is durable, single-byte or sector writes are atomic, powersafe overwrite), and earns trust through testing volume rather than proofs; the ones that relaxed durability by default (sled's 500 ms flush, SQLite WAL+NORMAL, IndexedDB "relaxed") all document a loss window after power failure. RCEdb's HS-7 (index is a refoldable projection) is exactly the posture that makes those loss windows harmless for indexes, but not for D itself, whose append must use the engine's strongest mode.

### Cited Findings

SQLite — testing regime
- As of SQLite 3.42.0 (May 2023) the core is about 155.8 KSLOC of C and the project has "590 times as much test code and test scripts" (92,053.1 KSLOC); four independently developed harnesses; TH3 is about 1,055.4 KSLOC of C implementing 50,362 distinct test cases, giving "100% branch test coverage (and 100% MC/DC test coverage) to the core SQLite library"; a full-coverage run is about 2.4 million test instances and the pre-release soak test about 248.5 million — [sqlite.org/testing.html](https://sqlite.org/testing.html) (figures quoted via search excerpt; an older 3.7.0 draft on a mirror gave 647:1 and 45,716.6 KSLOC, historical).
- Crash testing is done "in simulation" because real power failures are impractical: `test6.c` wraps the host `sqlite3_file`, buffers writes in an in-memory write list and crashes on the "iCrash'th call to xSync()"; I/O-error tests insert a VFS that fails after N operations, loop with N increasing, then run `PRAGMA integrity_check` — [sqlite.org/testing.html](https://www.sqlite.org/testing.html), [test6.c](https://www.sqlite.org/src/raw/d00c3930e2d22a9dc84415b1a2ead2ca4ab430ae?at=test6.c).
- Powersafe-overwrite (PSOW): since 3.7.9 (2011-11-01) SQLite assumes a write to a byte range "will not damage or alter any bytes outside of that range even if a power loss or OS crash occurs", because sector size grew from 512 to 4096; PSOW "says nothing about the state of the bytes that were written"; and "SQLite does not add any redundancy to the database file for the purpose of detecting corruption or I/O errors" — [sqlite.org/psow.html](https://sqlite.org/psow.html), [sqlite.org/atomiccommit.html](https://www.sqlite.org/atomiccommit.html).
- WAL mode: "since there is only one WAL file, there can only be one writer at a time"; readers and writers run concurrently; auto-checkpoint at 1000 pages (`SQLITE_DEFAULT_WAL_AUTOCHECKPOINT`), run by the committing thread, "which is why most commits are fast and an occasional one is slow"; a long-running read transaction can prevent checkpoint progress — [sqlite.org/wal.html](https://sqlite.org/wal.html).
- WAL + `synchronous=NORMAL`: the WAL is synced before each checkpoint and the db after it, so most transactions get no sync; the database "always stays consistent" but "a committed transaction might roll back following a power loss or system crash"; application crashes never cause loss; NORMAL is the compile-time default in WAL mode (one blog disputes this; check `PRAGMA synchronous`) — [sqlite.org docsrc](https://www.sqlite.org/docsrc/info/bcf687da9c172292), [SQLite forum (D. R. Hipp quoted)](https://sqlite.org/forum/forumpost/9d6f13e346231916?raw), [avi.im 2025](https://avi.im/blag/2025/sqlite-fsync/).
- macOS `F_FULLFSYNC` is off by default; a long-time contributor reported that without it, power-off and drive-eject experiments "sometimes led to databases which were less-up-to-date, sometimes losing the most recent transaction", never corruption — [SQLite forum 2022](https://sqlite.org/forum/info/b94afa45dda82aae8cbf49f9d511a00b332870fc926cba18954acd889bbfb7cd).
- Quirks page: columns may be untyped ("flexible typing"); PRIMARY KEY columns may hold NULL except `INTEGER PRIMARY KEY` and WITHOUT ROWID tables, "a historical oversight" kept for compatibility; foreign keys parsed for years but enforced only from 3.6.19 (2009) and still off by default to avoid breaking older databases (`PRAGMA foreign_keys`, `-DSQLITE_DEFAULT_FOREIGN_KEYS=1`) — [sqlite.org/quirks.html](https://www.sqlite.org/quirks.html).

RocksDB / LevelDB
- Dong, Kryczka, Jin, Stumm, "Evolution of Development Priorities in Key-value Stores Serving Large-scale Applications: The RocksDB Experience", FAST'21 (Feb 2021): the optimisation target moved from write amplification to space amplification to CPU; lessons include managing resources across many instances, keeping the data format compatible in both directions, supporting replication and backups, and that "data corruption needed to be detected earlier and at every layer of the system" — [USENIX FAST'21](https://usenix.org/conference/fast21/presentation/dong), [ACM ToS 2021 version](https://www.eecg.utoronto.ca/~stumm/Dong-ACMToS21.html).
- Typical amplification figures: "10-30x for level compaction and 2-5x for universal compaction, with space amplification at 1.1-2x" — [Mintlify mirror of RocksDB docs](https://www.mintlify.com/facebook/rocksdb/concepts/architecture) (third-party mirror; the official wiki was not reachable). The CIDR'16/'17 space-amplification papers state "it is not possible to simultaneously reduce space, read, and write amplification" — [Dong CIDR'17](https://cidrdb.org/cidr2017/papers/p82-dong-cidr17.pdf).

LMDB
- Howard Chu's slides: copy-on-write B+tree, single writer, readers never block writers or readers, "MVCC - Serializable", "live data is never overwritten ... no write-ahead logs needed", read-only mmap by default so stray writes crash immediately — [Chu, NLUUG 2015 slides](https://leden.nluug.nl/activiteiten/events/vj15/slides/280515%20Presentatie%20Howard%20Chu%20-%20Lightning.pdf).
- `lmdb.h`: "Avoid long-lived transactions. Read transactions prevent reuse of pages freed by newer write transactions, thus the database can grow quickly"; `MDB_NOSYNC` keeps "ACI properties, but not D"; `(MDB_NOSYNC | MDB_WRITEMAP)` "leaves the system with no hint for when to write transactions to disk, unless mdb_env_sync() is called" — [lmdb.h (hackage mirror)](https://hackage-content-origin.haskell.org/package/lmdb-clib-0.9.31/candidate/src/lmdb.h), [OpenLDAP commit patch](https://git.openldap.org/jklowden/openldap/-/commit/7fdf6720416d5eaadf5fd811c4513c87a2899a0f.patch).
- Furuseth (OpenLDAP list, Aug 2016): a page is reusable only after the freeing commit is durable and older readers are gone, "so when you don't sync, or a read-only txn won't die, LMDB degenerates to append-only" — [openldap-bugs 201608](https://www.openldap.org/lists/openldap-bugs/201608/msg00016.html).

redb (Rust)
- Design doc: single writer, many readers, serializable only; copy-on-write B+trees; a 512-byte super-header with two 128-byte commit slots; the "god byte" `primary_bit` flip is the atomic commit point "relying on the assumption that single-byte writes are atomic"; default 1PC+C (one fsync, checksums decide validity on recovery), optional 2PC (two fsyncs) because XXH3_128 "is not collision resistant" and a malicious writer could make a partial commit look complete; non-durable commits roll back to the last durable one; stated media assumptions: single-byte writes atomic, writes durable after fsync, powersafe overwrite — [redb design.md](https://github.com/cberner/redb/blob/master/docs/design.md).

sled (Rust)
- README: "lock-free tree on a lock-free pagecache on a lock-free log"; beta, "if reliability is your main constraint, you should use SQLite"; on-disk format will change before 1.0; "uses too much space sometimes"; fsyncs about every 500 ms by default (`flush_every_ms`); the README is out of sync with a large in-progress rewrite (komora/marble) — [spacejam/sled](https://github.com/spacejam/sled).

Turso / libSQL / Limbo
- Turso Database (ex-Limbo) is "the next evolution of SQLite in Rust", tracks SQLite 3.50.4 for dialect, file format and C API, reads existing SQLite files, is "not yet 100%" compatible (COMPAT.md), not 1.0; tested with "a native Deterministic Simulation Testing suite and Antithesis"; io_uring on Linux; `BEGIN CONCURRENT` via MVCC; encryption experimental; 21,758 commits at time of reading — [tursodatabase/turso](https://github.com/tursodatabase/turso).
- The simulator runs "randomized deterministic simulations", each from a random configuration generating interaction plans and assertions, reproducible with `--seed`, and `--doublecheck` reruns a plan and compares outputs; Antithesis was added "in addition to our own DST tool" — [limbo simulator README (mirror)](https://git.joshthomas.dev/mirrors/limbo/src/commit/fd63688edea580017f99ddec67d225a0ca712ed0/simulator), [commit](https://git.joshthomas.dev/mirrors/limbo/commit/be4014a1df53e148490f82c39e479085c77ceaea).
- libSQL (C fork) is production-ready; the Rust rewrite is beta; concurrent writes in Turso Cloud were still waitlisted when read — [turso.tech/what-is-turso](https://turso.tech/what-is-turso), [openreplay (German)](https://blog.openreplay.com/de/turso-rust-sqlite-entwicklung/).

DuckDB-WASM
- DuckDB's 18 Sept 2026 post: persistence to OPFS works only with specific builds; the npm `latest` (1.33.1-dev57.0) "creates the OPFS files but never writes to them"; pin 1.32.0 or 1.33.1-dev64.0+; default is in-memory, `opfs://` path to persist — [duckdb.org 2026-09-18](https://duckdb.org/2026/09/18/opfs-wasm.html). A third-party project reports OPFS persistence only on Chromium desktop, with Chrome for Android and Firefox in-memory only — [adhocdb](https://github.com/mstrahov/adhocdb) (secondary).

### Inferences
- What they got right (judgement): single writer + MVCC readers (SQLite WAL, LMDB, redb) is the only concurrency model that has survived in embedded engines; multi-writer engines that tried lock-free everything (sled) remain beta a decade on. RCEdb's single admitter per log is the same shape, and HC-18 to HC-20 (Raft-shaped failover) is how LiteFS also does it (KQ5). Adopt, already adopted.
- What they got wrong by hindsight (judgement): (a) relaxed durability as a default (SQLite WAL+NORMAL, sled 500 ms, Chrome IndexedDB relaxed in KQ5) without a visible marker of what is durable; (b) SQLite's compatibility-driven quirks (nullable PK, FKs off) show that a schema promise not enforced at admission becomes permanent debt; (c) SQLite's "no redundancy for detecting corruption" versus RocksDB's lesson "detect corruption at every layer". RCEdb's hash chain and per-seq digest are the RocksDB posture, not the SQLite one. Adopt (already in HS-7/T38); refuse SQLite's reliance on the OS for integrity.
- The `host.Synced` durable mark of E.8 is the right abstraction for the loss-window problem: every engine above has such a window, and only RCEdb makes it a logged event the program can see. Adopt; and the host contract should (judgement) require the strongest engine mode for D's own append (`synchronous=FULL`/`F_FULLFSYNC` on Apple, redb 2PC when inputs are untrusted), while leaving index stores at whatever setting is fastest, exactly as HS-7 permits.
- redb's "two commit slots + checksum, pick the newer valid one" is isomorphic to RCEdb's "verify on open, cut back to the last valid entry" (T38); redb's warning that non-cryptographic checksums let a malicious writer forge a complete-looking commit is an argument for RCEdb's SHA-256 chain. Adopt (already).
- Turso's DST is the one testing regime in this group that RCEdb can reuse directly: a deterministic step δ with a logged oracle for every adapter (T37) is what a simulator needs. Adopt: seed-reproducible randomized runs with `--doublecheck`-style replay equality are a conformance test RCEdb can add cheaply.
- Leave open: which foreign store to recommend for indexes. LSM (RocksDB) wins on write amplification only if the index is write-heavy; B+tree CoW (LMDB/redb) wins on read latency and simplicity; the measured trade-off (10–30x vs 1.1–2x) is from a mirror, not the primary wiki.

## KQ2. Local-first and sync systems: what each chose for conflicts and why

### Takeaway
The field split in 2024: CRDT-first systems (Automerge, Yjs, Loro, cr-sqlite, Ditto, Jazz, Fireproof, Triplit) kept per-field merge semantics and full history; the server-authoritative camp (Replicache/Zero, PowerSync, Electric after its July 2024 "Electric Next" pivot) moved conflict resolution to a canonical server order with client-side speculative rebase. Measured sync sizes exist only for text CRDTs (crdt-benchmarks B4: 260k ops, 129–258 KB documents); no latency numbers for the server-authoritative systems were found. RCEdb's canonical admitter order with optimistic client folds is the Replicache/PowerSync shape, and its monotone-tagged replicas are the CRDT shape, each where it belongs.

### Cited Findings

Local-first ideals
- Kleppmann, Wiggins, van Hardenberg, McGranaghan, "Local-first software: you own your data, in spite of the cloud" (Ink & Switch, 2019; Onward! Oct 2019): seven ideals, "no spinners" (fast), multi-device, offline, collaboration, "the long now" (longevity), privacy/E2EE, user control — [inkandswitch.com/local-first](https://inkandswitch.com/local-first/), [Kleppmann Onward! 2019](https://martin.kleppmann.com/2019/10/23/local-first-at-onward.html). PowerSync notes "most implementations that are referred to as 'local-first' today conform to only a subset" — [PowerSync docs](https://docs.powersync.com/resources/local-first-software).

Automerge
- Binary format: "a document always contains a complete history of changes"; document chunks use columnar storage with RLE/delta encoding (the Hexane crate implements it) — [Automerge binary format spec](https://automerge.org/automerge-binary-format-spec/), [hexane](https://docs.rs/crate/hexane/0.2.1).
- Automerge 3.0: earlier versions used the compressed columnar form only on disk and an uncompressed history in memory; 3.0 uses the compressed form at runtime; "pasting Moby Dick used about 700MB of memory in Automerge 2 and about 1.3MB in Automerge 3" — [automerge.org/blog/automerge-3](https://automerge.org/blog/automerge-3/) (post date not captured).
- crdt-benchmarks B4 (Automerge paper editing trace: 182,315 inserts + 77,463 deletes = 259,778 ops, final doc 104,852 chars; i5-8400, Node 20.5.0): Yjs 13.6.11 docSize 159,929 B, parse 39 ms, encode 11 ms, 3.2 MB heap; ywasm 0.9.3 159,929 B, 16 ms, 3 ms; Loro 0.10.1 258,228 B, 13 ms, 77 ms; Automerge 2.1.10 129,116 B, parse 1,805 ms, encode 185 ms (memUsed excludes WASM memory, so "0 B" for WASM libraries is not real) — [dmonad/crdt-benchmarks](https://github.com/dmonad/crdt-benchmarks).
- Loro's docsize page on the same trace: Loro 273.5 KB default, 132 KB compressed; Yrs 227 KB / 92 KB; diamond-types 281 KB; Automerge 293 KB; Loro shallow snapshot 63 KB / 54.5 KB compressed; Loro's author says "the current benchmarks on Loro are not stable" and Yjs should run with GC off for fairness — [loro.dev/docs/performance/docsize](https://loro.dev/docs/performance/docsize), [Yjs forum thread](https://discuss.yjs.dev/t/yjs-vs-loro-new-crdt-lib/2567/4).
- Yjs: YATA-based; its 2016 GC "only works under specific circumstances", removed in 2017 "and replaced by a compound representation"; Loro's author claims Yjs cannot implement time travel even with GC disabled — [Yjs internals](https://docs.yjs.dev/api/internals), [Yjs forum](https://discuss.yjs.dev/t/should-size-of-binary-ydoc-be-monotonically-increasing/2325).

cr-sqlite
- Loadable extension; `crsql_as_crr` turns a table into a "conflict-free replicated relation"; v1 is "history-free": tables are grow-only or observe-remove sets on a causal-length set (CLSet), rows are maps of per-column CRDTs (LWW, counter, fractional index); merge = union by PK, consult delete log, merge column by column; sync via `crsql_changes` (table, pk, cid, val, col_version, db_version, site_id, cl, seq); inserts into CRRs "about 2.5x slower" than plain tables, reads same; v2 plans a "causal event log" keeping full history with developer-defined resolution at higher write/space cost; ALTER TABLE must be wrapped in `crsql_begin_alter`/`crsql_commit_alter` — [vlcn-io/cr-sqlite](https://github.com/vlcn-io/cr-sqlite).

ElectricSQL
- 17 July 2024 "Electric Next": the team "originally aimed to build a next-generation distributed database" but "adoption dynamics for creating a new database from scratch are tough"; it pivoted to a replication layer, "a clean rebuild of the Electric sync engine" exposing "an HTTP API for syncing Shapes of data from Postgres"; only the read path for the initial release, "Writes go through your own API endpoint" — [electric-sql.com 2024-07-17](https://electric-sql.com/blog/2024/07/17/electric-next), [electric-sql Dart deprecation](https://pub.dev/documentation/electricsql/latest/). PowerSync's account: the first system "was too large and complex in scope" and the team "had a hard time getting it to a point where it was stable and reliable" — [powersync.com comparison](https://powersync.com/blog/electricsql-electric-next-vs-powersync) (competitor).

Replicache / Zero (Rocicorp)
- Replicache "uses a form of server reconciliation — an intuitive and powerful technique from multiplayer games": mutators run locally, the server re-runs them against canonical state, and unconfirmed local mutations are "replayed on top of the new server state", "like a git rebase"; mutators must be "a pure function of its parameters, including tx" (IDs passed in); the server result "replaces the speculative one, which prevents clients from lying or cheating"; push/pull/poke, poke "carries no data"; default pull interval 60 s; a pull response's cookie identifies the state and a mismatched poke errors — [doc.replicache.dev how-it-works](https://doc.replicache.dev/concepts/how-it-works), [local-mutations](https://doc.replicache.dev/byob/local-mutations), [poke](https://doc.replicache.dev/byob/poke).
- Zero: "a new kind of sync engine powered by queries"; custom mutators arrived in 0.18 ("arbitrary write operations in code"), `.client`/`.server` split in 0.19, legacy CRUD mutators disableable in 0.23; the server-side execution "is definitive, and client-side changes are speculative"; transactional poke/mutation-response semantics were still open issues — [zero.rocicorp.dev/docs/sync](https://zero.rocicorp.dev/docs/sync), [0.18 notes](https://zero.rocicorp.dev/docs/release-notes/0.18), [bug 3045](https://bugs.rocicorp.dev/issue/3045), [Marmelab review Feb 2025](https://marmelab.com/blog/2025/02/28/zero-sync-engine.html).

PowerSync
- "Designed for causal+ consistency": a checkpoint is "a single point-in-time on the server (similar to an LSN in Postgres)" containing only committed transactions; "the client only updates its local state when it has all the data matching a checkpoint"; local writes sit "on top of the last checkpoint" in an upload queue and "while changes are present in the upload queue, the client does not advance to a new checkpoint. This means the client never has to resolve conflicts locally"; after upload the client requests a Write Checkpoint tied to the source db's replication position; if the next checkpoint lacks an uploaded change "those changes will be removed from the client", visible as a few-second flicker, so the backend must write synchronously; per-bucket checksums force a full re-download on mismatch; `ps_oplog` staging then copy to `ps_data__<table>` — [docs.powersync.com/architecture/consistency](https://docs.powersync.com/architecture/consistency), [handling-writes](https://docs.powersync.com/handling-writes/), [checkpoint requests](https://docs.powersync.com/client-sdks/advanced/checkpoint-requests). For rich text PowerSync "becomes the provider for CRDT data" rather than merging itself — [PowerSync CRDT docs](https://docs.powersync.com/usage/use-case-examples/crdts).

Ditto
- Registers are LWW; "physical clocks were not reliable in a distributed mesh network", so a version vector with a Hybrid Logical Clock (64 bits: 48 physical + 16 logical) is used; Maps are add-wins, Counters merge additively; version vectors decide sequential vs concurrent — [Ditto legacy CRDT docs](https://legacydocs.ditto.live/common/how-it-works/crdt), [Ditto conflict resolution](https://www.ditto.com/solutions/conflict-resolution).

Jazz, Fireproof, Triplit
- Jazz: CRDT-based "CoValues" on CoJSON (identities, permissions, sync, persistence); permissions couple "public-key cryptography with CRDTs" so they are "defined on the client and enforced globally in an auditable way"; Jazz v2 "changed so much from v0.x" — [FOSDEM 2026 talk](https://fosdem.org/2026/schedule/event/cryptographic-permissions-for-crdts), [jazz.tools blog](https://jazz.tools/blog).
- Fireproof: documents in prolly trees (deterministic layout, same Merkle root for any op order); updates logged to Pail, "a Merkle clock causal event log, similar to a write-ahead log ... but distributed", mergeable across any two actors "revealing any conflicting record updates that need to be reconciled" — [fireproof.storage engine docs](https://fireproof.storage/documentation/how-the-database-engine-works/), [The New Stack](https://thenewstack.io/fireproof-uses-merkle-crdts-to-cut-database-latency/).
- Triplit: "CRDT-based syncing database", property-level conflicts, pluggable storage (IndexedDB, SQLite, Durable Objects), websockets; one 21 Oct 2026 comparison says development "has stalled since Jan 2026" (single third-party claim) — [npm @triplit/db](https://www.npmjs.com/package/@triplit/db), [pistack 2026-10-21](https://www.pistack.xyz/posts/2026-10-21-local-first-sync-engines-electricsql-powersync-triplit/).

### Inferences
- The strongest hindsight signal is Electric's pivot plus Replicache/Zero/PowerSync converging on the same design: an authoritative server order, a client that applies speculative writes on top of its last known checkpoint and rebases them, and "the client never has to resolve conflicts locally". That is exactly an admitter plus an optimistic client fold. RCEdb already has the canonical half (HC-15 canonical admission, T40 window permutation invariance). Adopt the client half explicitly (judgement): define the offline client as a chain whose entries are provisional until admitted, with the PowerSync rule that a client does not advance its admitted prefix while it holds unadmitted entries, and Replicache's rule that a mutator (event) is a pure function of its payload so the admitter's re-fold is the client's fold. Both rules are already implied by δ being pure and D being canonical; writing them down is cheap.
- PowerSync's "flicker" edge case (a change vanishes when the next checkpoint lacks it) is the cost of asynchronous backends; RCEdb avoids it structurally because the admitter is the backend (the admitted entry and the checkpoint are the same thing). Refuse the asynchronous-backend indirection.
- CRDT-first systems paid in size and complexity: Automerge needed a Rust rewrite and a runtime columnar representation to get from 700 MB to 1.3 MB for one pasted novel; Yjs gave up time travel; cr-sqlite's v1 is "history-free" and plans a causal event log (which is what D already is). Judgement: RCEdb should not adopt a per-column CRDT register model for its base record; the log already carries full history, and per-field merge rules belong in rules tagged monotone on replicated state, as the partial-order proposal says.
- Ditto's HLC choice (physical clocks unreliable in a mesh) supports RCE's "safety does not depend on clocks" (HC-18 to HC-20). Adopt the position; the admitter's seq is a logical clock.
- Open: Fireproof's Pail (Merkle clock causal log with prolly-tree indexes) is the closest existing artefact to the proposed partial-order D with refoldable indexes; a detailed comparison of its merge semantics was not possible from available sources.

### Gaps
- No measured sync latency or payload size for Replicache, Zero, PowerSync, Electric, Ditto, Jazz, Fireproof or Triplit was found.
- Rocicorp's own argument against CRDTs (the "ready player two" essay or equivalent) was not reachable; only a testimonial ("You might not want CRDTs") and the mechanism are sourced.
- The Automerge 3 post date and full numbers beyond the Moby Dick example were not captured.
- Jazz v2 and Fireproof's current compaction behaviour are unverified.

## KQ3. CRDT theory meeting practice: Shapiro 2011, BEC/BFT CRDTs, the hard parts, Peritext, unsafe observations, CALM

### Takeaway
Theory delivered convergence (SEC) and even Byzantine tolerance via hash graphs, but practice found three hard parts the theory did not cover: interleaving and move anomalies in sequences, rich-text intent, and the fact that CRDT reads are "unconstrained and unsafe" (Laddad et al. 2022), which only the CALM monotonicity test fixes. RCEdb's monotone tag on rules and the proposal's "every non-monotone event sits at a cut" is the CALM line drawn where Laddad et al. say it must be; it should be extended to reads, as the proposal already does.

### Cited Findings
- Shapiro, Preguiça, Baquero, Zawirski, "Conflict-free Replicated Data Types", SSS 2011 (INRIA RR-7687): formalises Strong Eventual Consistency and the two designs: "the values of state-based objects are monotonic in a semilattice, and the concurrent updates of operation-based objects commute"; a 2025 paper notes their state/op conversion "stop[s] short of formally defining a notion of emulation" and that "preserving SEC alone is insufficient for correctness" — [SSS 2011 PDF](https://www.cs.tufts.edu/~nr/cs257/archive/marc-shapiro/CRDTs_SSS-2011.pdf), [arXiv 2504.05398](https://arxiv.org/html/2504.05398v2).
- Hellerstein & Alvaro, "Keeping CALM: When Distributed Consistency is Easy" (arXiv Jan 2019; CACM): "the programs that have consistent, coordination-free distributed implementations are exactly the programs that can be expressed in monotonic logic"; CALM = "consistency as logical monotonicity"; first stated at PODS 2010 — [arXiv 1901.01930](https://arxiv.org/abs/1901.01930v2), [the morning paper](https://blog.acolyer.org/2019/03/06/keeping-calm-when-distributed-consistency-is-easy/).
- Laddad, Power, Milano, Cheung, Crooks, Hellerstein, "Keep CALM and CRDT On", PVLDB 16(4):856–863, 2022: "CRDT guarantees extend only to data updates; observations of CRDT state are unconstrained and unsafe"; they "extend CRDTs with a query model that reasons about which queries are safe without coordination by applying monotonicity results from the CALM Theorem" — [arXiv 2210.12605](https://arxiv.org/abs/2210.12605v1), [PVLDB PDF](https://www.vldb.org/pvldb/vol16/p856-power.pdf).
- Kleppmann, "CRDTs: The Hard Parts" (Hydra, July 2020): interleaving anomalies, moving list items, moving subtrees, metadata overhead — [kleppmann.com 2020-07-06](https://martin.kleppmann.com/2020/07/06/crdt-hard-parts-hydra.html). Interleaving: Kleppmann et al., PaPoC 2019, demonstrate the anomaly in Logoot, SOCT2 and LSEQ — [PaPoC 2019 PDF](https://www.cl.cam.ac.uk/~arb33/papers/KleppmannEtAl-InterleavingAnomalies-PaPoC2019.pdf). Moves: "existing algorithms behave poorly when users concurrently move list elements", PaPoC 2020 — [kleppmann.com 2020-04-27](https://kleppmann.com/2020/04/27/papoc-list-move.html). Fugue (Weidner & Kleppmann 2023) says the problem "gone unnoticed for decades" and affects CRDTs and OT alike — [arXiv 2305.00583](https://ar5iv.labs.arxiv.org/html/2305.00583).
- Peritext (Litt, Lim, Kleppmann, van Hardenberg; CSCW 2022): formatting spans stored alongside the character sequence, anchored to stable character ids; prior plaintext-CRDT extensions "cause editing anomalies that fail to preserve user intent"; validated by randomized property testing; later integrated into Automerge with blocks and a ProseMirror binding — [inkandswitch.com/peritext](https://inkandswitch.com/peritext/), [CSCW PDF](https://inkandswitch.com/peritext/cscw-publication.pdf), [Automerge dispatch 004](https://inkandswitch.com/newsletter/dispatch-004).
- Kleppmann, "Making CRDTs Byzantine Fault Tolerant", PaPoC 2022: "can tolerate any number of Byzantine nodes (making it immune to Sybil attacks), guarantees Strong Eventual Consistency, and requires only modest changes to existing CRDT algorithms" — the mechanism is a hash graph of operations in which each op names the hashes of its predecessors — [PaPoC 2022 PDF](https://martin.kleppmann.com/papers/bft-crdt-papoc22.pdf), [blog](https://martin.kleppmann.com/2022/04/05/bft-crdt-papoc.html). Kleppmann & Howard, "Byzantine Eventual Consistency and the Fundamental Limits of Peer-to-Peer Databases" (arXiv 2012.00472): I-confluence "is a necessary and sufficient condition for the existence of a byzantine fault-tolerant eventual consistency replication algorithm" — [jzhao.xyz notes](https://jzhao.xyz/thoughts/I-Confluence) (secondary paraphrase; abstract not retrieved). Jacob & Hartenstein characterise these designs as events "independently generated at the various replicas ... but associated to previous events known to the replica" — [arXiv 2304.04318](https://arxiv.org/pdf/2304.04318).
- Fireproof, Jazz and Automerge all implement the hash-graph pattern in practice (KQ2); Jazz adds public-key permissions on top — [FOSDEM 2026](https://fosdem.org/2026/schedule/event/cryptographic-permissions-for-crdts).

### Inferences
- What CRDTs cannot express: anything whose correctness is an observation rather than an update. Uniqueness, foreign keys and invariants over counts are non-monotone reads (a key is unique only until a concurrent insert arrives), which is why cr-sqlite's README is silent on constraints and PowerSync delegates CRDTs to rich text only. Laddad et al. make this precise: the update side converges, the read side is unsafe unless the query is monotone. Adopt: RCEdb's monotone tag must cover reads, as the partial-order proposal does ("a read is monotone when it is threshold-shaped ... any other read of a location another chain writes is a coordination point"). That sentence is the Laddad query model restated.
- The proposed `{chain, seq, deps, hash}` entry is the Kleppmann 2022 BFT hash graph (and Automerge's/Fireproof's Merkle DAG); the added `cut` entry with a state hash is what those systems lack and what lets a replica check a fold, not just a history. Adopt the proposal's shape; note (judgement) that BFT CRDT literature tolerates "any number of Byzantine nodes" only for convergence, never for invariants, so the single admitter remains necessary for every non-monotone event, consistent with the proposal's "What it refuses".
- Interleaving and move anomalies are sequence-CRDT problems. RCEdb's relational state has no sequence CRDT; a list ordered by a key is a scan in canonical key order (HS-8), so concurrent inserts get the admitter's order, not a merge. Refuse sequence CRDTs in the base record; leave open whether a Fugue- or Peritext-shaped rule can be written in RCE as a monotone replicated region for text (no evidence either way).
- Shapiro's SEC "is insufficient for correctness" (2025) is the theory-side confirmation of Laddad's practice-side point. Both support keeping convergence (replicas) and correctness (admitter) as separate guarantees, which RCEdb does.

### Gaps
- Laddad et al.'s concrete examples and the proposed "CRDT data store" agenda were not read beyond the abstract.
- The Kleppmann–Howard BEC abstract and the exact definition of I-confluence used were not retrieved.
- No source measured how often non-monotone reads occur in real local-first apps.

## KQ4. Single writer per log vs multi-master: offline reconciliation against a canonical order

### Takeaway
Every surviving offline design keeps a single canonical order somewhere: Replicache/Zero rebase speculative client mutations on the server's order, PowerSync holds the client at its last checkpoint until uploads are acknowledged, LiteFS and Durable Objects have one writer per database/object, and only pure CRDT systems let every replica be an authority, at the cost of KQ3's unsafe reads. A hash-chained single-admitter log like RCE's can let a device append locally to its own chain and fold optimistically; it cannot make those entries final, resolve uniqueness, or cross a non-monotone cut until the admitter admits them.

### Cited Findings
- Replicache: unconfirmed mutations are replayed on the new server state "like a git rebase"; mutators must be pure so replay is deterministic; server result replaces the speculative one — [doc.replicache.dev](https://doc.replicache.dev/concepts/how-it-works), [local-mutations](https://doc.replicache.dev/byob/local-mutations).
- PowerSync: "the client does not advance to a new checkpoint" while its upload queue is non-empty, so it "never has to resolve conflicts locally"; "PowerSync never applies a checkpoint while local writes are waiting to upload" — [consistency](https://docs.powersync.com/architecture/consistency), [checkpoint requests blog](https://powersync.com/blog/checkpoint-requests-client-synced-now).
- Automerge: deterministic merge over a complete history, document always contains all changes — [binary format spec](https://automerge.org/automerge-binary-format-spec/). cr-sqlite v1 merges "history-free" per column; v2 plans a causal event log — [cr-sqlite](https://github.com/vlcn-io/cr-sqlite).
- LiteFS: one primary at a time, elected by a Consul time-based lease ("the sole node that can write to the database during that time") or a static primary; writes forwarded to the primary (`fly-replay` header, HTTP 409), reads local; replication is asynchronous ("does not confirm that writes are committed to other nodes before continuing"); "a rolling checksum of the full contents of the database" detects divergence and triggers a snapshot; transactions packaged as LTX files; LiteVFS removes the FUSE dependency — [fly.io/docs/litefs/how-it-works](https://www.fly.io/docs/litefs/how-it-works), [Introducing LiteFS](https://fly.io/blog/introducing-litefs/), [Litestream revamped](https://fly.io/blog/litestream-revamped/).
- Durable Objects: each object is single-threaded and cooperatively multi-tasked; storage "durable, transactional, and strongly consistent" and private to the instance; the input gate defers all events except storage completions while a storage operation runs, and the output gate holds outgoing messages until pending writes complete — [Cloudflare DO concepts](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) (read via the cloudflare-docs GitHub source), [DO glossary](https://developers.cloudflare.com/durable-objects/reference/glossary/).
- D1 read replication (beta 10 April 2025): the Sessions API "ensures sequential consistency for all queries in a session" by carrying the latest bookmark in every request; queries outside a session are not guaranteed consistent with it; one replica per region — [D1 read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/), [Cloudflare blog](https://blog.cloudflare.com/d1-read-replication-beta).
- RCE partial-order proposal: a device's entries form a chain with `seq`; `deps` is a frontier; non-monotone events (`select` across chains, `resolve`, read-modify-write of a shared location, `atomic`, `freeze`, `restart`, deadlines) must sit at a cut; "Target-chosen linearization for non-monotone events" is refused — [local file](/home/user/rce/spec/proposals/partial-order-log.md).

### Inferences
- What a hash-chained single-admitter log can do offline (judgement, from the sources above): (1) append to the device's own chain with per-chain `seq` and `deps`, giving a Replicache-style pending queue that is already hash-linked and self-certifying (the BFT-CRDT property of KQ3); (2) fold optimistically over admitted prefix + pending chain for display, as Replicache and PowerSync do; (3) commit monotone replicated-state updates for real, since T62 says a dep-consistent order folds the same at the next cut. What it cannot do: (4) assign a global seq, pass a cut, or evaluate any non-monotone read (uniqueness, FK, select across chains) until the admitter admits; (5) promise that a pending entry survives, since the admitter may refuse it at admission (5.1 typing/HC-15 dedupe), which is Replicache's "server result replaces the speculative one" and PowerSync's flicker.
- Adopt: write the rebase rule down as PowerSync does, with the one improvement available to RCEdb: because the admitter's fold and the client's fold are the same δ over the same canonical bytes, "rebase" is just re-folding the pending chain after the admitted prefix; no second mutator implementation (Replicache's client/server pair) is needed. This is the single biggest simplification RCEdb has over the server-reconciliation systems, and it follows from T37.
- LiteFS's time-based lease is the clock dependence RCE's HC-18 to HC-20 explicitly avoids ("Safety of HC-18 to HC-20 does not depend on clocks. A leader lease ..."); its rolling checksum with snapshot-on-divergence is the operational cousin of T38's verify-on-open. Adopt the checksum-on-divergence behaviour for replicas (already implied by per-seq digests); refuse lease-based safety.
- Durable Objects' input/output gates are the same discipline as "an adapter's result is logged by the single admitter" plus "nothing leaves before the append is durable": a DO holds outbound messages until the write completes. Adopt as a host rule if not already stated: λ outputs that depend on an entry are released only after that entry is durable (the `host.Synced` mark). Judgement: the spec's "sync-result event" primitive is the right hook.
- Leave open: multi-admitter sharding. Turso's database-per-user and DO's object-per-key both pick "one writer per small log" and push cross-log joins to ATTACH or application code; RCEdb's fabrics (E.6) would be the analogue, and no measured cross-shard cost was found.

### Gaps
- The Durable Objects replication/PITR numbers (WAL batched every 16 MB or 10 s to object storage; five replicas, ack after three; 30-day PITR) come from Simon Willison's summary of Kenton Varda's Oct 2024 post and community pages, not from the official doc read here — [simonwillison.net 2024-10-13](https://simonwillison.net/2024/Oct/13/zero-latency-sqlite-storage-in-every-durable-object/); the primary post was not retrieved before the search budget ended.
- No source quantifies how often server-reconciliation rebases reject client writes in production.

## KQ5. Browser and edge storage: IndexedDB, OPFS, SQLite-in-browser, D1, Durable Objects, LiteFS, Litestream, Turso per-user DBs

### Takeaway
Browser storage is the least durable layer surveyed: Chrome made IndexedDB "relaxed" the default in Chrome 121 (3–30x speedups claimed), SQLite-WASM VFSes either mirror to IndexedDB or use OPFS sync-access handles with `synchronous=normal` trade-offs, and DuckDB-WASM's OPFS persistence silently did not write in the npm `latest` build as of Sept 2026. Edge stores (D1, DO, LiteFS, Litestream) all replicate a single-writer SQLite log asynchronously to object storage with a loss window measured in seconds. RCEdb's "index may live anywhere, D must be durably appended and the durable mark logged" is the only consistent posture across this spread.

### Cited Findings
- Chrome 121 changed IndexedDB readwrite durability default from `strict` to `relaxed`: strict "explicitly instructs the OS to flush changes to disk before issuing the complete event"; relaxed completes once changes reach the OS buffer, "typically flushed every few seconds"; Chrome reported "speed improvements between a factor of 3 and 30"; even strict "does not ensure that changes are actually written immediately to disk"; per-transaction `durability` option remains — [Chrome developers blog](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed/). Nolan Lawson's benchmark found relaxed "only modestly faster" and Chrome still slower than Firefox and Safari — [nolanlawson.com 2021](https://nolanlawson.com/2021/08/22/speeding-up-indexeddb-reads-and-writes/).
- wa-sqlite VFS options: `IDBMirrorVFS` keeps files in memory and persists to IndexedDB, "works in all contexts"; `IDBBatchAtomicVFS` makes batches all-or-nothing without a journal; `AccessHandlePoolVFS` is an OPFS VFS for synchronous builds "offering significant performance advantages"; IndexedDB VFSes "can trade durability for performance by setting PRAGMA synchronous=normal" — [wa-sqlite examples README](https://cdn.jsdelivr.net/npm/@journeyapps/wa-sqlite@1.7.0/src/examples/README.md). Official SQLite WASM added `opfs-sahpool` in 3.43.0 — [PowerSync web persistence post](https://powersync.com/blog/sqlite-persistence-on-the-web).
- DuckDB-WASM OPFS: see KQ1 (npm `latest` creates files but never writes; pin 1.32.0) — [duckdb.org 2026-09-18](https://duckdb.org/2026/09/18/opfs-wasm.html).
- Litestream: "takes over the checkpointing process"; holds "a long-running read transaction to prevent any other process from checkpointing", copies new WAL pages to a "shadow WAL", checkpoints itself; shadow WAL removed once replicated; a "generation" restarts when the WAL chain breaks (e.g. another process checkpoints while Litestream is stopped); restore replays WAL files from the last snapshot, slow for write-heavy DBs; newer versions package pages as LTX files with a monotonic TXID; a `_litestream_lock` table is created in the source db and travels into backups — [litestream.io/how-it-works](https://litestream.io/how-it-works/), [litestream.io v0.3](https://litestream.io/v0.3/how-it-works/), [GitHub README](https://github.com/benbjohnson/litestream). Loss window: asynchronous; a secondary note says "sub-second"; no official figure found.
- LiteFS: see KQ4; FUSE write overhead noted by users; LiteVFS alternative — [fly.io community](https://community.fly.io/t/litefs-setup/12982).
- Durable Objects: SQLite-backed storage currently 1 GB per object, 10 GB planned; key-value and SQL APIs; PITR only for SQLite-backed objects; in-memory state resets on hibernation after "several seconds" idle — [DO concepts (GitHub source)](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/durable-objects/concepts/what-are-durable-objects.mdx), [DO storage API](https://developers.cloudflare.com:2087/durable-objects/api/storage-api). Replication (secondary, see KQ4 gaps): WAL streamed to object storage "batched every 16MB or every ten seconds", forwarded to five nearby replicas, acknowledged after three, 30-day PITR — [simonwillison.net](https://simonwillison.net/2024/Oct/13/zero-latency-sqlite-storage-in-every-durable-object/).
- D1: see KQ4; bookmarks carried in `x-d1-bookmark`-style headers; `"first-unconstrained"` fallback; replicas transparent, one per region — [D1 docs](https://developers.cloudflare.com/d1/best-practices/read-replication/).
- Turso per-user databases: one SQLite file per tenant, exportable; plan caps 500 (free) and 10,000 ($29/month Scaler) databases at the time of the Launch Week post; cross-tenant queries via `ATTACH`; embedded replicas keep a local SQLite copy, reads local, writes remote; per-database and group tokens — [turso.tech/multitenancy](https://turso.tech/multitenancy), [Turso blog](https://turso.tech/blog/database-per-tenant-architectures-get-production-friendly-improvements), [docs.turso.tech](https://docs.turso.tech/integrations/).

### Inferences
- Browser durability is a spectrum the page cannot see: IndexedDB relaxed (seconds), OPFS SAH pool with `synchronous=normal` (checkpoint-time), DuckDB builds that never write. RCEdb in the browser (WASM target) should (judgement) treat every browser store as an index holder under HS-7 and treat D's browser copy as a pending chain, not the durable log, until a `host.Synced` from a server-side admitter arrives. Adopt: "browser = replica with a pending chain" as the default placement; refuse "browser = durable D".
- Litestream's design is a warning about owning the checkpoint: a second checkpointer breaks the WAL chain and forces a new generation. RCEdb has no such hazard because D is append-only and the index is disposable; Litestream's generation + TXID + snapshot is essentially D + seq + snapshot (HS-9). Nothing to adopt beyond noting that D already is the "LTX stream".
- DO's object-per-key with 1 GB storage and Turso's database-per-user with plan caps both show that "one small log per subject, one writer per log" scales operationally; RCEdb's fabrics/placement (E.6, HC-11 to HC-14) is the analogue. Leave open: whether RCEdb should recommend one D per tenant with cross-D joins done by a folding host (Turso's ATTACH) or one D with sharded chains (the proposal's chains). No measurements found to decide.
- D1's bookmark is a client-carried seq for sequential consistency; RCEdb's `upto`/seq in `host.Synced` is the same token. Adopt: expose the admitted seq to clients as a bookmark they pass back so reads on any replica are at least as fresh as their own writes (read-your-writes), which is the D1 pattern.

### Gaps
- OPFS's own flush/`fsync` semantics and how `FileSystemSyncAccessHandle.flush()` maps to SQLite's `synchronous` levels: no primary source found.
- Official Litestream replication interval and loss-window figures not found.
- Official Cloudflare source for the DO replication numbers not retrieved.

## KQ6. Mobile/edge data-loss and durability measurements (fsync on Android/iOS, SQLite power-loss testing)

### Takeaway
There is no rigorous field study of SQLite data loss on phones; what exists is (a) SQLite's own simulated crash and I/O-error harness, (b) a USENIX ATC'20 study showing applications including SQLite cannot recover correctly from fsync failures, (c) the Android "journaling of journal" literature showing SQLite's per-transaction fsync count (four per insert in PERSIST mode) and 5.1x throughput available by fixing it, and (d) anecdotes: full-fsync surviving 10 hard resets on iOS, and an Android deployment reporting "about 10 in 3,000 users per day" losing a database after power loss. Measured, mobile-specific loss rates are a gap.

### Cited Findings
- SQLite crash testing is simulated (KQ1): `test6.c` crash on the N-th `xSync`; I/O-error VFS loop with `integrity_check` — [sqlite.org/testing.html](https://www.sqlite.org/testing.html).
- Rebello et al., "Can Applications Recover from fsync Failures?", USENIX ATC 2020: tested Linux file systems and five applications including SQLite; "although applications use many failure-handling strategies, none are sufficient: fsync failures can cause catastrophic outcomes such as data loss and corruption" — [USENIX ATC'20](https://www.usenix.org/conference/atc20/presentation/rebello).
- Lee et al., WALDIO, USENIX ATC 2015: SQLite "synchronizes each change in the database file or in rollback journal file through fsync()/fdatasync()", each triggering ext4's journal ("Journaling of Journal anomaly"); WALDIO "achieves 5.1x performance (insert/sec) against WAL mode" and "reduces the IO volume to 1/6 compared against the WAL mode" (7.4x when relieved of explicit per-commit syncs) — [ATC'15 PDF](https://usenix.org/system/files/conference/atc15/atc15-paper-lee-wongun.pdf), [UNIST record](https://scholarworks.unist.ac.kr/handle/201301/32825?mode=full). A related paper: "an insert operation using PERSIST journal mode in SQLite, the default database for Android devices, issues four fsync() calls" — [KAIST SAC paper](https://oslab.kaist.ac.kr/wp-content/uploads/esos_files/publication/conferences/international/coarsegrained_mtime_update_SAC.pdf). The JOJ term originates in Jeong et al. 2013 — [I/O stack optimization for smartphones](https://solar.cs.ucl.ac.uk/appoptimization.github.io/publications/JLL2013).
- iOS anecdote (SQLite forum 2022, iPhone on iOS 13.5.1): corruption after simulated hard resets; "Full fsync, both with and without mmap_size, survived 10 hard reset loops"; full fsync "has a very significant performance impact for an issue that has occurred very rarely" — [SQLite forum](https://sqlite.org/forum/info/65f7b6246d8244b23268).
- Android anecdote (Zetetic forum): SQLCipher database "left containing only the metadata table after sudden power loss", "about 10 in 3,000 users per day", not reproducible — [discuss.zetetic.net](https://discuss.zetetic.net/t/sqlite-cipher-db-file-lost-after-android-get-lost-power-quickly/884) (anecdotal).
- Mohan et al. (HotStorage'17, from the PDF): Android's default SQLite mode is DELETE journal with `synchronous=FULL`; WAL-NORMAL checkpoints every 1000 pages; in DELETE-FULL "SQLite issues an fsync() after every transaction" — [HotStorage'17 PDF](https://microsoft.com/en-us/research/uploads/prod/2021/10/hotstorage17-paper-mohan.pdf).
- PSOW and "no redundancy for detecting corruption" (KQ1) — [sqlite.org/psow.html](https://sqlite.org/psow.html).

### Inferences
- The one reproducible mobile result is that SQLite's default Android configuration pays four fsyncs per insert and a 5–7x throughput penalty for durability, while its WAL-NORMAL mode trades that for a loss window. Judgement: RCEdb on mobile should batch admits per window (HC-17 `host.Window` already groups entries) and fsync once per window, which is the WALDIO/group-commit lesson; the durable mark then moves per window, which `host.Synced(upto)` already expresses. Adopt.
- ATC'20 shows that an application cannot assume fsync errors are recoverable; RCEdb's T39 ("after a failed barrier the admitter appends nothing") is the correct response and is stronger than every surveyed engine's. Adopt (already).
- SQLite's "no redundancy" plus the Zetetic report (a database reduced to its metadata table) argues for the per-entry hash chain: a truncated or torn D is detected and cut back (T38), not silently accepted. Adopt (already).
- Leave open: whether Apple's `F_FULLFSYNC` must be mandated for D on iOS/macOS; the evidence (losing the latest transaction, not corruption) suggests it is a loss-window question that `host.Synced` makes visible rather than a correctness one.

### Gaps
- No peer-reviewed, mobile-specific measurement of SQLite data-loss or corruption rates after power loss was found; only anecdotes.
- OPFS/IndexedDB loss rates on mobile browsers: nothing found.
- SQLite's WAL frame checksum/salt mechanism (how torn WAL writes are detected) was not sourced before the search budget ended.

## KQ7. Energy on devices: joules-per-operation for SQLite/RocksDB on mobile or embedded hardware

### Takeaway
Only one primary measurement set exists for SQLite on a phone (Mohan et al., HotStorage'17, Monsoon power monitor on an Android eMMC device): storage is 36% of system energy under random-I/O load, random 4 KB writes with fsync cost about 800 µJ/KB and 15x a sequential write, and SQLite update/delete energy is 1.5x lower on F2FS than ext4 in WAL-NORMAL mode; the per-operation joule bars (Figure 2) are in the graph only, not the text. No joules-per-operation figures for RocksDB on mobile were found.

### Cited Findings (all from the retrieved HotStorage'17 PDF unless noted)
- "for certain storage-intensive workloads, the storage subsystem on an Android smartphone consumes a significant amount of energy (36%), on par with screen energy consumption"; "random writes consume 15× higher energy than sequential writes, and ... F2FS consumes half the energy" of ext4 for most workloads — [Mohan et al., HotStorage'17](https://www.usenix.org/conference/hotstorage17/program/presentation/mohan).
- Setup: a commercial Android phone, internal eMMC `/data`, a Monsoon hardware power monitor, differential measurement; the workload is 100 MB of 4 KB random reads/writes over a 1 GB file, each write followed by `fsync()` — same PDF.
- Random writes: "an average of 800 uJ/KB"; for 10 MB of random writes blktrace shows ext4 writing "around 70MB" at block level vs "only 30MB" on F2FS (write amplification 7x vs 3x); random reads 7x more energy than sequential on ext4, 8x on F2FS; 100 MB random reads become 195 MB (ext4) / 272 MB (F2FS) at block level — same PDF.
- SQLite: 15,000 each of inserts, updates, deletes at 4 KB record size; Android default is DELETE-FULL; in DELETE-FULL ext4 is slightly lower energy than F2FS "because SQLite issues an fsync() after every transaction ... nullifying the benefits of sequentialization in F2FS"; in WAL-NORMAL "updates and deletes are about 1.5× lower, while inserts consume about 1.3× higher energy in F2FS as compared to ext4"; "inserts consume equal or lower energy than updates and deletes in both file systems" because inserts are sequential appends — same PDF (Figure 2 values are graphical; not extracted).
- The paper cites Li et al. that "the storage stack consumes 200× the energy of storage hardware" — same PDF (secondary citation inside the paper).
- PocketData (Kennedy, Challen et al., TPCTC 2019, Buffalo): a workload generator "to evaluate both performance and power consumption of SQLite on Android"; Android's default CPU frequency governors "can make queries slower and use more power than simpler heuristics"; saturation benchmarks hide this — [TPCTC PocketData PDF](https://odin.cse.buffalo.edu/papers/2019/TPCTC-PocketData.pdf). TPCdroid (JUCS 2014) ran TPC-H on Android and found "lowering frequency is not always helpful for reducing energy consumption" — [JUCS 20(10)](https://www.jucs.org/jucs_20_10/exploiting_the_performance_energy/jucs_20_10_1488_1498_yang.pdf).

### Inferences
- The decisive energy variable on flash is write pattern and fsync count, not engine: random+fsync is 15x sequential, and a per-transaction fsync erases F2FS's advantage. An append-only hash-chained log with one fsync per window is the lowest-energy shape this evidence supports (estimate: at 800 µJ/KB random vs roughly 1/15 of that sequential, a 4 KB entry appended sequentially costs on the order of 0.2 mJ rather than 3 mJ; this is an extrapolation from the paper's averages, not a measured figure). Adopt: D is appended sequentially; index rewrites (random) should be deferred and batched, which HS-7 permits since indexes need not be durable.
- RocksDB-on-mobile energy: no data; the LSM's sequential writes would be favoured by the same reasoning but at 10–30x write amplification (KQ1 mirror figure), so the net is unknown. Leave open.
- RCE's own energy-calibration proposal (`spec/proposals/energy-calibration.md`, not read here) should cite Mohan's 800 µJ/KB and 15x figures as the only primary mobile storage-energy baseline found.

### Gaps
- Per-operation joule values for SQLite insert/update/delete (Figure 2 of Mohan et al.) are not in the extractable text; the paper must be read as a rendered figure to quote them.
- PocketData's measured power numbers were not retrieved (only the methodology finding).
- No published joules-per-operation figure for RocksDB, LevelDB, LMDB, redb or sled on mobile or embedded hardware was found in this session.
- Searches for microcontroller-class (ESP32/Cortex-M) SQLite or key-value energy figures were not run before the budget ended.
