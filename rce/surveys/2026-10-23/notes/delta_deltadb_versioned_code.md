## Key question 1 — Delta: what it is, threads, agent/human context sharing, guided reviews, browser version, platforms, beta status and dates, pricing, Zed turning off pull requests

### Takeaway
Delta is a standalone multiplayer application (not a Zed editor feature) "for coding with agents and reviewing what they build", organised around *threads* that bind an agent conversation to the worktree it edits; announced 12 Aug 2026 (private beta), public beta 16 Sep 2026 on macOS/Linux/Windows plus a web build, free during beta with paid plans promised. Zed reports it has disabled pull requests on Delta's own (private) repository and landed 570 changes to main from 33 people through Delta threads; the public Zed editor repo still uses PRs.

## Key question 2 — DeltaDB: what it stores, relation to Git, data model, content-addressing / append-only / hash-chaining, DAG, determinism/replay, conflicts and CRDTs, where data lives, open source, published architecture, benchmarks, limits

### Takeaway
DeltaDB is a CRDT-based operation log layered beside Git: each edit (by person or agent), file-tree change, message and comment is a "delta" with a stable identity, an author and the version it builds on, where a base is either earlier deltas or a Git object (commit or blob); ordering comes from the causal graph (a DAG) rather than a clock; Git keeps commits, branches and remotes. Data is stored on the user's machine *and on Zed's servers*; agent conversations pass through Zed Cloud. Zed says it intends to open-source DeltaDB but no engine source, benchmarks, storage-growth figures or self-hosting option had been published by 23 Oct 2026; there is no published claim of hash-chaining or content-addressing of deltas.

### Cited Findings
- First public description (funding post, 20 Aug 2025, $32M Series B led by Sequoia, total funding past $42M): DeltaDB "records every operation rather than only commits", "uses CRDTs to incrementally record and synchronize changes as they happen", and "is designed to interoperate with Git, though its operation-based design supports real-time interactions that Git's snapshots don't"; fine-grained tracking "enables character-level permalinks that survive any code transformation". — [Zed blog: Sequoia Backs Zed](https://zed.dev/blog/sequoia-backs-zed); [Gus Mueller quoting the post, Aug 2025](https://shapeof.com/archives/2025/8/deltadb_from_zed.html)
- Zed 1.0 post: "Zed is actively developing DeltaDB, a synchronization engine built on CRDTs that tracks every change with character-level granularity." — [Zed blog: Zed is 1.0](https://zed.dev/blog/zed-1-0)
- "Software Is Made Between Commits" (Zed blog, Jun 2026; GIGAZINE coverage dated 12 Jun 2026; HN thread "Zed DeltaDB" item 49187256 reported at 241 points / 110 comments by an aggregator): DeltaDB is "built on a single coherent abstraction that transforms your conversations with agents and the worktrees they edit into shared artifacts"; "Where Git captures a snapshot at each commit, DeltaDB captures every operation in between and gives each one a stable identity"; it uses "conflict-free replicated worktrees"; "DeltaDB doesn't replace Git"; waitlist opened Jun 2026. — [Zed blog: introducing-deltadb](https://zed.dev/blog/introducing-deltadb); [GIGAZINE, 12 Jun 2026](https://gigazine.net/gsc_news/en/20260612-zed-deltadb/); [HN item 49187256](https://news.ycombinator.com/item?id=49187256); [TechTimes, 13 Jun 2026](https://www.techtimes.com/articles/318322/20260613/zed-opens-deltadb-waitlist-crdt-version-control-records-every-edit-not-just-commits.htm)
- Product page (delta.dev/deltadb, "Keep the context behind every change"): DeltaDB "records work as a stream of fine-grained deltas as it happens, alongside the conversation that produced it. Git stays in place for commits, branches, and remotes"; "Each edit, from a person or an agent, is recorded as a delta with a stable identity, its author, and the version it builds on"; "each delta names the version it builds on, which is either earlier deltas or a Git blob holding a file's starting text. Ordering then comes from the causal graph rather than a shared clock"; "edits sync as they're typed, and ... concurrent edits resolve identically on every machine regardless of arrival order"; DeltaDB is "built on CRDTs, loosely based on diamond-types and adapted to work with Git"; storage "grows with the size of the edits instead of the number of edits squared". — [delta.dev/deltadb](https://delta.dev/deltadb)
- Conrad Irwin (Zed), "DeltaDB: The Future of Version Control", Delta blog, 15 Oct 2026, based on his Bay Area Rust talk "Building a Distributed CRDT Layer for Git" (June 2026): DeltaDB is "a collaboration layer for software development, where changes sync to collaborators and the server as you type"; "not meant to replace Git"; design "loosely based on the diamond-types approach, adapted so it can interoperate with Git"; "a CRDT edit must record where and when it happened. A delta is either based on something in Git, such as a commit or blob, or on earlier deltas"; "each change is identified by its parent in the causal graph, so no distributed clock is needed"; conflict detection: "an incoming edit is based on a version that lacks the local edit", resolved via "a fragment index to place the incoming text, so position alone isn't enough to locate it"; the post walks through two concurrent insertions yielding two possible merged orders. — [Delta blog: future-of-version-control](https://delta.dev/blog/future-of-version-control); [talk recording](https://www.youtube.com/watch?v=yif2rday2bw)
- Where data lives (official docs, "Data Storage & Deletion"): "Delta uses DeltaDB to store its contents and history on your machine and on our servers." Stored items: repository Git objects; a change log of "deltas" (edits, file-tree changes, messages, comments); metadata including "The Git remote URL you configured, the derived repository name, and a normalized lookup key" ("Avoid remotes that embed credentials"), collaborators' GitHub logins, commit author and message details. Threads "stay private unless you share them or change the default visibility to your organization". Agent conversations "including code the agent quotes, pass through Zed Cloud to your chosen model provider". — [Delta docs: data storage](https://delta.dev/docs/privacy-and-security/data-storage)
- Worktree virtualisation: "Delta DB virtualizes the work tree, making these isolated clones cheap to create"; "creating a new agent branch doesn't involve copying files on disk, per Zed"; agents work in isolated per-thread worktrees/clones by default; "any point in history [is] a valid branch point, including mid-run states". — [AlphaSignal, Aug 2026](https://alphasignal.ai/news/zed-launches-delta-to-replace-git-where-ai-agents-write-code); [Sesame Disk](https://sesamedisk.com/what-is-zed-deltadb-features/); [aiidelist.com](https://aiidelist.com/ide/delta)
- Open source: Zed "intends to open source Delta DB, with optional paid services layered on top, and eventually integrate Delta DB's capabilities into the main Zed editor". An August 2026 analysis: "no package to install, no public CLI, and no open technical documentation", and Zed "hasn't yet published how it plans to handle that history's growth or whether there will be any pruning or summarization mechanism". An HN commenter on the Delta thread noted "neither Delta nor, it seems, DeltaDB is open source, unlike Zed". — [Sesame Disk](https://sesamedisk.com/what-is-zed-deltadb-features/); [agentmarketcap, 5 Aug 2026](https://agentmarketcap.ai/blog/2026/08/05/zed-deltadb-agent-native-database); [HN 49276574](https://news.ycombinator.com/item?id=49276574)
- Roadmap: "Zed's next major dependency is Git storage, which it intends to bring into DeltaDB." — [The New Stack, Sep 2026](https://thenewstack.io/zed-delta-github-alternative/)
- Zed likens Delta + DeltaDB to Ted Nelson's Xanadu ("kept every version of a document, hypertext links that knew source and destination, and quotations kept by reference"). — [Zed on X, Sep 2026](https://x.com/zeddotdev/status/2094825392683270306)

### Inferences
- Data model as published: an operation log ("deltas") whose entries are identified by position in a causal DAG, with Git blobs/commits as roots. That is append-only in practice (CRDT op logs are), and deterministic in the CRDT sense (same op set gives same state regardless of arrival order), but Zed has **not** published that deltas are hash-chained, content-addressed, or that replay is verified; "stable identity" is described as causal-parent-derived, not as a content hash. Treat hash-chaining/content-addressing as unconfirmed.
- Because the base of a delta can be a Git blob, DeltaDB can be dropped onto an existing repo without rewriting Git history; commits remain Git commits, so Git compatibility is by reference, not by translation.
- "Storage grows with the size of edits, not edits squared" is a complexity claim about the index (consistent with diamond-types' run-length encoded op log), not a benchmark.
- The server is a required participant for sync ("changes sync to collaborators and the server as you type"; stored "on our servers"); there is no published offline-only or self-hosted mode.

### Gaps
- No published architecture document, schema, wire format, benchmark, size limit, GC/compaction policy, or Jepsen-style analysis for DeltaDB as of 23 Oct 2026.
- Whether DeltaDB reuses the Zed editor's in-buffer CRDT code or is a fresh implementation is not stated in the sources found; the product page cites diamond-types (Joseph Gentle's Rust CRDT) as the design basis, which is not the Zed buffer CRDT lineage.
- Full text of Conrad Irwin's post and the data-storage doc page could not be read; quotes are index extracts.

## Key question 3 — Hacker News and other technical discussion: strongest criticisms and defences

## Key question 4 — Zed's prior technical foundations (CRDT collaboration, GPUI, channels, Teletype/xray)

### Takeaway
Zed's founders (Sobo, Brunsfeld, Scandurra) built Atom and Teletype (2017), where the buffer was not collaborative and Teletype "basically replicated the entire buffer" via a CRDT bolted on; Zed was rebuilt with a CRDT text buffer at its core (rewritten "two or three times"), and real-time collaboration (channels, shared projects) ships in the editor. DeltaDB extends this lineage from live buffer sync to a persisted, Git-anchored operation history, but Zed has not published a deep design post on its buffer CRDT.

### Cited Findings
- Max Brunsfeld: "in Atom, they tried building Teletype, and the big problem was that the core data structures of the editor were not collaborative. The workaround basically replicated the entire buffer." — [Zed blog: The Full Spectrum of Collaboration](https://zed.dev/blog/full-spectrum-of-collaboration)
- Teletype (Nov 2017): each collaborator "modifies their own replica of a document, and the CRDT should ensure all replicas end up with the same content". — [InfoQ, Nov 2017](https://www.infoq.com/news/2017/11/atom-teletype-collaboration)
- Antonio Scandurra: the buffer "wasn't always a CRDT"; he and Sobo "read a lot of papers before settling on the approach"; "rewrote it two or three times, but the approach is more or less the same". — [Zed blog: We Have to Start Over](https://zed.dev/blog/we-have-to-start-over)
- Zed lists itself among CRDT implementations. — [crdt.tech implementations](https://crdt.tech/implementations)
- Zed's `crates/collab` contains randomized project-collaboration integration tests (file `crates/collab/tests/integration/random_project_collaboration_tests.rs` matched a "deltadb" code search), showing the collab server is tested by randomized operation interleaving. — [GitHub code search, zed-industries/zed](https://github.com/zed-industries/zed)
- DeltaDB's stated basis is diamond-types rather than the editor buffer CRDT ("loosely based on diamond-types and adapted to work with Git"). — [delta.dev/deltadb](https://delta.dev/deltadb)

### Inferences
- Zed's collaboration stack has always been operation-based (CRDT ops over a server relay); DeltaDB generalises "ops over a live session" into "ops persisted beside Git with conversation ops in the same log". The novelty is persistence and Git anchoring, not the CRDT itself.

### Gaps
- No Zed blog post explaining the buffer CRDT in depth was found; "how Zed does collaboration" as a titled post was not located. GPUI and channel docs were not reachable.

## Key question 5 — The wider field: what each system stores, and what a "database of code" needs that Git lacks

### Takeaway
Git stores content-addressed snapshots (blobs/trees/commits) with no first-class notion of a change, author intent, or semantic identity; Pijul stores commuting patches; Jujutsu stores Git commits plus a separate change identity and first-class conflicts; Fossil stores artifacts in a SQLite relational store with tickets/wiki beside code; Dolt stores content-addressed prolly trees of SQL tables with cell-level diffs; Unison stores definitions by hash of their syntax tree with names as repointable metadata; Piper/CitC and Sapling/EdenFS virtualise huge monorepos on database/virtual-filesystem backends. None records *why* a change was made as a checked artefact; DeltaDB adds conversation-as-provenance, and Unison alone gives semantic (hash) identity to definitions.

### Cited Findings
- Pijul: "commutation property means independent changes can be applied in any order without changing the result or the version's identifier"; conflicts "treated as the standard case rather than a failure to merge"; criticism: the graph "only tracks patch-level dependencies, so semantic dependencies between patches go unseen". — [HN Pijul thread, 2026](https://news.ycombinator.com/item?id=47672941); [64p.org notes on Pijul](https://64p.org/notes/pijul.html)
- Jujutsu: "does not work from a theory of patches ... but it does separate changes from revisions and treats conflicts as first-class items, borrowing those ideas from Mercurial, Pijul, and Darcs"; eliminates the staging area and "stores merge conflicts as commits you can walk away from and resolve later"; native (non-Git) backend "still not ready for regular use". — [Chris Krycho, jj init](https://v5.chriskrycho.com/essays/jj-init/); [kunalganglani, 2026](https://www.kunalganglani.com/blog/jujutsu-jj-git-version-control)
- Fossil: bundles "bug tracking, wiki, forum, email alerts and chat with its distributed VCS", is "the primary tool for the SQLite project", and its Git mirror "is one-way and lossy". — [Soundbarrier: Version Control Beyond Git](https://www.soundbarrier.io/posts/git_alternatives/)
- Dolt: prolly trees are "a content-addressed, immutable data structure where each node is identified by a hash of its contents"; "branching and diffing do not get slower as the database grows"; "structural sharing across revisions"; version-control primitives "operate at the level of table cell"; Dolt, Doltgres and DoltLite are Apache-2.0 (LWN, May 2026). — [Better Stack Dolt guide](https://betterstack.com/community/guides/databases/dolt-git-version/); [Console interview with Zach Musgrave](https://console.substack.com/p/console-132); [LWN, May 2026](https://lwn.net/SubscriberLink/1068864/4d53e651a1254bce/)
- Unison: "each definition is identified by a hash of its syntax tree"; "Names are like pointers to addresses in this space. We can change what address a name points to, but the contents of each address are forever unchanging"; the Codebase Manager (ucm) manipulates the codebase; a bug fix "works by computing a new hash and repointing the name, while the codebase keeps its full history, similar to git". — [Unison docs: The Big Idea](https://www.unison-lang.org/docs/the-big-idea/); [Unison FAQ](https://www.unison-lang.org/docs/usage-topics/general-faqs/)
- Google Piper/CitC (Potvin & Levenberg, CACM 2016): Piper "implemented on top of standard Google infrastructure, originally Bigtable, now Spanner"; CitC lets developers "browse and edit files anywhere across the Piper repository, and only modified files are stored in their workspace"; "over 80% of Piper users today use CitC". — [CACM: Why Google Stores Billions of Lines of Code in a Single Repository](https://dl.acm.org/doi/fullHtml/10.1145/2854146)
- Sapling/EdenFS (Meta): EdenFS "speeds up operations in large repositories by only populating working directory files on demand"; FUSE on Linux, NFSv3 on macOS; "used in production within Meta but is not yet supported for external use". — [facebook/sapling README](https://github.com/facebook/sapling); [EdenFS Overview](https://github.com/facebook/sapling/blob/main/eden/fs/docs/Overview.md)
- Darklang "deployless": language, editor and hosted infrastructure in one; deployments claimed at "about 50 milliseconds"; safety via feature flags and versioning; current focus includes "a deployless workflow with DB migrations, branches, and pull requests". — [Darklang blog: Unveiling Dark](https://blog.darklang.com/unveiling-dark); [SE Daily](https://softwareengineeringdaily.com/?p=7095)
- A competitor positioning piece contrasts Delta's "sync layer" (CRDT operation replication) with a "shared machine" model. — [aq.dev: AQ vs Zed Delta](https://aq.dev/compare/aq-vs-zed-delta/)

### Inferences
- Axes on which the field differs: (a) unit of history — snapshot (Git, Dolt), patch (Pijul), op/delta (DeltaDB, Zed buffers), definition (Unison); (b) identity — content hash (Git objects, Dolt nodes, Unison defs), causal position (DeltaDB), patch hash (Pijul), change-id (jj); (c) what sits beside code — tickets/wiki (Fossil), conversation (DeltaDB), nothing (Git). Only Unison and Git/Dolt are content-addressed; only DeltaDB stores provenance conversation; none stores a checked *intent* or *examples* as part of the record.
- What a "database of code" needs that Git lacks, per these sources: semantic identity of definitions (Unison solves), first-class changes and conflicts (jj/Pijul solve), provenance of who/what produced an edit (DeltaDB solves at keystroke level), and a declared, checkable reason for the change (none solves).

### Gaps
- No single comparative survey was found; Graphite, Replit multiplayer (OT-based) and GitHub Copilot Workspace returned no usable results in this session and are not cited. Fossil's internal artifact/SQLite schema was not fetched.

## Key question 6 — Agent collaboration primitives: how Delta, Cursor, Devin, OpenHands, Jules etc. record agent actions, provenance and review; whether any gates on intent/examples; measured acceptance rates

### Takeaway
Delta is the only product found that records agent edits and the conversation that produced them as one synchronised, reviewable log, but it gates nothing: review is post hoc and agent-generated. Published acceptance data for agent PRs (AIDev dataset, 2025–26) show agents below the human baseline overall (Codex ~64%, Devin ~49%, Copilot ~35% vs 76.8% human in one summary; LinearB 2026: AI PRs merge within 30 days 32.7% vs 84.4% unassisted), with task type the dominant factor and 67.9% of rejected agent PRs lacking any reviewer feedback.

### Cited Findings
- Delta records "every edit and conversation ... between your commits" and ties "each change to the agent conversation that produced it"; third-party agents connect over ACP, with Claude Code first; Zed ships a Claude Code plugin (`delta-claude`) with hooks for setup, sharing and watching. — [Zed on X](https://x.com/zeddotdev/status/2087602344020135974); [Zed blog: Introducing Delta](https://zed.dev/blog/introducing-delta); [zed-industries/delta-claude](https://github.com/zed-industries/delta-claude)
- AIDev dataset: "over 456,000 pull requests authored by five prominent autonomous coding agents" (OpenAI Codex, Devin, GitHub Copilot, Cursor, Claude Code); a later snapshot counts "932,791 Agentic-PRs created between 2025-01-01 and 2025-08-01"; acceptance: Codex ~64%, Devin ~49%, Copilot ~35%, human baseline 76.8%; Claude Code 85.7% on documentation PRs vs 76.5% human. — [AIDev paper, arXiv 2507.15003 (alphaXiv summary)](https://www.alphaxiv.org/abs/2507.15003v1); [On the Use of Agentic Coding (ACM)](https://dl.acm.org/doi/10.1145/3798166)
- Pinna et al., MSR 2026 Mining Challenge, 7,156 PRs (AIDev-POP): "task type is the dominant factor influencing acceptance rates"; Devin "the only consistent positive trend (+0.77%/week over 32 weeks)"; Claude Code leads documentation (92.3%) and features (72.6%); Cursor leads fixes (80.4%); Codex most consistent (59.6%–88.6%); authors warn acceptance rate "as a sole quality proxy may be misleading". — [Pinna et al. 2026, arXiv 2602.08915](https://arxiv.org/html/2602.08915v2); [MSR 2026 listing](https://2026.msrconf.org/details/msr-2026-mining-challenge/16/Comparing-AI-Coding-Agents-A-Task-Stratified-Analysis-of-Pull-Request-Acceptance)
- "Why Agentic-PRs Get Rejected" (2026): of 654 rejected agent PRs, "67.9% lack explicit reviewer feedback". — [arXiv 2602.04226](https://arxiv.org/html/2602.04226v1)
- LinearB 2026 benchmark: AI PRs merge within 30 days 32.7% of the time vs 84.4% for unassisted work; elite thresholds >95% manual vs ~71% AI; "Devin's acceptance improved from April while Copilot's declined from May". — [LinearB, 2026](https://linearb.io/library/ai-in-software-development)
- A 2026 study on "follow-up fixes and commit authorship on AI coding agent pull requests" exists ("Who Finishes the Job?") but its findings were not retrievable. — [arXiv listing](https://arxiv.org/pdf/2609.26847)

### Inferences
- Every measured agent workflow (Codex, Devin, Copilot, Cursor, Claude Code) uses the PR as the gate and records provenance only as a PR author label; Delta moves provenance to keystroke level but still has no declared-intent or example-based admission check. No system found records intent or examples as a gate; this is RCE's distinguishing claim and it is unoccupied.
- Low acceptance rates with no reviewer feedback (67.9%) suggest the bottleneck is review capacity, which supports both Delta's "review beside the thread" and RCE's "check at a gate before the human sees it" — but only the latter is machine-checkable.

### Gaps
- No published Delta acceptance/review-rate data. Cursor, Devin, OpenHands and Jules provenance formats were not individually sourced in this session.

## Key question 7 — Positioning: RCE's hash-chained event log + content-addressed `defs` + emit-target registry relative to DeltaDB; what a DeltaDB-like layer over RCE's log would be; what to adopt, refuse, leave open

### Takeaway
DeltaDB and RCEdb both treat "the log is the database", but they log different things with different guarantees: DeltaDB logs text edits and chat as CRDT ops ordered by a causal DAG, is server-synced, unverified and closed; RCE logs typed events in a SHA-256 hash-chained, append-only, Lean-proved-deterministic fold, with content-addressed definitions and intent/example gates. RCE should adopt three things from Delta/DeltaDB (conversation-as-provenance stored in the same log; Git-object anchoring so the layer drops onto existing repos; stable anchors that survive edits for review comments), refuse three (text-level CRDT as the unit of history, mandatory cloud relay, post-hoc agent-generated review as the gate), and leave open the live-collaboration question until DeltaDB's engine is published.

### Cited Findings
- DeltaDB stores deltas "with a stable identity, its author, and the version it builds on", bases are "earlier deltas or a Git blob", and ordering is "the causal graph rather than a shared clock". — [delta.dev/deltadb](https://delta.dev/deltadb)
- DeltaDB keeps data "on your machine and on our servers" and agent traffic passes "through Zed Cloud". — [Delta docs: data storage](https://delta.dev/docs/privacy-and-security/data-storage)
- Zed's stated scope: "not aiming to replace Git or continuous integration". — [daily.dev mirror of Zed post](https://daily.dev/posts/zed-s-delta-rethinks-git-for-a-world-of-ai-agents-ndr9gkvor)
- Unison's hash-of-syntax-tree identity with repointable names is the closest published analogue to RCE's content-addressed `defs`. — [Unison docs](https://www.unison-lang.org/docs/the-big-idea/)
- HN critique that Delta does not show *why* code changed, and that it removes the merge gate. — [HN 49727245](https://news.ycombinator.com/item?id=49727245); [rohitghumare.com](https://rohitghumare.com/blog/zed-delta-after-pull-requests/)
- Agent-PR acceptance is well below human baseline and most rejections carry no feedback. — [AIDev summary](https://www.alphaxiv.org/abs/2507.15003v1); [arXiv 2602.04226](https://arxiv.org/html/2602.04226v1)

### Inferences
- Comparison matrix (RCE facts from the task brief; DeltaDB facts as cited above):
  - Unit of record: DeltaDB = character-level edit/message/comment delta; RCE = typed event in D.
  - Identity: DeltaDB = causal-parent position (hash-chaining unpublished); RCE = SHA-256 hash chain over events, content-addressed `defs`.
  - Determinism: DeltaDB = CRDT convergence (claimed, unverified); RCE = Lean-proved fold determinism.
  - Provenance: DeltaDB = author + conversation beside edits; RCE = events (who/what emitted is representable but, per the brief, conversation provenance is not yet an RCE primitive).
  - Gate: DeltaDB = none before landing (agent-written review guide after); RCE = `intent` and `example` admission gates.
  - Git relation: DeltaDB = sidecar referencing Git blobs/commits; RCE = separate log; the proposed emit-target registry would be the natural place to anchor emitted artefacts to Git objects the way DeltaDB anchors deltas to blobs.
  - Storage: DeltaDB = local + Zed servers, closed source; RCE = local, open monorepo.
- Adopt: (1) record the model/human conversation that produced an event as events in the same hash-chained log (DeltaDB's one strong idea, answering the HN "why" objection better than Delta does because the intent block is also there); (2) anchor each emitted artefact to the Git blob/commit it was emitted into (DeltaDB's "base is a Git object" trick) via the emit-target registry, so RCE works on unmodified repos; (3) stable anchors for review comments computed from the log rather than line numbers.
- Refuse: (1) character-level CRDT ops as the unit of history — RCE's unit is a typed event over definitions, which is what gives semantic identity (Unison's lesson) and keeps the log small and checkable; (2) a mandatory cloud relay — RCE's determinism theorem does not need a server to converge; (3) agent-generated review guides as the admission mechanism — RCE's gate is checked before admission, which is the gap both HN and the rejection statistics expose.
- Leave open: real-time multi-writer collaboration on a single program. Appending to a hash chain from two writers requires ordering; DeltaDB's answer is a CRDT DAG; RCE would need either a merge rule for concurrent event batches (a DAG of chain segments, cf. Pijul/jj first-class conflicts) or a single sequencer. Revisit when DeltaDB's engine is open-sourced (promised, not delivered as of 23 Oct 2026).
- A "DeltaDB-like layer over RCE's log" would be: an index (a fold of D) that groups events by the thread/conversation that emitted them, exposes "from any definition hash, find the intent, examples and conversation that admitted it; from any message, find the definitions it changed", and anchors each emit to a Git object — the first two are already expressible as RCEdb typed queries, the third is the emit-target registry.

### Gaps
- Zed has not published DeltaDB's schema, hashing, or verification model, so any claim that DeltaDB is or is not tamper-evident is unconfirmed; the comparison above uses only what Zed has stated.
- RCE's own conversation-provenance and multi-writer semantics are described from the task brief, not from sources found in this session.
