# Energy-aware compilation, per-op energy cost models and measurement — design input for the Reality Code Engine

Grounding (read first, before any web search). Everything below is framed against the RCE state as it stands on 2026-10-22:

- Labels. `est_j` is an analytical estimate; `reported_j` is an OS or on-chip counter; `measured_j` "is reserved for a wall meter and is empty in every result here" — [RCE paper §1](https://research.openie.dev/papers/rce/). The receipts proposal sharpens `measured_j` to "a wall or shunt meter on a named rail" and fixes a label lattice `unpriced < est < reported < measured` in which a combined figure carries the weakest label — [receipts-P1-P10](file:///tmp/claude-0/-home-claude/a51bc2e6-10c5-5671-9c6b-8af67db8621d/scratchpad/repos/rce/spec/proposals/receipts-P1-P10.md).
- Definition 7: `cost_J(t)` = `est_j` to run t once on a named substrate, weighted by expected runs. Proposition 3: extraction under `cost_J` returns the least-joule term the extractor finds in F's e-class, because rewrites are sound and cost is joules. Proposition 7: ι = dX/dJ, read in hindsight from D; extraction under `cost_J` holds the gate fixed and does not raise J — [RCE paper §3.4](https://research.openie.dev/papers/rce/).
- Pricing today: `est_j` is "op count priced by the substrate table" (Prop R3), concretely "interpreter operation counts using the FGIR host cost table"; `est_j` is required on every receipt, finite non-negative or null only when `basis` is `unpriced`; unpriced is never read as 0 J; model calls carry `est_uj`; one ladder subsample adds a package energy counter as `reported_j`; a worked example of extraction lowers `est_j` from 1.69×10⁻⁸ J to 1.49×10⁻⁸ J — [RCE paper §4.4, §5.6](https://research.openie.dev/papers/rce/).
- C.6 (draft 0.6 concurrency): "Cost is a deterministic accounting of Form operations, the same on every target; it is not a measurement of time or energy (est_j is separate)." Table: `c_call` 4, stdlib method 4 + work(m,n,k), `c_chan` 8, `c_spawn` 32, `c_fork` 16, list literal 4+n, index/member 1, unary 1, int/bool/text binop 1, float +−× 2, float / 8; work classes linear n+k, sort n⌈log₂n⌉, constant 0. Stated rationale: "A budget is a proxy for energy, and energy scales with the operations performed" — [14-draft06-concurrency.md C.6](file:///tmp/claude-0/-home-claude/a51bc2e6-10c5-5671-9c6b-8af67db8621d/scratchpad/repos/rce/spec/book/14-draft06-concurrency.md).
- E.6/E.7: HC-12 places lane-wise ops "from the cost table of C.6.4 extended with per-fabric overhead and throughput (time = overhead + work / throughput), whose calibration results are `host.Calibrated` entries"; placement is a function of D and replays (T37). HC-14: energy and thermal counters are input events. `host.FabricCaps` = {cpu, gpus, npus, memory, counters}; `counters` names readable energy and performance counters; a field the host cannot query is `null` — [16-host-contract.md E.6–E.7](file:///tmp/claude-0/-home-claude/a51bc2e6-10c5-5671-9c6b-8af67db8621d/scratchpad/repos/rce/spec/book/16-host-contract.md).
- Receipts P4–P6 (adopted): `reported_j` without `reported_j_provenance` {sampler, counter, interval, idle baseline, machine} is refused; `boundary` (what the joules include) is required for `reported_j` and `measured_j`; `amortization` ∈ {per_call, batch_mean, per_solved_task} is required and figures with different amortization may not be summed — [receipts-P1-P10](file:///tmp/claude-0/-home-claude/a51bc2e6-10c5-5671-9c6b-8af67db8621d/scratchpad/repos/rce/spec/proposals/receipts-P1-P10.md).

## Q1. Measurement: RAPL accuracy and pitfalls, vendor counters, wall meters, methodology standards

### Takeaway
RAPL on Intel Haswell and later correlates with wall power at r ≈ 0.99 and predicts plug power to ~2 % MAPE once DRAM is included, but it is a 1 ms-update, non-atomic, 32-bit-overflowing counter with ~10 % thermal drift; AMD RAPL is modeled, has no DRAM domain and misses operand-data effects; NVML on A100/H100 samples only ~25 % of runtime and consumer-card cumulative counters are stale below 100 ms; Jetson INA3221 under-reads by up to 50 %; Apple powermetrics has no published validation. No counter qualifies as `measured_j`; every counter needs the P4 provenance object, and wall meters need SPEC/MLPerf-style windows (≥60 s, ideally 240 s per level) plus interleaving.

### Cited Findings
Intel RAPL
- Haswell package RAPL vs wall power r = 0.99 (Stream, several frequencies). Over ~1000 production nodes, a linear model from RAPL to plug power: MAE 5.6 W, RMSE 9.8 W, MAPE 1.8 % (Haswell); Sandy Bridge 4.0–4.3 % with no DRAM domain. CPU-only modeling 3.1 % error, +DRAM 1.7 %, DRAM alone 7.7 %. Counters update ~1 ms (measured mean 1.00229 ms), no timestamps, 32-bit, overflow ~52 min at 84 W with 61 µJ units. Domain counters are not updated atomically (PP0 lags PKG by 2.8–3.6 µs); at 200 Hz the 4-to-6-update jitter gives ±20 % spikes. Package power rose 10–12 % between ~37 °C and ~74 °C on Haswell (r = 0.93 with temperature); Skylake far more stable (σ 0.28 W vs 1.29 W). Sandy Bridge values are modeled, Haswell measured (on-chip VRs). Recommended: ≥2 min warm-up, sample at least every 5 min for overflow, busy-poll for short paths, no per-core attribution (all cores report the same PP0), EC2 reports constant 25 °C and idle PKG swinging 35–100 W — [Khan et al., RAPL in Action, TOMPECS 2018](https://helda.helsinki.fi/server/api/core/bitstreams/bdc6c9a5-74d4-494b-ae83-860625a665ce/content).
- Software interfaces compared (Raffin & Trystram, 2024): perf-events read latency 0.50–0.74 µs vs MSR 0.54–4.45 µs vs powercap 1.97–6.12 µs; perf-events corrects overflow in-kernel; powercap's hierarchy places dram under package but tests show memory energy is not included in package; the energy unit is machine-dependent and must be read from registers; Intel's default unit does not apply to the dram domain on Xeon E5-2600; AMD Zen 1–4 expose only package and core domains. Measurement itself raises idle power: at 1000 Hz, +2.7–3.3 W on EPYC 7702 but +25.4 W (eBPF) to +48.6 W (powercap) on a Xeon E5-2680 v4, attributed to lost deep C-states; overhead negligible at ≤10 Hz — [arXiv:2401.15985 v2, Jul 2024](https://www.arxiv.org/pdf/2401.15985).
- Sampling-interval study (HotCarbon 2026, Xeon Gold 6326 + Ryzen 9 5950X, A100 + RTX 4090, NPB EP/CG/LU, 588 runs, 0.5 ms–1 s): RAPL at 0.5 ms has ~50 % stale reads and a 6.1 % energy shift; stale 4.6 % at 1 ms, 3.7 % at 10 ms; runtime overhead 2.4 % (0.5 ms), 0.9 % (1 ms), 0.4 % (10 ms); at ≥10 ms mean absolute deviation from baseline 0.57 %; recommendation: do not poll RAPL below 10 ms for aggregate energy — [Dauner et al., HotCarbon 2026 paper 46](https://hotcarbon.org/assets/2026/paper-46.pdf).
- Pereira's original tool bugs (relevant because RCE's ladder subsample uses the same counter family): reserved upper bits of the energy MSR included, no overflow handling (~60 s at high power), subtraction after float conversion, negative energies in the dataset — [van Kempen et al., arXiv:2410.05460 v4](https://arxiv.org/html/2410.05460v4).

AMD RAPL
- Zen 2 (EPYC 7702): "modeled, not measured"; no DRAM domain and package does not cover DRAM energy, so package RAPL under-reads vs the AC meter; 1 ms update; operand-data blindness: 256-bit `vxorps` with different operand weights changed full-system AC power by 21 W (7.6 %) with non-overlapping distributions, while RAPL averages moved 0.08 % and did not reproduce the ordering; 64-bit `shr` AC 0.9 % vs RAPL core 0.015 %. Idle: all threads in C2 → 99.1 W; one thread in C1 → 180.3 W; each further C1 core +0.09 W; package C-states only when every thread of every package is in the deepest state; do not offline hardware threads — [Schöne et al., arXiv:2108.00808](https://arxiv.org/pdf/2108.00808).

NVIDIA NVML / nvidia-smi
- A100 and H100: a 25 ms averaging window reported every 100 ms, so ~75 % of activity is unsampled; Volta/Pascal 10 ms window per 20 ms (~50 % missed); Turing 100/100 ms; GH200 "instant" reading covers ~10 % and includes CPU and DRAM. Error is proportional (~±5 % of reading, not NVIDIA's flat ±5 W). Naive single runs were off by up to ~70 % (mean ~39 %) against an external meter; following the paper's protocol (≥32 iterations or ≥5 s, eight evenly spaced phase-shifting delays, four randomized trials, discard 100–250 ms rise time) reduced mean error to ~5 % with a residual ≈ −5 % attributed to shunt tolerance — [Yang, Adámek, Armour, arXiv:2312.02741 v3, Dec 2024](https://arxiv.org/html/2312.02741v3).
- NVML cumulative energy counter stale-read fraction: 93.4 % at 0.5 ms, 86.3 % at 10 ms, 79.9 % at 20 ms, 1.0 % at 100 ms, 0 % at ≥500 ms. RTX 4090's integrated-from-counter power under-reports NVML power by 95.4 % at 0.5 ms, 75.6 % at 10 ms, 13.3 % at 100 ms, within 1.6 % only at 1 s; A100 matches within ±0.2 % at all intervals. Recommendation: validate cumulative counters per device; prefer integrating power readings — [Dauner et al., HotCarbon 2026](https://hotcarbon.org/assets/2026/paper-46.pdf).
- ML.ENERGY measures GPU only, via Zeus/NVML, in a steady-state window; no external-meter validation, no error bars ("not able to run the benchmark multiple times"); TDP-based estimates overestimate by up to 4.1× — [ML.ENERGY Benchmark, arXiv:2505.06371 v2](https://arxiv.org/html/2505.06371v2).

Embedded / SoC sensors
- Jetson AGX Orin, Xavier NX, TX2, Nano: onboard INA3221 sysfs readings underestimate external power by up to 50 %, with a near-constant gap per device; a linear calibration (e.g. Orin 1.02x + 3115 mW, Nano 1.11x + 233 mW) leaves ±3 % mean absolute error (Nano ±0.8 %); reference was a PicoScope 2204A at 1 ms, both streams smoothed with a 100 ms moving average — [Shalavi et al., arXiv:2306.13107](https://arxiv.org/pdf/2306.13107).
- Kria KV260 INA260 on VCC_SOM: see grounding; 1.25 mA step, 5 mA offset, 0.15 % gain — [Metered Commit Gates](https://research.openie.dev/papers/gates/).
- Apple powermetrics: a careful M4 study (0.1 s samples, 50 samples per test) reports ~1300 mW per P-core thread vs 110 mW per E-core thread on FP, ~3000 vs 280 mW on NEON, and E-core energy per task at 47 % (FP) / 38 % (NEON) of P-core, but makes no statement of calibration against an external meter — [Eclectic Light, 25 Nov 2024](https://eclecticlight.co/2024/11/25/inside-m4-chips-cpu-power-energy-and-mystery/). The agency paper notes Apple's own documentation warns the values may be inaccurate — [Thermodynamic Bounds](https://research.openie.dev/papers/agency/). I found no peer-reviewed validation of powermetrics against a wall meter.

Wall-meter methodology standards
- SPECpower_ssj2008: SPEC-accepted analyzer driven by PTDaemon over serial/USB/GPIB; load levels 100 %…10 % plus "active idle" (0 %), each 240 s by default excluding ramps; temperature sensor required, ambient ≥20 °C; analyzer accuracy class is in the Run Rules (not the design overview) — [SPECpower design overview](https://www.spec.org/power/docs/SPECpower_ssj2008-Design_Overview.pdf).
- MLPerf Power: SPEC-approved analyzers (e.g. Yokogawa WT310) for edge, PTD API for datacenter, waveform capture with Arduino-isolated timing for tiny, IPMI/Redfish or PDU for training; measurement ≥60 s (short workloads looped); only the execution phase counts; ranges: 5.64 mW tiny systems to 500 kW training submissions; reported energies 8.7 mJ/sample (datacenter ResNet), 20 mJ/inference (tiny autoencoder), 111.4 J/sample (Llama2-70B); no idle protocol; TDP/PSU ratings called poor proxies — [MLPerf Power, arXiv:2410.12032](https://arxiv.org/pdf/2410.12032).
- Green Software Foundation SCI = (E × I + M) per R, R a functional unit (per user, transaction, API call); ISO/IEC 21031:2024 (April 2024); the standard defines E but does not prescribe measured vs estimated — [GSF SCI](https://greensoftware.foundation/standards/sci/).

### Inferences
- The P4 provenance object already captures what every study above says is missing from ad-hoc readings; the two fields it lacks are a per-device validation reference (which external meter, what residual) and the sampling interval's stale-read fraction. Both are cheap to add.
- `reported_j` from AMD RAPL and from any NVML cumulative counter on a consumer card should carry a weaker sub-label than Intel Haswell+ package+DRAM RAPL; the lattice `est < reported < measured` is too coarse to distinguish a 1.8 %-MAPE counter from a 50 %-under-reading one.
- The gates paper's rung protocol (interleaved A/B/A, SE on N differences) is already closer to the state of the art than most published software-energy papers; its weak point is N = 4 and a module rail, exactly what its own "next protocol" fixes.

### Gaps
- No published validation of Apple powermetrics against an external meter.
- Could not retrieve the RCE §8.3 wall-meter protocol text to compare line by line.
- SPEC analyzer accuracy class (commonly stated as ≤1 % of reading) is in the Run Rules document, which I did not fetch; treat the exact figure as unverified.

## Q2. Per-instruction / per-op energy models and what is stable across microarchitectures

### Takeaway
Instruction-level models work (≤3–5 % error) on simple in-order cores where a handful of event counts explain energy, and degrade (10–28 %) once IR-to-ISA expansion, predication and operand data enter; on big out-of-order cores the published evidence says energy ≈ constant active power × time, so op-type weights matter far less than time. The only numbers stable across generations are ratios and orderings: DRAM access ≫ cache ≫ ALU (about 10²–10⁴×), and off-chip DRAM energy did not scale from 45 nm to 7 nm (1300 pJ both), while FP32 logic fell 3.7 → 1.31 pJ.

### Cited Findings
- Tiwari et al. 1994: energy = Σ base_i·N_i + Σ overhead_{i,j}·N + Σ stall/miss costs; measured with a digital ammeter on instruction loops. 486DX2: nop 276 mA, `mov dx,[bx]` 428 mA, `mov [bx],dx` 522 mA, `add dx,bx` 314 mA, `jmp` 373 mA (3 cycles). Inter-instruction overhead 0–30 mA against 300–400 mA program current on 486/SPARClite (hidden by the common cost), but 0–26 mA against 20–60 mA on the Fujitsu DSP (significant). Operand dependence <5 % on 486/SPARClite, large on the DSP (LDI 15.8–22.9 mA). Accuracy within 3 % on three processors — [Tiwari lecture notes, Berkeley EE290](https://people.eecs.berkeley.edu/~newton/Classes/EE290sp99/lectures/ee290aSp9912_2/ucb-sw-lecture-99.PDF).
- Horowitz ISSCC 2014 (45 nm, 0.9 V): ~70 pJ total overhead per instruction, ~20 pJ first-level cache fetch, ~10 pJ for an internal cache access or functional op, I-cache ~25 pJ and register file ~6 pJ (partly legible), FP arithmetic ~1/10 of a simple instruction, DRAM access 1–2 nJ, DRAM I/O >20 pJ/bit today and ~10 pJ/bit (~0.6 nJ per 8 B) projected; "reaching ~1 pJ per operation requires short integer data, tens of operations per local memory fetch, and roughly a thousand operations per DRAM fetch"; LLC leakage ~100 mW/MB — [Horowitz 2014](https://pages.cs.wisc.edu/~markhill/restricted/isscc2014_horowitz_power_scaling.pdf). The itemized figure (8-bit add 0.03 pJ … 32-bit FP mult 3.7 pJ, 8 KB SRAM 10 pJ … DRAM 1.3–2.6 nJ) is garbled in both PDF extractions; a 2026 secondary source quotes the same figure as FP ops 0.4–3.7 pJ, cache 10–100 pJ, off-chip 64-bit access 1300–2600 pJ, and from Jouppi et al. (TPUv4i) Int32 logic 0.1 pJ (45 nm) → 0.03 pJ (7 nm), FP32 3.7 → 1.31 pJ, DDR3/4 1300 pJ unchanged, GDDR6 350–480 pJ, HBM 250–450 pJ — [Lee & Bruck, arXiv:2603.26053, Mar 2026](https://arxiv.org/pdf/2603.26053).
- Cortex-M0 (STM32F0, MAGEEC measurement rig, 230 benchmarks of which 76 BEEBS, 10 hardware configs): a six-counter linear model (instructions, multiplies, taken branches, RAM reads, RAM writes, flash reads) reaches R² ≈ 0.99 and MAPE 2.80–4.33 %; coefficients at 20 MHz/prefetch off/0 wait states: 0.964 nJ per non-multiply instruction, 1.652 nJ per multiply, 2.092 nJ per taken branch, RAM read 1.1–1.5 nJ, RAM write 0.4–1.1 nJ, flash read 0.63 nJ (WS0) vs 1.18 nJ (WS1). No operand-data term; model tied to that family — [Lee et al., arXiv:2104.01055](https://arxiv.org/pdf/2104.01055). BEEBS is the 88-benchmark open embedded energy suite — [BEEBS, arXiv:1308.5174](https://arxiv.org/pdf/1308.5174).
- Grech et al. (LLVM IR static energy analysis): ISA model mapped up to IR via debug info on XMOS XS1-L gives 3.4 % mean error (range −3.4 to +10.1 %); a direct four-group IR model on Cortex-M3 gives 9.9 % mean (−3.3 to +28.0 %, base64 worst from predication). Error sources: IR→ISA expansion mismatch, random-operand assumption (logic ops and `char` use less of the datapath), ignored scheduling/fetch stalls, data-dependent branches producing max() terms. Conclusion: mapping from a measured ISA model beats a direct IR model — [arXiv:1405.4565](https://arxiv.org/pdf/1405.4565).
- Big cores: with one core fixed and turbo off on Xeon Gold 6430, power was 189.8 ± 0.5 W "across all implementations and benchmarks", so energy ∝ time; DRAM energy 2–8 % of CPU energy; LLC misses vs DRAM power R² = 0.93; power ≈ 31·log₂(cores) + 246 W (R² 0.72) — [van Kempen et al. 2025](https://arxiv.org/html/2410.05460v4).
- Operand-data effects exist and are invisible to RAPL: 7.6 % of full-system power from operand weights on 256-bit XOR (Zen 2) — [Schöne et al.](https://arxiv.org/pdf/2108.00808).

### Inferences
- Two regimes, and `cost_J` needs both: (a) in-order MCU / FPGA fabric, where Σ count_op × E_op with 5–10 calibrated coefficients is accurate to ~5 %; (b) OoO CPU / GPU, where the right model is E = P_active(target, cores, freq) × t(term, target) + E_mem(LLC misses) + P_idle × t, i.e. a time model with a memory term. The C.6 op weights are a plausible time proxy for (b) only if calibrated per target, and HC-12's `time = overhead + work/throughput` is already that model.
- What transfers across targets: the ordering ALU < cache < DRAM and the DRAM-does-not-scale fact. What does not transfer: any absolute pJ number, the FP/int ratio (1/10 at 45 nm per Horowitz, but 0.03 vs 1.31 pJ at 7 nm per Jouppi), and the branch/multiply premiums.
- For e-graph extraction, the Cortex-M0 result is the strongest evidence that a linear, additive, target-indexed coefficient vector over a small op alphabet is sufficient on simple targets; the van Kempen result says that on big cores the same linear form is adequate as long as the coefficients are calibrated to time.

### Gaps
- Horowitz's itemized 45 nm table could not be extracted verbatim from any fetched source; the report should cite it from the ISSCC digest figure directly.
- No published per-op energy table for RISC-V or for modern Arm application cores (Cortex-A7x/Neoverse) was found in this pass; MCU models dominate the literature.
- No study quantifying how much the C.6-style weights (call 4, float div 8, etc.) would mis-rank terms relative to measured joules.

## Q3. Energy-aware compilation and languages

### Takeaway
The language-energy ranking that drove "use Rust for sustainability" does not survive replication: at fixed core count energy is proportional to execution time, and the apparent language gaps were implementation, library, parallelism, warm-up and measurement-bug artefacts. Static IR-level energy analysis is viable at 3–10 % on small cores. WebAssembly interpreters on microcontrollers cost 11–52× native energy; on servers Wasm's cost is a time cost. Compile-time energy optimization that is not simply time optimization has published evidence only on microcontrollers (and there, memory and branch counts are the lever).

### Cited Findings
- Pereira et al. (2017/2021) Table I normalized to C (time / energy): Rust 1.04/1.03, C++ 1.56/1.34, Java 1.89/1.98, Go 2.83/3.23, JavaScript 6.52/4.45, TypeScript 46.20/21.50, Python 71.90/75.88, Lua 82.91/45.98; measured with Intel RAPL — summarized in [van Kempen et al.](https://arxiv.org/html/2410.05460v4); original ranking paper [Pereira et al. SCP 2021](https://web.fe.up.pt/~jacome/downloads/SCP21.pdf).
- Replication/critique (van Kempen, Kwon, Nguyen, Berger; two Xeon Gold 6430, RAPL package+DRAM at 1 Hz with a corrected tool, 118 CLBG programs + SPEC CPU 2017 + DaCapo): no significant effect of language on energy beyond time; C++ regex-redux 8.9× slower than C only because of Boost vs PCRE; TypeScript mandelbrot 21× slower because sequential vs JavaScript on ~28 cores; NumPy 84× faster and 44× less energy than naive C++ matmul; first Java iteration up to 2.7× slower than the 15-iteration mean; Go GC off gives 1.15× mean, 2.8× on binary-trees; doubling cores is energy-positive if throughput rises ≥13 % — [arXiv:2410.05460 v4](https://arxiv.org/html/2410.05460v4).
- Static energy analysis on LLVM IR (XMOS 3.4 %, Cortex-M3 9.9 %) — [Grech et al.](https://arxiv.org/pdf/1405.4565); EnergyAnalyzer applies WCET-style static analysis to energy on embedded targets — [arXiv:2305.14968](https://arxiv.org/pdf/2305.14968) (not fetched in full).
- WebAssembly on MCUs (Pico, ESP32-C6, nRF5340; WAMR and wasm3 interpreters; Nordic PPK2 meter; bubble sort of 100 ints): native ~0.06–0.1 mJ vs wasm3 1.12–3.11 mJ and WAMR 2.82–2.96 mJ, i.e. 11–52× energy and 11–48× time; WAMR needs 279–480 KB RAM — [Has et al., arXiv:2512.00035, Nov 2025](https://arxiv.org/html/2512.00035).
- Deterministic metering in Wasm: wasmtime recommends "deterministic fuel-based interruption" over "non-deterministic epoch-based interruption"; the page makes no claim that fuel measures time or energy — [wasmtime docs](https://docs.wasmtime.dev/examples-deterministic-wasm-execution.html).

### Inferences
- For RCE's five emitted targets (Rust, Python, JavaScript, …), the cross-language `est_j` difference should be modelled as a per-target throughput coefficient on the same op count, not as a per-language energy constant; the replication shows that is exactly what the data supports on CPUs.
- The language-level lever RCE actually controls, choosing the term in the e-class, is the right one: the replication's biggest wins (library choice, algorithm, parallelism) are term choices, not language choices.
- Wasm as an RCE target would carry a fabric-specific overhead coefficient of order 10–50× on interpreters and ~1× on AOT; the fabric record should state interpreter vs AOT because the energy coefficient differs by that factor.

### Gaps
- No 2023–2025 server-class Wasm energy study with RAPL error bars was fetched; the IoT paper is the only one with a hardware meter.
- EnerJ / approximate computing and "green compiler" LLVM energy passes: not researched in this pass beyond Grech; I found no LLVM upstream energy cost model.
- GPU/accelerator per-op costs: only TENSAT's measured per-operator runtime (Q5) and the TPUv4i pJ figures (Q2); no per-kernel joule table.

## Q4. Thermodynamic floors and reversible computing

### Takeaway
Landauer's bound is 2.87×10⁻²¹ J per erased bit at 300 K and has been experimentally confirmed; CMOS sits roughly 8–11 orders of magnitude above it per op, and the first reversible+adiabatic test chip (Vaire Ice River, Aug 2025) reduced energy by ~30 % on one computation, with the 4000× roadmap figure placed 10–15 years out. For a software cost model the floor is irrelevant to the numbers and relevant only as a labeled lower bound that must never be confused with an estimate or a measurement.

### Cited Findings
- Landauer: k_B T ln 2 ≈ 2.87×10⁻²¹ J at 300 K (~3.5×10²⁰ bits/J); Margolus–Levitin 2⟨E⟩/(πħ) ≈ 6.04×10³³ transitions/s per joule; TUR example: 1 % precision costs ≥20,000 k_B T — [Thermodynamic Bounds](https://research.openie.dev/papers/agency/). Experimental confirmation of the bound with a one-bit memory — [Bérut et al., Nature 483, 2012](https://ideas.repec.org/a/nat/nature/v483y2012i7388d10.1038_nature10872.html) (abstract only).
- Gap to CMOS: Horowitz figures are "about 8 to 11 orders of magnitude above that floor" — [Metered Commit Gates](https://research.openie.dev/papers/gates/); IEEE Spectrum's own figure is "more than a thousand times" per erased bit, with Frank saying conventional logic efficiency plateaus "later this decade" — [IEEE Spectrum, 2 Jan 2025](https://spectrum.ieee.org/reversible-computing). (The two figures measure different things: the Spectrum number is per bit-erasure at the device level, the gates figure is per 32-bit op; both are consistent with ~10⁹ J-per-op ratio at op level.)
- Vaire: prototype reversible adder in an LC resonator expected Q1 2025; tape-out announced 22 May 2025 "capable of recovering 50 % of the energy used in the resonator circuit" (stated capability); 4000× is a roadmap target "10 or 15 years out"; Frank left Sandia for Vaire July 2024 — [IEEE Spectrum](https://spectrum.ieee.org/reversible-computing). Ice River test chip, tested Aug 2025, drew ~30 % less energy than a conventional chip on the same computation; first chip to combine reversible logic with an on-chip adiabatic supply; "proof of concept"; no workload, trial count or independent verification reported — [Science News, 23 Sep 2025](https://www.sciencenews.org/?p=3160033).
- Frank (ACM Ubiquity): adiabatic designs can go "well below CV²"; a reversible FPU reportedly achieved an order of magnitude improvement; leakage limits real-world efficiency; no quantified speed/energy trade-off given — [Ubiquity](https://ubiquity.acm.org/article.cfm?id=3140589).

### Inferences
- With ~10⁹ between CMOS op energy and the floor, no extraction decision in RCE will ever be influenced by the floor; the only use is the one the gates paper already makes: a receipt may carry a Landauer figure as a labeled bound, never as `est_j`.
- Reversible hardware, if it arrives, changes the coefficient vector of a target, not the structure of `cost_J`; the adiabatic speed/energy trade-off would add a frequency dimension to the fabric record, which HC-12's `overhead + work/throughput` model does not have today.

### Gaps
- No peer-reviewed per-op measurement from Vaire; all figures are press reports of company statements.
- Frank's 4000× Sandia projection was not traced to its primary paper.

## Q5. Cost models in e-graph extraction

### Takeaway
Every production e-graph extractor assumes a cost that is computed per e-node from its children (egg's `CostFunction`), and the exact methods (ILP, ASP, treewidth) assume additive integer or linear costs with DAG sharing; the one extractor supporting non-additive (learned, differentiable) costs, SmoothE, is 8–37× faster than ILP and within 0–5 % of a 10-hour CPLEX oracle. Per-target cost is handled in practice by measuring per-operator costs on the target and keeping the sum additive (TENSAT/TASO), which is exactly the shape `cost_J(term, target) = Σ count_op × E_op(target)` has.

### Cited Findings
- egg `CostFunction`: `cost(&mut self, enode, costs)` returns one e-node's cost from a closure giving child e-class costs; docs say cost "should be monotonic" (exceed children's costs); `Cost` only needs `PartialOrd` (floats allowed, NaN panics); sums can overflow because an e-class appears many times, so `saturating_add` is advised; `AstSize`/`AstDepth` built in — [docs.rs egg CostFunction](https://docs.rs/egg/latest/egg/trait.CostFunction.html).
- TENSAT: TASO's cost model, each operator's cost is its measured runtime on the target (Tesla T4, cuDNN) for its specific shapes, costs independent and additive (fusion counted as one operator) "which suits GPUs that run one operator at a time"; greedy extraction ignores sharing (no gain on BERT, worse on NasNet-A, 22.5 vs 17.8 ms); ILP via SCIP with topological-order cycle constraints was the bottleneck (>3600 s) so cycles are filtered during exploration and the constraints dropped (BERT k=2: 510 s; NasRNN k=1: 1116 s → 0.32 s); speedups over TASO up to 16 %; noted cost-model/runtime mismatch on SqueezeNet — [Yang et al., arXiv:2101.01332](https://www.arxiv.org/pdf/2101.01332).
- SmoothE (ASPLOS 2025): relaxes extraction to "any differentiable cost function", including a 4-layer MLP non-linear correction; on extraction-gym datasets, quality gap to a 10 h CPLEX oracle (worst/avg): diospyros 0.1/0.1 %, $exc 0.7/0.2 %, impress 0.0/0.0 %, rover 4.4/0.2 %, tensat 17.0/4.6 % (egg greedy: 46.4/12.1 % on tensat, 280/53 % on impress); runtime 4.6–24 s on an A100 vs 0.1–1.3 s greedy and 15 min ILP caps; 8–37× faster than ILP; non-linear MLP costs finish every e-graph under a minute; target-dependent costs not addressed — [SmoothE](https://www.csl.cornell.edu/~zhiruz/pdfs/smoothe-asplos2025.pdf).
- ASP extraction (Yang & Sergey, 2026): exact DAG-cost extraction via Clingo with an acyclicity propagator; competitive with an optimized ILP on babble/herbie/rover; limitation: weak constraints need integer costs, so non-integer e-graphs are out; no non-additive costs; naive ILP "clearly not competitive", optimized ILP fast mainly from zero-cost simplification hooks — [arXiv:2606.10644](https://arxiv.org/pdf/2606.10644).
- Treewidth-based optimal extraction and sparse-e-graph optimal extraction exist (OOPSLA 2024, arXiv:2408.17042) — surfaced in search, not fetched: [E-Graphs as Circuits](https://arxiv.org/pdf/2408.17042); [Fast and Optimal Extraction for Sparse E-Graphs](https://cse.hkust.edu.hk/~parreaux/publication/oopsla24a/).

### Inferences
- A per-target cost for RCE is a coefficient vector `E[target]` over the op alphabet (plus a per-target `P_idle·t` and memory term); extraction minimizes `⟨count(term), E[target]⟩`, which is linear, additive and integer-scalable (price in pJ or in 10⁻¹² units so Clingo/ILP integer constraints hold). Target choice is a swap of the vector, not a change of extractor.
- Proposition 3 is a statement about tree cost; sharing (DAG cost) is where egg's greedy extractor over-counts, and the tensat/impress rows show greedy can be 12–53 % off on average. If `est_j` is to be the extraction objective, the extractor should be DAG-aware (ILP/ASP with cycle filtering as TENSAT does) or SmoothE-style.
- Non-additive energy effects that are real on CPUs (cache state, frequency, thermal) cannot be expressed in egg's monotonic child-cost model; they belong in the calibration of coefficients (`host.Calibrated`), not in the extraction objective.

### Gaps
- No paper found that uses measured joules (rather than time or resource count) as an extraction cost.
- The egg docs page does not describe `LpExtractor` or the greedy fixpoint; those details were not verified here.

## Q6. Budget/metering languages: gas, fuel, step counts as proxies for joules

### Takeaway
Deterministic unit metering (EVM gas, Wasm fuel, RCE budget units) is a replay-safe proxy, but the only published correlation between metered units and a physical resource is weak for CPU (EVM gas vs CPU time Pearson ≈ 0.51) and dominated by storage; nothing in the literature correlates an op-count table like C.6 with joules. The C.6 rationale "energy scales with the operations performed" is therefore an assumption that the ladder's `reported_j` subsample can and should test.

### Cited Findings
- Broken Metre (Perez & Livshits; aleth client replaying mainnet, ~100k blocks before/after EIP-150): gas vs storage Pearson 0.821 → 0.907, vs memory 0.545 → 0.766, vs CPU 0.528 → 0.507 (adding CPU to the multivariate fit lowers correlation); MUL costs 65 % more gas than ADD but 96.96 vs 82.20 ns; DIV same gas as MUL but ~5× slower (476 ns; 10.5 vs 51.6 gas/µs); EXP twice DIV's gas and ~40 % faster; BLOCKHASH at 20 gas has the highest variance (disk); page-cache effects 24–33× on large contracts; a GA found programs at ~300 k gas/s vs ~20 M gas/s average (>60×) — [arXiv:1909.07220 v2](https://arxiv.org/pdf/1909.07220v2).
- wasmtime: fuel is the deterministic interruption mechanism; epochs are non-deterministic — [wasmtime docs](https://docs.wasmtime.dev/examples-deterministic-wasm-execution.html).
- RCE C.6 defines units as target-blind op accounting, explicitly "not a measurement of time or energy", with the budget trap placed deterministically on the same operation across the reference evaluator and the Rust/Python/JS runtimes — [C.6](file:///tmp/claude-0/-home-claude/a51bc2e6-10c5-5671-9c6b-8af67db8621d/scratchpad/repos/rce/spec/book/14-draft06-concurrency.md).
- On big cores, energy tracks time at fixed core count (189.8 ± 0.5 W) — [van Kempen et al.](https://arxiv.org/html/2410.05460v4); on Cortex-M0, six event counts explain energy at R² 0.99 — [arXiv:2104.01055](https://arxiv.org/pdf/2104.01055).

### Inferences
- The C.6 ratios (float div 8 vs float add 2 = 4×; call 4; spawn 32) are latency-flavoured and roughly consistent with the EVM microbenchmark ordering (DIV ≈ 5× MUL in time), but they are not energy on any target, and they cannot be: energy per op depends on the target's P_active and throughput, which C.6 by design excludes.
- The right split is the one the spec already makes: budget units stay deterministic, in D, target-blind; `est_j` is derived from the same counts by a per-target price vector that lives in D as `host.Calibrated`. The missing piece is the empirical check: regress `reported_j` on op counts per target over the ladder subsample and report R²; if R² on a CPU target is low, switch that target's price model to time-based (Q2 regime b).

### Gaps
- No published R² between a software-level op-count table and measured joules on any target other than the Cortex-M0 event-counter study; this is the measurement RCE would have to produce itself.

## Q7. Synthesis for RCE: how to build cost_J(term, target) that is per-target, measurable, and usable in extraction — adopt/refuse

### Takeaway
Keep C.6 units as the deterministic, target-blind budget; make `est_j = ⟨count(term), E[target]⟩ + P_idle[target]·t_est` with `E[target]` a calibrated coefficient vector logged in D; calibrate it by A/B/A metered runs following the gates paper's "next protocol"; promote figures through the label lattice only by evidence; extract under the linear per-target objective with a DAG-aware extractor.

### Cited Findings
(All items below are recommendations grounded in findings already cited in Q1–Q6; no new sources.)

Adopt
1. Two-regime price model per target, selected by the fabric record. Regime A (in-order MCU, FPGA lanes, NPU): `est_j = Σ_op count_op · E_op[target]`, with an alphabet of ~6–10 op classes (the Cortex-M0 study's six counters reach 3–4 % MAPE — [arXiv:2104.01055](https://arxiv.org/pdf/2104.01055)). Regime B (OoO CPU, GPU): `est_j = P_active[target](cores, freq) · t_est + E_llc_miss[target] · misses + P_idle[target] · t_est`, where `t_est = overhead + work/throughput` is already HC-12's placement model ([E.6](file:///tmp/claude-0/-home-claude/a51bc2e6-10c5-5671-9c6b-8af67db8621d/scratchpad/repos/rce/spec/book/16-host-contract.md)); the evidence for a time-dominated model is 189.8 ± 0.5 W constant power and DRAM at 2–8 % ([van Kempen](https://arxiv.org/html/2410.05460v4)).
2. The coefficient vector is a `host.Calibrated` entry: {target id from `host.FabricCaps`, op alphabet version, coefficients, units (pJ), method, N, SE per coefficient, counter/meter provenance per P4, boundary per P5, date}. Extraction is then a function of D (T37) and replays. Price in integer pJ (or fJ) so ILP/ASP extractors with integer-weight constraints apply ([ASP extraction](https://arxiv.org/pdf/2606.10644)).
3. Calibration protocol = the gates paper's required next protocol, generalized: interleaved randomized A/B pairs (≥30), ≥10⁹ op evaluations per block or ≥60 s per block (MLPerf minimum; SPEC uses 240 s), 2-minute warm-up (Khan), die/package temperature logged, idle baseline before each block, report gross and net with SE, and the analytical estimate printed beside the reading. Coefficient = slope of the regression of block energy on block op counts; report R² and the stale-read fraction of the sampler.
4. Counter hygiene encoded in `reported_j_provenance`: Intel RAPL via perf-events at ≥10 ms interval, package+DRAM, Haswell+ only; AMD RAPL flagged `modeled` and `no_dram`; NVML by integrating power at ≥100 ms with the Yang et al. run-length/phase-shift protocol, cumulative counters only if validated per device; Jetson INA3221 only with a per-board linear calibration; powermetrics flagged `unvalidated`. Add two fields to P4: `validation_ref` (external meter, residual %) and `stale_fraction`.
5. A sub-label or confidence field inside `reported_j` (e.g. `reported_j_class ∈ {validated_lt_3pct, modeled, unvalidated}`) because the lattice `est < reported < measured` cannot separate a 1.8 % MAPE counter from a 50 % under-reading one.
6. `measured_j` definition: a named rail or wall AC with a SPEC/PTDaemon-class analyzer or a shunt whose offset cancels in A−B (INA260: 5 mA offset, 0.15 % gain), window ≥60 s, both gross and idle-subtracted figures stored, SE from ≥30 interleaved pairs; minimum detectable difference reported as 2ε per the gates paper's ordering rule.
7. Extraction objective stays linear and additive per target; use a DAG-aware extractor (ILP with TENSAT-style cycle pre-filtering, ASP, or SmoothE) rather than egg's greedy tree extractor when terms share subterms, because greedy is 12–53 % off on average on tensat/impress ([SmoothE](https://www.csl.cornell.edu/~zhiruz/pdfs/smoothe-asplos2025.pdf)). Prop 3's claim "least-joule term the extractor finds" is then honest about the extractor's optimality class.
8. Falsification hook: for each target with a calibrated vector, the ladder subsample regresses `reported_j` on op counts; publish R² and the sign of each coefficient. A target whose R² falls below a threshold (say 0.8, the Cortex-M0 study's 0.99 being the ceiling) is re-priced under regime B. This is the natural content of an RCE-F3-style falsifier.

Refuse
9. Do not turn C.6 units into joules or add target-specific numbers to the C.6 table; its value is the deterministic trap position across runtimes (C.6.2–C.6.4), which any target dependence would break.
10. Do not use a language-level constant per target (the Pereira ratios); the replication shows those ratios are implementation and parallelism artefacts ([van Kempen](https://arxiv.org/html/2410.05460v4)).
11. Do not put non-additive effects (cache state, DVFS, thermal, operand data) into the extraction cost function; egg's model is monotonic child-cost, and the published non-additive extractor (SmoothE) still trails ILP on adversarial graphs. Keep those effects in calibration.
12. Do not read any counter as `measured_j`; do not sum across labels (gates paper: tiers "never summed"); do not subtract idle silently (store gross and net).
13. Do not let the Landauer figure or any thermodynamic bound appear as `est_j`; it is a labeled bound, ~10⁹ below any CMOS op cost.
14. Do not rely on NVML cumulative energy counters on consumer GPUs or on powermetrics without a per-device validation entry.

### Inferences
- The structural change needed is small: the spec already has `host.Calibrated`, `FabricCaps.counters`, P4–P6 provenance, and a linear op-count pricing. What is missing is (i) the per-target coefficient vector as a first-class D entry with SE, (ii) the regime-B time model for CPUs/GPUs, (iii) the calibration protocol as a normative appendix, and (iv) the R² falsifier.
- The cheapest first measurement is on the KV260: rerun rung 3 with VCCINT telemetry and N ≥ 30, then regress against op counts of three RCE kernels; that yields the first non-placeholder `E_op` and converts `E_LUT_READ = 1e-12` from a stand-in to a calibrated coefficient with an SE.

### Gaps / open problems
- Attribution: RAPL has no per-core or per-thread attribution (all cores report the same PP0), so per-handler `reported_j` in a multi-tenant run is a model, not a reading; the spec needs a rule for how shared package energy is amortized across concurrent handlers (P6's `amortization` field is the hook).
- Frequency/DVFS: HC-14 forbids performance knobs, but the host OS governor still moves frequency; the time model's `P_active` is frequency-dependent, so the calibration entry must record the governor state or pin it.
- Operand-data energy (7.6 % on Zen 2) is invisible to counters and absent from every software model found; no fix short of a wall meter.
- No source gives a per-op joule table for the GPU fabrics RCE targets through wgpu; TENSAT measures runtime per operator, not joules.
- Could not read RCE §6.3 / §8.3 / §9; the report writer should reconcile item 8 with the actual RCE-F3 text.
