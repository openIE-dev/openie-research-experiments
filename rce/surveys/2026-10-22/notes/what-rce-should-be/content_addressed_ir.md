# Content-addressed code and lossless IRs: design input for the Form IR

Grounding (read before any search): RCE paper §3.6/§4.5/§6 at https://research.openie.dev/papers/rce/ ; local `spec/proposals/form-ir-2.md`, `spec/proposals/closing-the-loop.md`, `spec/book/07-form-evaluation.md` §6.1.1, `spec/checker/src/anf.rs`, `spec/checker/src/emit/mod.rs`.

Current RCE state as grounded (all from the local clone, commit on branch `rce/host`):
- Form IR format 1 is a bare JSON term tree; "A call is lowered by copying the callee's term into the caller ... a recursive function has no finite term at all. 77 of the 188 refused stdlib bricks are refused for size or depth alone." (`form-ir-2.md` §1). Full refusal breakdown: 188 = 77 size/depth, 50 mutable borrows, 38 error results, 7 `match`, 7 other calls, 5 slices/place assignments, 4 narrow ints/floats; 457 bricks, 269 lowered, 252 agree with the reference interpreter, 0 disagree, 17 no vectors (`closing-the-loop.md` §7).
- Format 2 proposal: `{"format": 2, "defs": {KEY: term}, "main": term}` with `ref(node, KEY)`, KEY = SHA-256 of canonical JSON of the body; well-formedness (a) key = digest(body), (b) every ref resolves; acyclicity falls out of (a) ("a cycle would need a fixed point of SHA-256"); recursion deferred to a bounded `fix`; e-graph treats `ref` as opaque leaf and inlines only bodies ≤ `INLINE_MAX` nodes (`form-ir-2.md` §1).
- Canonical JSON (§6.1.1, normative): UTF-8, no whitespace; ints exact decimal in [-2^63, 2^64-1]; floats finite binary64, shortest round-trip digits, `10.0` not `10`, `-0.0` preserved, fixed exponent thresholds 10^-4/10^16; text NOT Unicode-normalised; records sorted by code point; Set/Map embedded as sorted lists. Explicitly diverges from RFC 8785 in six documented rows; 77 golden vectors in `spec/data/canonical-json-vectors.json`.
- Log entries: `hash = SHA-256(canonical JSON of {event, prev_hash, seq, state_hash})`; `state_hash = SHA-256(canonical JSON of state)`.
- Paper §3.6: "the canonical serialization of the Form is injective"; lift/projection lens: π_L(λ_L(p)) ≡ p on behaviour, λ_L(π_L(F)) = F on shape hash ("the GetPut condition at the level of the whole program"); U3 (lift) "is a construction, not a theorem". §4.5: `rce form` = lower → normalize → egg saturation → extract with cost = est_j; "Every target is generated. None is authored."; i64 checked overflow "is an error and never wraps"; floats IEEE binary64.
- Emitters (`emit/mod.rs`): four targets (`Lang::{Rust, Python, Js, Scala}`), one shared ANF pass (`anf.rs`, order-preserving flattening of `&mut` write-back calls) then `base::G::new(&m, lang).program()`; per-target branching is pervasive: `grep -c "Lang::"` gives expr.rs 64, stmt.rs 107, base.rs 68, prog.rs 121; four hand-written runtimes rt.rs 2084 / rt.py 2107 / rt.js 2000 / rt.scala 1903 lines. The emitters walk the surface AST (`crate::ast::*`), not the Form IR.

## KQ1. Unison: hash-named definitions, no builds, codebase as content-addressed store — what worked, what did not

### Takeaway
Unison's core bet (identity = hash of a name-free syntax tree; names are mutable metadata outside the hash) delivered the promised no-build, no-conflict, cache-everything properties, but the operational pain was all in *edits*: propagating a changed hash through dependents without losing names, surfacing conflicts, and ordering edits. The 2023 `update` rewrite is the retrospective that matters.

### Cited Findings
- Identity: "Each Unison definition is identified by a hash of its syntax tree." Hash is 512-bit SHA3. Named arguments become positional references (`#arg1`), dependencies are replaced by their hashes; example `increment = (#arg1 -> #a8s6df921a8 #arg1 1)`. "names are just separately stored metadata that don't affect the function's hash." "We can change what address a name points to, but the contents of each address are forever unchanging." — [Unison docs, The Big Idea](https://www.unison-lang.org/docs/the-big-idea/) (undated page, current site)
- Claimed benefits: no builds ("parsed and typechecked once and cached"), cached deterministic tests ("no need to rerun a deterministic test if none of its dependencies have changed"), no dependency conflicts (two `Email` types coexist), instant non-breaking renames, typed durable storage of any value including functions, distributed execution with missing hashes fetched on demand, codebase "never in a broken state, even midway through a refactoring." Caveat stated: "there's a lot of engineering that goes into making this work nicely." — [Unison docs, The Big Idea](https://www.unison-lang.org/docs/the-big-idea/)
- Oct 16 2019 status post (Paul Chiusano): content addressing gives "no builds, easy renames, test caching, no dependency conflicts, typed durable storage" "almost for free"; open question raised: what it means "if you can't ever modify a definition, only introduce new ones"; gaps at the time: docs authoring, PR/code review workflow, publishing libraries, "a better type-refactoring algorithm that avoids manual propagation of edits." — [Unison blog, 2019-10-16](https://unison-lang.org/blog/heres-whats-been-happening-with-unison)
- Oct 20 2023 `update` redesign (Rebecca Mark): the old patch mechanism failed on exactly the content-addressing seams: "It's easy to accidentally replace your human readable names with mysterious hashes."; "There is no indication that conflicts are present unless you run `todo`."; "The suggested order of edits sometimes leads you in a circle."; no first-class dependency-upgrade workflow. New process: type-preserving edits "propagate automatically"; otherwise ucm creates an update branch and dumps affected definitions into `scratch.u` for the user to re-typecheck, then `merge`; `upgrade lib.base_2_0_0 lib.base_3_2_1` for libraries. Stated goals: semantically meaningless changes (whitespace, import order, moving definitions) must not conflict; renames must not break dependents; "A codebase that always typechecks, even partway through a complex refactoring." — [Unison blog, 2023-10-20](https://unison-lang.org/blog/new-update-process)
- Further 2024 ucm changes (project-based commands, ucm 0.5.25) exist but I did not fetch them: [project-based ucm commands, 2024-07-23](https://unison-lang.org/blog/project-based-ucm-commands), [ucm 0.5.25, 2024-07-23](https://unison-lang.org/blog/ucm0525).
- Third-party experience report (code-as-hashes, with worked examples): [SoftwareMill, "Trying out Unison part 1: code as hashes"](https://softwaremill.com/trying-out-unison-part-1-code-as-hashes/) (not fetched; listed in search results).

### Inferences
- The invariant that survived five years is "hash covers semantics, never names": variables positional, dependencies by hash, names in a separate table. RCE format 2 already does the first two (ref by digest, no namespace) but has no stated name table; it needs one if humans or `rce scan` ever need to print a `defs` entry.
- The failure mode to design against is not hashing but *re-hashing under edit*: changing one body changes its digest and therefore every transitive caller's digest. Unison needed a dependents index plus a typed propagation algorithm (2023) before this was usable. Format 2's acyclicity-by-hash makes the same cascade mandatory and gives no cycle for mutual recursion; Unison handles mutual recursion by hashing a cycle as one component with positional indices (this is how its public hashes `#abc.1`, `#abc.2` arise), but I could not fetch a primary page stating it this session — see Gaps.
- "Always typechecks mid-refactor" is the same property as RCE's "correctness is proven not reviewed": a `defs` table where every entry is independently checked (and the check result cached by key) is the mechanism.

### Gaps
- No fetched primary source on how Unison hashes mutually recursive components (cycle hashing with component indices) or on Unison's 2024–2025 codebase-format (SQLite v2) retrospective; the ucm 0.5.25 and project-commands posts were listed but not read.
- No quantitative retrospective (adoption, codebase sizes, propagation cost) was found.

## KQ2. Canonical binary encodings and the cost of JSON as hash input

### Takeaway
Every mature canonical encoding makes the same six decisions (shortest integer form, one float rule, NaN/−0 policy, sorted keys by encoded bytes, no indefinite/optional framing, forbid or fix every optional feature), and the two biggest ecosystems that *skipped* canonicalisation (Protobuf; JSON before RFC 8785) tell users outright not to hash the bytes. RCE §6.1.1 is already a correct, deliberately-non-RFC-8785 canonical JSON; the residual costs are size, parse speed, and Unicode normalisation policy, not correctness.

### Cited Findings
- RFC 8949 §4.2.1 core deterministic CBOR (Dec 2020, STD 94): shortest-form integer/length/tag arguments; floats "use the shortest form that preserves the value" (1.5 → binary16 `f93e00`); "Indefinite-length items MUST NOT appear"; map keys sorted by "bytewise lexicographic order of their deterministic encodings" (works because CBOR is self-delimiting so no key is a prefix of another). §4.2.2: a protocol must either require or forbid a tag, never allow both; must fix integer-vs-float encoding of integral values (three candidate rules; RFC suggests "always the smallest float"); should pick one NaN (`f97e00`); may forbid −0.0 and subnormals. §4.2.3: RFC 7049's length-first order is now "Old Canonical CBOR". Duplicate keys are left to each protocol (§5.6). — [RFC 8949 §4.2](https://www.rfc-editor.org/rfc/rfc8949#section-4.2)
- DAG-CBOR (IPLD, "Descriptive – Draft", undated): only tag 42 (CID) allowed; map keys must be strings; keys sorted length-first then bytewise (i.e. the *old* 7049 order, not 8949 core); shortest ints; no indefinite lengths; floats "must always use 64-bit double precision" (opposite of 8949 preferred serialisation); NaN/±Inf "must not appear"; −0.0 "should not appear" and is encoded as +0; one top-level object per block; decoders may relax by default with opt-in strict mode. — [IPLD DAG-CBOR spec](https://ipld.io/specs/codecs/dag-cbor/spec/)
- Dhall semantic integrity: hash is "a SHA-256 hash of the binary representation of an expression's normal form"; expressions "are fully interpreted before they are hashed or cached"; encoding assumes "fully resolved and αβ-normalized" (variables by index since α-normalised code has only `_`); record fields sorted before encoding; ints smallest form but "A decoder MUST accept an integer that is not encoded using the most compact representation"; Doubles use "the shortest floating point encoding that preserves its value" (half → single → double), NaN fixed to half `0x7e00`, ±Inf and ±0 fixed to half encodings so that "These values ensure identical semantic hashes on different platforms"; import integrity stored as multihash `\x12\x20` + 32 bytes. — [dhall-lang standard/binary.md](https://github.com/dhall-lang/dhall-lang/blob/master/standard/binary.md)
- Cap'n Proto canonicalisation: preorder, single segment, unpacked, trailing zero words truncated (so adding a field later does not change the canonical bytes of old messages because zero = default), struct lists must use element size C=7 (since 0.5), zero-size structs pointer offset −1; purpose "for hashing and signing"; pre-0.5 data "may not be canonicalizable". Floats stored as little-endian IEEE-754; page does not say whether NaN or −0 are normalised. — [capnproto.org encoding](https://capnproto.org/encoding.html)
- Protobuf: "The handling of unknown fields is a primary obstacle to canonical serialization" (bytes vs nested message share a wire type, so unknowns cannot be recursed); "we intentionally leave serialization order undefined"; "we recommend against generic fingerprinting on messages"; "hashes of serialized protos are fragile and not stable across time or space" even with deterministic serialisation on; recommended fix is a hand-written per-field fingerprint. — [protobuf.dev, Serialization is not canonical](https://protobuf.dev/programming-guides/serialization-not-canonical/)
- RCE §6.1.1 vs RFC 8785 (local spec, normative): six documented divergences — `10.0` vs `10` (int/float must decode differently), `-0.0` vs `0` (sign is observable state), `1e-6`/`1e21` vs `0.000001`/`1e+21`, exact integers to 2^64−1 vs ECMAScript doubles, `\u0008` vs `\b`, code-point vs UTF-16 member order; "an RFC 8785 library does not produce these bytes and must not be used to hash a Form value." Text "is not normalised: `é` (U+00E9) and `é` (U+0065 U+0301) give different bytes." — `spec/book/07-form-evaluation.md` §6.1.1 (local)
- Bencode (BitTorrent) and ASN.1 DER are the two oldest canonical encodings (DER: X.690 distinguished rules; Bencode: sorted raw-string dictionary keys). Not fetched this session; standard references are ITU-T X.690 and BEP 3.

### Inferences
- RCE's canonical JSON already satisfies the structural checklist the binary formats converge on (one float rule, −0 policy, sorted keys, no optional framing, int≠float). What it pays for JSON is (a) bytes: decimal floats and quoted keys are 2–5× CBOR size for term trees, which matters because `defs` bodies are hashed and transmitted per brick; (b) parse cost on every hash check (well-formedness rule (a) re-hashes every body on read); (c) no native bytes type, so text-as-UTF-8-bytes bricks (`closing-the-loop.md` §7, commit 13c3ebca1) are lists of ints.
- Unicode non-normalisation is the right call for state values (NFC would merge observable strings), but it is the wrong call for *identifiers in `defs` keys/node names* if those ever come from source text via `rce scan`: two editors can emit NFC vs NFD identifiers for the same program and get different shape hashes. Dhall sidesteps this by α-normalising names away before hashing; RCE should do the same for binders inside a term (hash positional/de-Bruijn, keep names in a side table), which also makes bodies that differ only in local variable names share one `defs` entry.
- Decoder strictness: DAG-CBOR and Dhall both accept non-compact input by default; RCE's format-2 rule (a) ("A program that fails (a) or (b) is refused, never evaluated") is the strict choice and is correct for a hash-verified store, but then *every* producer (JS runtime, Python emitter, Rust emitter) must ship the same 77-vector-tested serialiser; a second canonical encoder in another language is the most likely source of silent hash drift.

### Gaps
- Did not measure byte sizes or hash throughput of canonical JSON vs deterministic CBOR on actual Form IR terms; no published benchmark found for term-tree payloads specifically.
- Cap'n Proto's NaN/−0 behaviour under canonicalisation is undocumented on the page fetched.

## KQ3. Nix/Guix store paths and Dhall: content addressing of build graphs and of normalised expressions

### Takeaway
Nix is the cautionary tale for content addressing *outputs*: fifteen years to make it experimental because outputs embed their own address (self-reference) and builds are non-deterministic; Dhall is the success story for content addressing *normal forms*: hash after full resolution and αβ-normalisation, so the hash is semantic, not textual. RCE's `defs` keyed by canonical bytes of a *lowered, normalised* body is the Dhall model, and its acyclicity-by-digest is exactly the property Nix's modulo-hashing had to give up.

### Cited Findings
- Input-addressed Nix: "the name of a package is derived from all of its inputs"; any input change, even output-irrelevant, rebuilds all dependents (OpenSSL example). Content-addressed proposal: name "should be derived from the content of the compiled package", enabling early cutoff ("detecting when changes in a package ... yields the exact same output"), smaller stores, IPFS caches; blocked "for about 15 years"; RFC 62. — [Tweag, 2020-09-10](https://www.tweag.io/blog/2020-09-10-nix-cas/)
- Self-references: the hash "depends on the content of the directory", which contains the final path, so it is "quite impossible" to compute before the build; workaround "modulo self-references": replace self-paths by a same-length placeholder, hash, rewrite — "pedantically speaking" not true content addressing; fails when self-references are "hidden" (e.g. inside compressed files), so "content-addressability will not be the default in Nix, at first at least." Non-determinism "diamond problem": two builds of one derivation yield two hashes; pulling both into a dependent duplicates the library so "the C linker will fail because of the duplicated symbols"; chosen mitigation: one build per derivation is admitted, which is "not optimal" but keeps "correctness while staying conceptually and technically simple"; Dolstra's thesis rewriting approach deemed "quite complex to implement for a first version". — [Tweag, 2020-11-18](https://tweag.io/blog/2020-11-18-nix-cas-self-references)
- Later status trail (not fetched): [NixOS/nix issue #8113](https://github.com/NixOS/nix/issues/8113), [Nix roadmap: CA derivations → dynamic derivations](https://code.obsidian.systems/Ericson2314/nix-roadmap), [Discourse call for testers](https://discourse.nixos.org/t/content-addressed-nix-call-for-testers/12881?page=2).
- Dhall: hash = SHA-256 over CBOR of the αβ-normal form after import resolution; names erased by α-normalisation; platform-fixed float encodings so hashes agree across platforms; `sha256:` import pin. — [dhall-lang binary.md](https://github.com/dhall-lang/dhall-lang/blob/master/standard/binary.md)

### Inferences
- RCE's `defs` sit on the Dhall side: a body is a *term*, not a build artefact, and there is no self-reference problem because rule (a) forbids a body from containing its own digest. Keep it that way: never let a node attribute (`node`) or oracle key feed back into the body digest.
- Dhall's lesson that the hash must be over the *normal form* is the one RCE has only half-taken: `rce form` normalises and egg-extracts, but `defs` keys in the proposal are digests of the *lowered body as written*. Two bricks that are β-equivalent but not byte-equal get two entries. Options: (i) hash after a fixed, confluent normaliser (ANF + sorted commutative args + α-erasure) and call that the shape hash; (ii) keep raw-body keys for the store and a separate "semantic key" from the e-graph canonical representative for dedup. Dhall does (i); egg-style canonicalisation is (ii).
- Nix's "diamond" is the Form IR analogue of a non-deterministic emitter: if the Rust emitter emits a `defs` function under one name and the JS runtime under another, differential tests will pass but the trace log's oracle keys diverge. Emit function names *from the key* (as format 2 says for Rust) in every target.

### Gaps
- Guix (uses the same store model with its own derivation hashing; `guix hash`, grafts) not researched this session.
- Current (2025–2026) status of Nix CA derivations (`ca-derivations` experimental feature) not verified beyond the 2020 posts and the issue/roadmap links above.

## KQ4. Verified compilers and their IRs; what makes an IR lossless (lenses, BX)

### Takeaway
Verified compilers prove *forward* semantics preservation per pass over a chain of small IRs (CompCert ~10, CakeML 12 ILs); none of them is lossless backward, and none tries to be. Losslessness is a *lens* property (GetPut/PutGet), and the BX literature's main result is that total, lawful lenses exist only when the source carries no information the view drops — which is exactly why RCE's U3 is "a construction, not a theorem" and why `rce scan` labels output "a syntactic lift".

### Cited Findings
- RCE paper: Form serialisation "is injective"; round trip is "the GetPut condition at the level of the whole program"; cites Foster et al. [122] for get/put lenses and Hofmann, Pierce, Wagner [123] for symmetric lenses; U3 lift "is a construction, not a theorem"; `rce scan DIR --form` lifts Rust, Python, TypeScript, Go and "every lifted element is labeled as a syntactic lift"; "A lifted program carries the faults of its source". — [RCE paper §3.6, §4.5, §6](https://research.openie.dev/papers/rce/)
- Lenses: Foster, Greenwald, Moore, Pierce, Schmitt, "Combinators for bidirectional tree transformations: A linguistic approach to the view-update problem", ACM TOPLAS 29(3), May 2007 — defines well-behaved lenses by GetPut (`put (get s) s = s`) and PutGet (`get (put v s) = v`), and very-well-behaved by PutPut. — [ACM DL](https://dl.acm.org/doi/10.1145/1232420.1232424) (not fetched; standard reference)
- Symmetric lenses: Hofmann, Pierce, Wagner, "Symmetric lenses", POPL 2011 — both sides carry private information; a complement stores what each side drops. — [ACM DL](https://dl.acm.org/doi/10.1145/1926385.1926428) (not fetched)
- Cross-discipline survey: Czarnecki, Foster, Hu, Lämmel, Schürr, Terwilliger, "Bidirectional Transformations: A Cross-Discipline Perspective", ICMT 2009 (GRACE meeting report) — catalogues BX across databases (view update), PL (lenses), MDE (TGGs/QVT-R); identifies totality vs. lawfulness trade-offs and the need for complements. — [Springer](https://link.springer.com/chapter/10.1007/978-3-642-02408-5_19) (not fetched)
- CompCert: Leroy, "Formal verification of a realistic compiler", CACM 52(7), 2009 — Coq-verified chain Clight → C#minor → Cminor → CminorSel → RTL → LTL → Linear → Mach → Asm; each pass proves forward simulation; no decompilation direction. — [CACM](https://dl.acm.org/doi/10.1145/1538788.1538814) (not fetched)
- CakeML: Tan, Myreen, Kumar, Fox, Owens, Norrish, "A new verified compiler backend for CakeML", ICFP 2016 — 12 intermediate languages, proof of end-to-end correctness in HOL4 including GC and bignums. — [ACM DL](https://dl.acm.org/doi/10.1145/2951913.2951924) (not fetched)
- Vellvm: Zhao, Nagarakatte, Martin, Zdancewic, "Formalizing the LLVM intermediate representation for verified program transformations", POPL 2012 — formal LLVM IR semantics in Coq; later VIR (Vellvm 2) uses interaction trees. — [ACM DL](https://dl.acm.org/doi/10.1145/2103656.2103709) (not fetched)
- WebAssembly Canonical ABI (component model, fetched 2026-10-22 from main): lifting canonicalises NaN on the way *in* ("some languages and protocols do not preserve these bits"), `CANONICAL_FLOAT32_NAN = 0x7fc00000`, `CANONICAL_FLOAT64_NAN = 0x7ff8000000000000`; lowering *scrambles* NaN payloads (`random_nan_bits`) unless `DETERMINISTIC_PROFILE`, in which case "NaNs are canonicalized to a particular NaN bit-pattern"; narrow ints lifted by `i % (1 << t_width)` with sign fold for signed; three string encodings `utf8`, `utf16`, `latin1+utf16` with a dynamic high-bit tag, surrogates trap (`trap_if(0xD800 <= i <= 0xDFFF)`); flattening limits `MAX_FLAT_PARAMS = 16`, `MAX_FLAT_RESULTS = 1`, beyond which `memory`/`realloc` are required. — [CanonicalABI.md (raw)](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md)
- MLIR: Lattner et al., "MLIR: Scaling Compiler Infrastructure for Domain Specific Computation", CGO 2021 — dialects, regions, attributes; round-trippable textual form is a design requirement. CIRCT applies it to hardware. — [IEEE/arXiv](https://arxiv.org/abs/2002.11054) (not fetched)
- Cranelift ISLE: instruction-selection DSL compiled to Rust with term rewriting; verified-ish via Crocus (Veri-ISLE) — [Bytecode Alliance docs](https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/isle/docs/language-reference.md) (not fetched)
- Koka/Perceus: Reinking, Xie, de Moura, Leijen, "Perceus: Garbage Free Reference Counting with Reuse", PLDI 2021 — ownership-precise RC inserted in a core IR with explicit `dup`/`drop`, reuse of unique cells (functional-but-in-place). — [ACM DL](https://dl.acm.org/doi/10.1145/3453483.3454032) (not fetched)
- GHC: Core (System F_C) → STG → Cmm; Core is typed and small, STG makes evaluation/allocation explicit. — [GHC commentary](https://gitlab.haskell.org/ghc/ghc/-/wikis/commentary/compiler/hsc-main) (not fetched)

### Inferences
- "Lossless" has two incompatible readings and the paper uses both: (1) injective serialisation of the *Form* (a theorem, U1); (2) lens round trip through a *target language* (U3, construction). (2) can only hold on the image of π_L: for arbitrary p ∈ L, λ_L must either fail, approximate (the paper's "syntactic lift" label), or carry a complement (the symmetric-lens construction) holding what the Form drops: comments, formatting, non-Form constructs, unchecked arithmetic. Format 2 should make the complement explicit: a `src` side table keyed by node id (span, original token text, target-specific attributes) that is *not* hashed into the shape hash but is hashed into a separate "presentation hash". Then λ_L∘π_L = id on shape hash holds by construction and the complement is where lossy data lives — the standard BX answer.
- WebAssembly's Canonical ABI is the closest published artefact to RCE's emitter contract: it fixes per-type lifting/lowering with explicit NaN, width and string policies, and its deterministic profile is the mode RCE already runs in (no NaN at all, N3). Adopt its *structure* (a single machine-readable table of type → core representation per target) rather than per-target branches scattered across 300+ `Lang::` match arms.
- Verified compilers show the cheap path to trust is many small IR steps each with its own proof/test, not one big IR; RCE's single lower→normalize→egg→extract pipeline with differential testing is fine, but the four emitters walking the *surface AST* means the Form IR is not actually the thing emitted — the lens laws are being asserted about an IR the emitters never see.

### Gaps
- No source fetched on "lossless IR" as a term of art with a formal definition beyond lens laws; the bidirectional-transformation literature uses "well-behaved"/"very well-behaved" instead.
- Did not verify current Cranelift/ISLE verification status or CIRCT's canonical form rules.

## KQ5. Multi-target emission from one IR: where semantics leak per target

### Takeaway
Every multi-target language ships with a documented list of per-target semantic leaks, and the list is always the same four: integer width/overflow, float formatting/NaN, string encoding (code units vs scalar values), and map/set iteration order. RCE's N-rules (checked i64, finite binary64, scalar-value text, sorted-list Map/Set) pre-empt all four at the value level; the remaining leak surface is the four hand-written runtimes.

### Cited Findings
- Haxe: "For performance reasons, the Haxe Compiler does not enforce any overflow behavior." "The burden of checking for overflows falls to the target platform." C++, Java, C#, Neko, Flash: "32-bit signed integers with usual overflow practices"; PHP, JS, Flash 8: no native Int, "loss of precision will occur if a number reaches the float limit"; workaround `haxe.Int32`/`haxe.Int64` "at the cost of additional computations on certain platforms". — [Haxe manual, Overflow](https://haxe.org/manual/types-overflow.html)
- WebAssembly component model canonical ABI: NaN payloads not preserved across lifting ("some languages and protocols do not preserve these bits"); JS/Python/Scala-style targets are the motivating case; narrow ints lifted modulo 2^width; strings require surrogate-free scalar values (trap on lone surrogates), three encodings negotiated per component. — [CanonicalABI.md](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md)
- RCE's own position (local spec and paper): i64 "checked 64-bit integer overflow is an error and never wraps"; `/` truncates toward zero, `%` takes the dividend's sign; floats finite binary64 with NaN excluded; text = "sequence of Unicode scalar values"; `Map[k,v]` = "list of [k, v] pairs sorted by canonical order of k"; canonical order "null < bool < int < float < text < list < record", floats by IEEE totalOrder (`-0.0 < 0.0`). — [paper §4.5](https://research.openie.dev/papers/rce/); `spec/book/07-form-evaluation.md` §6.1
- RCE emitter structure (local `emit/mod.rs`): "Each emitter turns a checked module into one self-contained source file. The file starts with a runtime that follows the reference evaluator (src/interp.rs) value by value." Rust output mirrors the Lean-verified emitter T9 (`spec/lean/RCE/Emit.lean`): "one uniform value type, `Result` with `?` for traps and refusals, checked i128 arithmetic against each integer type's range, and one counter per bounded loop." Runtimes: rt.rs 2084, rt.py 2107, rt.js 2000, rt.scala 1903 lines; per-target branches: `Lang::` occurrences expr.rs 64, stmt.rs 107, base.rs 68, prog.rs 121.
- Other multi-target systems (not fetched this session; well-known doc locations): Nim (C/C++/JS backends; JS backend uses JS Number for ints so 64-bit ints are lossy — [Nim backends doc](https://nim-lang.org/docs/backends.html)); Kotlin Multiplatform (`expect`/`actual` declarations isolate per-platform divergence; `Long` on Kotlin/JS is boxed and slow — [Kotlin docs](https://kotlinlang.org/docs/multiplatform-expect-actual.html)); Dart (ints are 64-bit on VM but JS Numbers on web, documented — [Dart numbers](https://dart.dev/guides/language/numbers)); Fable (F#→JS: `int64` emitted as BigInt or custom class, `int` as JS number with `| 0` truncation — [Fable docs, numeric types](https://fable.io/docs/javascript/features.html)). Treat these as unverified pointers.

### Inferences
- RCE has already made the hard value-level decisions that Haxe/Nim/Dart punted on; the leak is now purely in *runtime fidelity*: four 2k-line runtimes "follow the reference evaluator value by value" and are the only place a target can diverge. Differential testing (`trace --json` agreement) is the right gate, but each runtime is a separate re-implementation of the canonical-JSON serialiser and totalOrder comparator, i.e. four copies of §6.1.1. Any drift there changes trace hashes silently across targets.
- The 300+ `Lang::` match arms in the emitter are the multi-target "leak surface" in code form; a `defs`-driven emitter that walks Form IR (not the surface AST) with a per-target *table* (Canonical-ABI style: type → representation, op → runtime helper name) would shrink that to data and make the four targets diff-able.
- Scala/JVM is the odd target: JVM `String` is UTF-16 code units, so "text by code point" ordering and length must be computed over code points, not `String.length`/`compareTo`; this is a known class of leak (WASM CABI handles it by transcoding at the boundary).

### Gaps
- Did not fetch Nim/Kotlin/Dart/Fable pages this session; claims above are from background knowledge and should be spot-checked before citing externally.
- No data on how many of RCE's differential-test disagreements historically came from runtime (rt.*) bugs vs emitter (expr/stmt) bugs.

## KQ6. Lifting source to IR: tree-sitter/LSP, decompilers, semantic diff

### Takeaway
Industrial lifters (Ghidra P-code, Binary Ninja LIL/MLIL/HLIL) are explicitly *lossy and layered*: a raw per-instruction IR that is mechanically total, then progressively abstract levels that discard information. Structural diff tools built on tree-sitter show the same shape: total on parse, heuristic on matching, and they fall back to text on parse errors. The design pattern is "total syntactic lift + labelled approximations", which is what RCE's "syntactic lift" label already is.

### Cited Findings
- RCE paper §6: `rce scan DIR --form` "builds a Form from the abstract syntax tree and the symbols that language-server tooling resolves", Rust/Python/TypeScript/Go; repair results on the lifted programs: L0 one-token 520,541/520,821 (0.9995), L1 Java hunk-only 9,288/24,072 (0.386), full-file 13,586/21,320 (0.637), L1 Python hunk-only 27,266/157,089 (0.174); 108 of 280 L0 misses are float-literal digit mutations. — [RCE paper §6](https://research.openie.dev/papers/rce/)
- Difftastic tricky cases (tree-sitter-based structural diff): "Difftastic will fall back to a line-oriented diff if any parse errors occur, to avoid diffing incomplete syntax trees"; `DFT_PARSE_ERROR_LIMIT` lets error nodes be treated as atoms; ambiguity classes documented: flat/nested sliders ("The correct answer depends on the language"), "Difftastic considers ordering to be meaningful everywhere, so it will always report ordering changes" (bad for unordered data), blank-line changes hidden ("it can hide accidental code reformatting"), depth changes ("`x` has changed its depth in the tree, but `x` itself is unchanged"), trailing-punctuation lists treated as equal, comment prefix/suffix matching. — [difftastic, Tricky cases](https://difftastic.wilfred.me.uk/tricky_cases.html)
- Ghidra P-code reference (fetch failed with client error this session; standard location): raw p-code is produced per instruction by SLEIGH specs over varnodes/address spaces; the decompiler then builds "high" p-code with SSA and type recovery; unmodelled instructions appear as `CALLOTHER`. — [ghidra.re pcoderef](https://ghidra.re/courses/languages/html/pcoderef.html) (not fetched; from background)
- Binary Ninja: Low/Medium/High-Level IL tower with documented information loss at each level (HLIL drops stack/flag detail) — [Binary Ninja BNIL docs](https://docs.binary.ninja/dev/bnil-overview.html) (not fetched)
- Hash-consing as the enabling data structure for lifts and term stores: Filliâtre & Conchon, "Type-Safe Modular Hash-Consing", ACM SIGPLAN ML Workshop 2006 — maximal sharing by construction, O(1) structural equality, hash tables of weak pointers. — [ML 2006 accepted papers](https://gallium.inria.fr/ml2006/accepted/5.html); OCaml package [hashcons 1.3](https://opam.ocaml.org/packages/hashcons/hashcons.1.3/)

### Inferences
- The "L0 token-identity gate" results depend on the lift being *injective on tokens* (float literal digits were the failure class: 108/280). That is a losslessness failure at the leaf level: if λ_L normalises `1.50` to `1.5`, token identity cannot be restored by π_L. Keep literal *spelling* in the complement (see KQ4) and hash only the value.
- Difftastic's documented ambiguity classes are exactly the places where λ_L is not a function of the AST alone (sliders, delimiter attribution). A Form-level diff should compare `defs` keys (set difference of digests) first and only descend into tree diff for bodies whose digest changed — content addressing removes most of the ambiguity surface because unchanged subterms are byte-identical by key.
- LLM-free lifting at scale (2023–2026) appears in the RCE paper's own numbers (0 model calls); I found no independent 2023–2026 published result on source→semantic-IR lifting with round-trip guarantees (binary lifters publish correctness only by differential testing).

### Gaps
- Ghidra P-code page failed to fetch; no primary quote. Binary Ninja, SemanticMerge, Diffsitter, GumTree not fetched.
- No independent 2023–2026 paper found on LLM-free source-to-IR lifting with lens-style round-trip claims; the search budget was exhausted on canonical encodings.

## KQ7. Term graphs vs trees: hash-consing, sharing, egg, cost of inlining

### Takeaway
Format 1's inlining is the textbook failure mode of tree IRs (exponential blow-up, no recursion), and format 2's `defs` table *is* hash-consing at the definition granularity; the remaining design choice is whether to hash-cons every subterm (DAG) or only named definitions, and how the e-graph interacts with `ref` leaves.

### Cited Findings
- RCE: "a term grows with the number of call sites times the callee size, and a recursive function has no finite term at all"; 77/188 refusals are size/depth; `defs` keyed by SHA-256 of canonical JSON of the body; "two bricks that call the same function share one entry"; e-graph "treats a `ref` as an opaque leaf (its key is its identity), and inlines a definition only when its body is at most `INLINE_MAX` nodes, so rewriting never grows a term past a stated bound." — `spec/proposals/form-ir-2.md` §1 (local)
- Hash-consing: maximal sharing by construction, physical equality for structural equality, memoisation keyed on hashed nodes — Filliâtre & Conchon 2006 — [ML 2006](https://gallium.inria.fr/ml2006/accepted/5.html)
- egg: Willsey, Nandi, Wang, Flatt, Tatlock, Panchekha, "egg: Fast and Extensible Equality Saturation", POPL 2021 — e-graphs with deferred rebuilding and e-class analyses; the e-graph is a hash-consed term DAG where e-nodes are keyed by (op, child e-class ids). — [ACM DL](https://dl.acm.org/doi/10.1145/3434304) (not fetched; RCE already depends on egg 0.11 per `closing-the-loop.md` §2)
- Unison: dependencies replaced by hashes in the syntax tree before hashing; the codebase is a DAG of hashes. — [Unison, The Big Idea](https://www.unison-lang.org/docs/the-big-idea/)
- Dhall: hashes the fully β-normalised expression, i.e. *after* total inlining — acceptable only because Dhall is total and non-recursive. — [dhall binary.md](https://github.com/dhall-lang/dhall-lang/blob/master/standard/binary.md)

### Inferences
- A content-addressed `defs` table whose keys are digests of bodies that themselves contain keys is a Merkle DAG; the shape hash of a Form becomes the digest of `main` plus the sorted key set, which is what Unison and IPLD do. This gives O(1) sharing detection and makes "did this brick change" a key comparison.
- Rule (a) makes the DAG acyclic by construction; the price is no mutual recursion in `defs`. Unison solved this by hashing a strongly connected component as one unit; RCE's planned bounded `fix` is the Form-consistent alternative (a decreasing measure is a stronger requirement than Unison's).
- Inlining in the e-graph should be a *rewrite rule with a cost*, not a size threshold alone: `INLINE_MAX` bounds growth, but extraction with cost = est_j already prefers smaller terms; the risk is the opposite — the e-graph never sees through a `ref` to a law that would fire. Carry per-definition e-class analyses (e.g. the catalog's `laws[]`, pre/post) on the opaque leaf so laws apply without inlining.

### Gaps
- No measurements of term-size reduction from `defs` on the 77 refused bricks (the proposal is unimplemented as of the grounding snapshot).
- Did not fetch the egg paper; e-graph/term-DAG claims are from the POPL 2021 paper as known.

## KQ8. Recommendations for the Form IR (adopt / refuse) and open problems

### Takeaway
Adopt format 2 `defs` as a Merkle DAG with α-erased bodies and an unhashed complement table; keep canonical JSON as the normative hash input but add a bit-exact binary mirror for transport; make emitters walk Form IR via a Canonical-ABI-style per-target table; treat λ_L as a symmetric lens with an explicit complement rather than a theorem.

### Cited Findings
(Recommendations below cite the findings in KQ1–KQ7; sources are repeated inline.)

**Adopt**
- `defs` as Merkle DAG; shape hash of a program = digest of canonical JSON of `{"format":2, "defs": sorted keys, "main": term}`; key = digest(body); acyclic by rule (a). — grounded in `form-ir-2.md`; mirrors [Unison](https://www.unison-lang.org/docs/the-big-idea/) and [DAG-CBOR CID links](https://ipld.io/specs/codecs/dag-cbor/spec/).
- α-erasure before hashing: local binders by position/index inside bodies; human names in a separate, unhashed `names` table. — [Unison](https://www.unison-lang.org/docs/the-big-idea/), [Dhall](https://github.com/dhall-lang/dhall-lang/blob/master/standard/binary.md). This also fixes the Unicode-normalisation hazard for identifiers (RCE §6.1.1 deliberately does not normalise text).
- Hash the *normalised* body (ANF + confluent normaliser), not the as-lowered body, so β/η-equal bricks dedupe. — [Dhall](https://github.com/dhall-lang/dhall-lang/blob/master/standard/binary.md).
- Emit target function names from the key in every target (Rust already; extend to Python/JS/Scala) so oracle/trace keys agree across targets. — Nix diamond problem, [Tweag 2020-11-18](https://tweag.io/blog/2020-11-18-nix-cas-self-references).
- A machine-readable per-target lowering table (type → representation, op → runtime helper, trap policy) consumed by one emitter walking Form IR, replacing ~360 `Lang::` match arms; the WebAssembly Canonical ABI is the template, with RCE's N-rules already equal to the deterministic profile. — [CanonicalABI.md](https://raw.githubusercontent.com/WebAssembly/component-model/main/design/mvp/CanonicalABI.md).
- Dependents index + typed propagation for `defs` edits (change one body ⇒ recompute keys up the DAG, re-check each, keep names). — [Unison update, 2023-10-20](https://unison-lang.org/blog/new-update-process).
- Strict decoder (refuse non-canonical bytes), as format 2 already specifies; plus the 77 golden vectors must be run against every runtime that serialises (rt.js, rt.py, rt.scala, rt.rs). — RCE §6.1.1; contrast with lenient defaults in [DAG-CBOR](https://ipld.io/specs/codecs/dag-cbor/spec/) and [Dhall](https://github.com/dhall-lang/dhall-lang/blob/master/standard/binary.md).
- Symmetric-lens complement for λ_L: an unhashed `src` table (spans, literal spellings, dropped constructs) keyed by node id; shape hash excludes it, a separate presentation hash includes it. Then λ_L∘π_L = id on shape hash by construction. — [Hofmann–Pierce–Wagner 2011](https://dl.acm.org/doi/10.1145/1926385.1926428); L0 float-literal misses in [RCE §6](https://research.openie.dev/papers/rce/).

**Refuse**
- Replacing canonical JSON with RFC 8785 or deterministic CBOR as the *normative* hash input: RFC 8785 cannot represent int≠float, −0, or u64 exactly (RCE §6.1.1 table); RFC 8949 "preferred" float serialisation (shortest of f16/f32/f64) and DAG-CBOR's always-f64 disagree with each other, so switching would re-open the float rule. Keep §6.1.1 bytes as the hash input; a CBOR *transport* mirror is fine only if defined as a bijection to those bytes and tested on the same vectors. — [RFC 8949 §4.2](https://www.rfc-editor.org/rfc/rfc8949#section-4.2), [DAG-CBOR](https://ipld.io/specs/codecs/dag-cbor/spec/).
- Protobuf/schema-evolution-style unknown fields anywhere in Form IR: the protobuf team's own verdict is that unknown fields make canonicalisation impossible. Format 2's "a format 1 term (no `format` field) is read as format 2 with empty defs" is a one-shot migration, not an open extension point; keep it that way. — [protobuf.dev](https://protobuf.dev/programming-guides/serialization-not-canonical/).
- Content-addressing *emitted artefacts* (the Nix model) as the identity of a target: outputs embed paths/names and emitters are allowed to differ in text; identity stays the Form shape hash, artefacts are derived. — [Tweag 2020-09-10](https://www.tweag.io/blog/2020-09-10-nix-cas/), [2020-11-18](https://tweag.io/blog/2020-11-18-nix-cas-self-references).
- Full β-normalisation before hashing (Dhall's choice): Dhall can because it is total and non-recursive; RCE's bounded loops and future `fix` make total inlining the same blow-up format 1 has. Normalise, do not inline. — [Dhall](https://github.com/dhall-lang/dhall-lang/blob/master/standard/binary.md), `form-ir-2.md`.
- Treating λ_L as a theorem for arbitrary L programs; keep "syntactic lift" labels and the complement. — [RCE §3.6](https://research.openie.dev/papers/rce/) (U3 "is a construction, not a theorem").

### Inferences (open problems)
- Mutual recursion in `defs`: Unison hashes SCCs as one component; RCE's rule (a) forbids cycles and defers to a bounded `fix`. Open: whether a component-level key (digest of the sorted list of member bodies with intra-component refs replaced by positional indices) is compatible with the decreasing-measure requirement, or whether `fix` must stay a single-body construct.
- Semantic vs syntactic key: two keys per body (store key = digest of normalised bytes; semantic key = e-graph canonical representative under catalog laws) vs one. One key is simpler; two keys let the catalog dedupe by law without invalidating stored hashes when laws are added.
- Canonical-JSON implementation drift across four runtimes is the largest practical integrity risk; a single shared serialiser (Rust via WASM for JS/Python, JVM via a generated port tested on the 77 vectors) or a conformance test in CI per target is needed before `defs` keys cross targets.
- Unicode policy split: values unnormalised (correct), identifiers erased (recommended), but `node` attributes and oracle keys derived from source text still carry raw identifiers; decide whether those are hashed.
- Lift totality: `rce scan` is total on tree-sitter parses but not on semantics; the L1 "new conjuncts 3–7%" and whole-statement-rewrite 1.2% classes are where the complement must carry intent that the Form cannot represent; no external result found that does better without a model.
