## BLAS
- The Level 1 BLAS paper is cited as C. L. Lawson, R. J. Hanson, D. Kincaid and F. T. Krogh, ACM TOMS 5 (1979) 308–323, with the Level 2/3 papers by Dongarra, Du Croz, Hammarling and Hanson in TOMS 14 (1988) [secondhand: the paper itself could not be fetched]. — AMD ROCm, "references.rst", rocBLAS docs, ROCm/rocm-libraries commit 24106e1, 2026, https://github.com/ROCm/rocm-libraries/blob/develop/projects/rocblas/docs/reference/references.rst
- Reference LAPACK ships the Fortran reference BLAS "intended for use only if there is no other implementation of the BLAS already available", together with its testing programs, CBLAS and LAPACKE. The reference code is the de facto definition and test oracle; speed comes from vendor libraries. — Reference-LAPACK, "README.md" (latest listed release 3.12.1, Jan 2025), GitHub, https://github.com/Reference-LAPACK/lapack
- The reference ?GEMM did not follow its own documented formula C := alpha·op(A)·op(B) + beta·C under IEEE rules. With alpha=0 and beta=1, NaN/Inf in A or B "do not affect the result", and alpha=beta=0 returns a zero matrix "irrespective of any NaNs or Infs in A, B or C". Maintainer J. Langou confirmed this, and the docs were fixed in PR #1098 (Aug 2025). — TiborGY, "?GEMM documentation is fuzzy on NaN handling when alpha or beta is zero", Reference-LAPACK issue #1077, 2024–2025, https://github.com/Reference-LAPACK/lapack/issues/1077
- Until 2026 the reference BLAS disagreed with itself on NaN. isamax/idamax skipped NaNs (for [0, NaN, 2], isamax returned 3) while icamax returned 2. PR #1416 (merged 18 Oct 2026) made the real routines return the first NaN, matching the complex routines that PR #1116 (June 2025) had rewritten "as proposed in" arXiv:2207.09281, "Proposed Consistent Exception Handling for the BLAS and LAPACK". That paper's own contents were not fetched. — ACSimon33, PR #1416, 2026, https://github.com/Reference-LAPACK/lapack/pull/1416; W. Pereira, "Adds new icamax with exception handling", PR #1116, 2025, https://github.com/Reference-LAPACK/lapack/pull/1116
- rocBLAS says gemv, symv, trsv, trsm and gemm "can use atomic operations"; "By using atomics, functions might not give bit-wise reproducible results." Atomics are on by default; rocBLAS 4.0 announced that the default will switch to not-allowed "for improved determinism". Its docs also list API departures from legacy BLAS: C status returns, a handle argument, scalar results returned through pointers, device pointers, and no NULL checks in device pointer mode [self-reported]. — AMD, rocblas-design-notes.rst, deprecations.rst and Programmers_Guide.rst, ROCm/rocm-libraries, 2026, https://github.com/ROCm/rocm-libraries/tree/develop/projects/rocblas/docs
- PyTorch makes no bitwise-identity promise across releases, commits or platforms, and says CPU and GPU "can be different even for bitwise-identical inputs". (A@B)[0] is not guaranteed equal to A[0]@B[0]. TF32 on Ampere keeps only 10 mantissa bits of the input. linalg results "may vary when using the same inputs on different devices or when using different backends" [self-reported]. — PyTorch contributors, "Numerical accuracy", docs/source/notes/numerical_accuracy.md, 2026, https://github.com/pytorch/pytorch/blob/main/docs/source/notes/numerical_accuracy.md

## LAPACK
- OpenBLAS's FAQ says the LAPACK tests were written for "unoptimized, single-threaded Fortran" and are "very sensitive to small numerical deviations" from FMA or parallel reordering. "A small number of errors in the 'numerical' column" is "usually nothing to worry about", and the count varies with compiler flags and CPU [self-reported]. — OpenBLAS, docs/faq.md, https://github.com/OpenMathLib/OpenBLAS/blob/develop/docs/faq.md
- One reported run (OpenBLAS 0.3.23, GCC 12.2, AMD Genoa) gave 269 numerical errors (0.006%) and 1 other error (DDRGES3 INFO=9) out of 4,216,069 LAPACK tests. The maintainer said "parts of the testsuite appear to be too stringent to be useful in the context of optimized implementations"; the workaround was to edit a test input. — OpenBLAS issue #4032, 2023–2024, https://github.com/OpenMathLib/OpenBLAS/issues/4032
- NaN behaviour changed with OpenBLAS 0.3.15. np.linalg.cond on [[1, nan], [1, 1]] began raising "SVD did not converge"; the test had passed with 0.3.12 and 0.3.13. Langou traced this to Reference-LAPACK PR #471 (NaN-norm early return). The same split later appeared between MKL 2021.4 (returns NaNs) and MKL 2022.0 (raises). NumPy maintainers chose to document that results may differ between LAPACK implementations. — R. Gommers et al., numpy issue #18914, 2021–2026, https://github.com/numpy/numpy/issues/18914
- eigh on NaN input can raise, return all NaN, or return the result for the opposite triangle. A commenter quotes the oneMKL specification: "LAPACK routines assume that input matrices do not contain IEEE 754 special values" [secondhand]. The issue is still open. — F. Draxler et al., numpy issue #20280, 2021–, https://github.com/numpy/numpy/issues/20280

## Python Array API standard and DLPack
- The Consortium for Python Data API Standards was assembled in May 2020. "No reference implementation is planned": the standard is a document plus a test suite. Execution semantics and behaviour on invalid input are out of scope. The adoption table lists NumPy at 2025.12 and JAX at 2024.12; PyTorch, Dask and CuPy conform only through array-api-compat. — Consortium, "Purpose and scope", spec/draft/purpose_and_scope.md, data-apis/array-api commit ff497ed, 2026, https://github.com/data-apis/array-api
- Required accuracy is narrow. Only + − × ÷ (and add/subtract/multiply/divide), sqrt and reciprocal must be correctly rounded. 22 functions, including exp, log, sin, pow and hypot, are "implementation-dependent approximation". There are no accuracy requirements for statistical, linear-algebra or complex operations, and subnormal support "may vary". — Consortium, design_topics/accuracy.rst, same repo
- The draft stubs use "implementation-defined" 64 times, "implementation-dependent" 95 times and "unspecified" 114 times (count by this survey). For example, unique() element order "may vary between implementations", whether an output shares memory with its input is unspecified, and out-of-bounds indexing is implementation-defined. Released versions: 2021.12, 2022.12, 2023.12, 2024.12, 2025.12. — data-apis/array-api, src/array_api_stubs/_draft
- The verification page says the test suite "is still a work in progress" and that "the specification is the ground source of truth". The array-api-tests README says floating-point values are only checked to be "roughly as expected", that Hypothesis's default of 20 examples makes XFAILs flaky, and that some parts of the spec are "impractical or impossible to actually test". — Consortium, verification_test_suite.md; array-api-tests README.md, commit 6c0b59f, 2026, https://github.com/data-apis/array-api-tests
- Maintainer-kept failure lists (test IDs, of which special-case tests in parentheses; count by this survey) [self-reported]: array-api-compat lists NumPy 34 (30), CuPy 178 (120), PyTorch 116 (53) and Dask 111 (28); NumPy's own CI list has 51 (26); JAX's skip list has 94 (83). Stated reasons include:
  - PyTorch: "inverse trig functions are too inaccurate on CPU", and RuntimeError where the spec says ValueError.
  - CuPy: "(arg)min/max wrong with infinities".
  - Dask: data-dependent shapes reported as NaN.
  - JAX: "Returns wrong zero sign", and int32 where int64 is expected.

  — data-apis/array-api-compat {numpy,cupy,torch,dask}-xfails.txt, https://github.com/data-apis/array-api-compat; numpy tools/ci/array-api-xfails.txt, https://github.com/numpy/numpy; jax tests/array_api_skips.txt, https://github.com/jax-ml/jax
- The authors built the standard from API intersections across NumPy, CuPy, PyTorch, JAX, TensorFlow, Dask and MXNet. They call the property-based suite "the first example known to these authors of a Python test suite capable of running against multiple different libraries". They built the compat layer because co-evolution is "not likely to always proceed in unison". — A. Meurer, A. Reines, R. Gommers, Y.-L. L. Fang, J. Kirkham, M. Barber, S. Hoyer, A. Müller, S. Zha, S. Shanabrook, S. Jiménez Gacha, M. Lezcano-Casado, T. J. Fan, T. Reddy, A. Passos, H. Kwon, T. Oliphant, Consortium, "Python Array API Standard: Toward Array Interoperability in the Scientific Python Ecosystem", Proc. SciPy 2023, source https://github.com/scipy-conference/scipy_proceedings/blob/2023/papers/aaron_meurer/paper.rst
- DLPack semantics leave room for differences. from_dlpack must be zero-copy "if possible", so the result "may or may not be a view". Stream synchronization is a producer obligation. Producer and consumer device_id numbering is "not guaranteed" to match. — DLPack, docs/source/python_spec.rst, https://github.com/dmlc/dlpack
- The DLPack header records non-conformance in its own text. It requires 256-byte alignment, then notes that "as of Nov 2021, multiple libraries (CuPy, PyTorch, TensorFlow, TVM, perhaps others) do not adhere" and advises not relying on it. NULL strides were allowed before v1.2 and are disallowed from v1.2; the header is now v1.3. In array-api-tests, CuPy xfails test_dlpack because "CuPy 14 does not support copy=" and Dask has "no dlpack support". — DLPack, include/dlpack/dlpack.h; array-api-compat xfails, as above

## ONNX
- ONNX defines operators as "abstract interfaces… the contract between a model author and the implementations"; any semantic change MUST be a new operator version in a new opset. The backend test suite is "one of the two ways to define each operator's expected behavior", and "adding more test cases is the only way to enforce" that there is no ambiguity. — ONNX, docs/Versioning.md and docs/OnnxBackendTest.md, https://github.com/onnx/onnx
- The operator spec leaves gaps on purpose. Cast float→integer is "undefined if OOR"; TopK with sorted=0 has "undefined" order; repeated axes are "undefined" in Slice, Pad and Resize. Resize-10 defined only output size and nearest/linear interpolation, with no coordinate mapping. Later versions added coordinate_transformation_mode with framework-named modes: half_pixel, pytorch_half_pixel, align_corners, asymmetric, tf_crop_and_resize, half_pixel_symmetric. — ONNX, docs/Operators.md and docs/Changelog.md, same repo
- Scoreboard (count by this survey): ONNX Runtime 1.23.2 passed 1,265 and failed 172 of the onnx 1.17.0 tests (88.0%, 2025-11-09). onnx-tf 1.10.0 on TF 2.13.1 passed 1,296 and failed 141 (90.2%, 2025-11-13). Only 35 failures are shared. Failures mix unsupported operators (adagrad, bernoulli) with divergent results. — ONNX, backend-scoreboard results/{ort,onnx-tf}/stable/report.json, https://github.com/onnx/backend-scoreboard
- NNSmith reports 185 bugs [self-reported], including 12 in the PyTorch→ONNX converter, 11 in ONNX Runtime and 10 in TensorRT. Examples: ORT Resize "nearest" inconsistent with PyTorch and TVM (#12098); Resize linear "always produces 0.5 on GPU" (#12091); interpolation exported with pytorch_half_pixel instead of half_pixel (#79361). — J. Liu, J. Lin, F. Ruffy, C. Tan, J. Li, A. Panda, L. Zhang, "NNSmith: Generating Diverse and Valid Test Cases for Deep Learning Compilers", ASPLOS '23 Vol. 2, 530–543, 2023, DOI 10.1145/3575693.3575707 (as listed in the repo); bug list https://github.com/ise-uiuc/nnsmith/blob/main/doc/bugs.md

## WASI
- WASI is developed by the WASI Subgroup of the WebAssembly CG: Preview 1 (witx), then 0.2 (WIT and the component model), with 0.3 the current preview. It uses unforgeable handles and "no ambient authorities". Portability "will be specific to each API", and engines need not implement every API. — WebAssembly, WASI README.md and docs/DesignPrinciples.md, https://github.com/WebAssembly/WASI
- wasi-filesystem says path lookup and file, directory and symlink semantics are "host-dependent", and it is "not aiming for deterministic semantics". Its bar for portability is passing the testsuite on Windows, macOS and Linux with "at least two complete independent implementations". — WebAssembly, wasi-filesystem README.md, https://github.com/WebAssembly/wasi-filesystem
- Daily results for 2026-06-08 (count by this survey):

  | Runtime | Preview 1 Rust tests | C tests | Preview 3 Rust tests |
  |---|---|---|---|
  | Wasmtime 47.0.0 | failed 1 of 46 (remove_directory_trailing_slashes, EINVAL) | passed all | failed 2 of 40 |
  | WAMR 2.4.3 | passed 46 | passed 14 | all 40 skipped |
  | WasmEdge | passed 46 | passed 14 | all 40 skipped |
  | wazero | failed 12 of 46 (readlink, path_link, renumber, rights tests) | failed 2 of 14 | all 40 skipped |
  | pywasm 2.2.1 | failed 42 of 46 | not tabulated | all 40 skipped |

  Runners can mark tests skip or expected-fail per runtime. — WebAssembly, wasi-testsuite README.md and branch prod/daily-test-results commit ad248d8, https://github.com/WebAssembly/wasi-testsuite
- The suite itself accepts two outcomes. pwrite-with-append says "POSIX says it should write at 0, Linux says it should write at the end with O_APPEND. Accept either". This matches the Linux pread(2) BUGS note: "on Linux… pwrite() appends data to the end of the file, regardless of the value of offset." — wasi-testsuite tests/c/src/pwrite-with-append.c; Linux man-pages, pread(2), 2021-03-22, https://github.com/mkerrisk/man-pages/blob/master/man2/pread.2

## POSIX
- The Open Group's VSX/VSTH suites and UNIX certification register could not be reached (opengroup.org returned 403), so nothing about them is verified here. The Open POSIX Test Suite (shipped in LTP) does assertion-traceable conformance testing of IEEE 1003.1-2001 "agnostic to any given implementation" and is "not affiliated with the IEEE or The Open Group". — Linux Test Project, testcases/open_posix_testsuite/README, https://github.com/linux-test-project/ltp
- SibylFS's executable POSIX file-system model has to be parameterized per platform: `ty_arch = ARCH_LINUX | ARCH_POSIX | ARCH_MAC_OS_X | ARCH_FREEBSD`, with traits such as a leading "//" ("POSIX has maybe implementation defined") and group inheritance for new directories. About 55 platform branches appear in the model (count by this survey). Examples: renaming root gives EBUSY on Linux and Mac but EISDIR on Mac and FreeBSD. Its annotated POSIX notes say "posix test suite doesn't appear to check this; Linux gives ENOTDIR" for `rename a.txt/`. The SOSP paper's own figures were not reachable. — T. Ridge, D. Sheets, T. Tuerk, A. Giugliano et al., "SibylFS: formal specification and oracle-based testing for POSIX and real-world file systems", SOSP 2015; source sibylfs_src commit 30675bc, https://github.com/sibylfs/sibylfs_src

## Khronos (Vulkan CTS, OpenCL CTS)
- Vulkan conformance runs VK-GL-CTS (derived from dEQP) against a mustpass list. Submitting means a package of logs, git state and patches. Test bugfixes must be merged upstream first, and "other changes must be accompanied by a waiver". The main-branch mustpass names 3,220,329 cases in 196 group files, 757 of them dEQP-VK.graphicsfuzz cases (count by this survey). — Khronos, VK-GL-CTS README.md and external/vulkancts/README.md and mustpass/main, https://github.com/KhronosGroup/VK-GL-CTS
- Vulkan pins precision only as tolerances. Single-precision sin/cos must be within absolute error ≤ 2^-11 on [−π, π], exp within 3 + 2|x| ULP, and pow is "inherited from exp2(y × log2(x))". Without the float-controls path, denormals "may be flushed to 0" and "NaNs may not be generated". — Khronos, Vulkan-Docs appendices/spirvenv.adoc, https://github.com/KhronosGroup/Vulkan-Docs
- The OpenCL CTS math test accepts several kinds of answer:
  - a bitwise match with the reference, or any result within the ULP bound;
  - any NaN when the reference is NaN;
  - FTZ zeros;
  - premature overflow or underflow within tolerance.

  For native_ functions "any result is conformant". For OpenCL 1.0 the reference was the OS math library, so that "all devices on a particular operating system are returning similar results". — Apple/Khronos, test_conformance/math_brute_force/README.txt, https://github.com/KhronosGroup/OpenCL-CTS
- GraphicsFuzz (glsl-fuzz, spirv-fuzz) lists driver bug write-ups for AMD, Apple, ARM, Imagination, Intel, Nvidia and Qualcomm (2016–17) and for specific phones (2018) [self-reported]. Its shaders now make up the 757 CTS cases above. The OOPSLA paper's numbers and author list were not fetched. — Google, graphicsfuzz README.md, https://github.com/google/graphicsfuzz; "Automated Testing of Graphics Shader Compilers", OOPSLA 2017

## Java TCK / JCK
- On 10 April 2007 the ASF wrote that since August 2006 it had been unable to obtain an acceptable licence for the Java SE 5 JCK, needed for Apache Harmony to show compatibility, because the licence imposed "field of use" restrictions. Its FAQ explains: the spec lead must deliver a TCK, passing it grants "necessary IP", and the ASF had signed "15+" other TCK licences without such limits. The ASF left the JCP SE/EE Executive Committee effective 9 Dec 2010. — G. Magnusson Jr./ASF, "Open Letter to Sun Microsystems – JCK" and FAQ, 2007, https://www.apache.org/jcp/sunopenletter.html, https://www.apache.org/jcp/sunopenletterfaq.html; ASF, https://www.apache.org/jcp/
- The JCK remains private. It is available under the OpenJDK Community TCK Licence Agreement (OCTLA); Adoptium does not currently run it; licensees run it on their own private Jenkins servers. — Adoptium, aqa-tests README.md and jck/README.md, https://github.com/adoptium/aqa-tests
- Jakarta EE under the Eclipse process works differently. A Compatible Implementation "fulfils all requirements… as demonstrated by fulfilling all requirements of the associated TCK". There is exactly one open-source TCK per specification version, at least one open-source compatible implementation is required, and "all parts… should be covered by the TCK". — Eclipse Foundation, Specification Process v1.4.1, https://www.eclipse.org/projects/efsp/
- The Java SE spec itself allows differences. java.lang.Math implementations "are not defined to return the bit-for-bit same results" (1–2 ulp, semi-monotonic); only StrictMath is bit-exact. HashMap does not guarantee iteration order "will remain constant over time". — OpenJDK, Math.java and HashMap.java, https://github.com/openjdk/jdk
- I could not verify any study of behavioural divergence between JVMs that pass the TCK.

## C++ standard library (libstdc++, libc++, MSVC STL)
- The draft fixes random engines bit-exactly: the 10000th output of a default-constructed mt19937 "produces the value 4123659995". Distribution algorithms, by contrast, are implementation-defined. The library clauses have 176 \impldef markers, out of 280 in the whole draft (count by this survey). — WG21, cplusplus/draft source/numerics.tex, commit 47974a2, 2026-10-14, https://github.com/cplusplus/draft
- The standard requires implementation-defined behaviour to be documented, but the documentation is incomplete. libc++'s page says it "is far from complete". libstdc++'s entry for [rand.dist.general] says only that "The algorithms used by the distributions should be documented here." — LLVM, libcxx/docs/ImplementationDefinedBehavior.md, https://github.com/llvm/llvm-project; GCC, libstdc++-v3/doc/xml/manual/status_cxx2011.xml, https://github.com/gcc-mirror/gcc
- libc++ added a mode that randomizes unspecified orderings (std::sort, partial_sort, nth_element) because user tests depended on them. "Google has measured couple of thousands of tests to be dependent on the stability of sorting and selection algorithms" [self-reported]. — LLVM, libcxx/docs/DesignDocs/UnspecifiedBehaviorRandomization.md, same repo
- MSVC STL runs its own std and tr1 suites plus libc++'s test suite. Its expected-results file has 881 entries (683 FAIL, 198 SKIPPED) covering 769 distinct libc++ tests; libc++'s libcxx/test/std has about 8,669 test files at LLVM main (count by this survey; MSVC pins its own LLVM revision). The entries break down as:
  - 222 not analyzed
  - 188 missing features
  - 90 known upstream
  - 87 "likely bogus tests"
  - 64 likely STL bugs
  - 61 STL bugs
  - 48 compiler bugs

  Named divergences include: "we set 0, libc++ sets ECMAScript" for default basic_regex flags; "libc++ chose option A for [time.clock.file.members], and we chose option B"; lerp with infinity; fs::absolute(""); and different speculative fixes for LWG-2227, LWG-3645 and LWG-4058 [self-reported classifications]. — Microsoft, STL README.md and tests/libcxx/expected_results.txt, https://github.com/microsoft/STL

## What this establishes
- **Passing a conformance suite does not mean producing the same output.** In every case the specification leaves numerical results loose (transcendental functions, reductions, NaN/subnormal handling), and the suites check against tolerances or accept several outcomes rather than requiring identical bits. Sources: Array API accuracy.rst and array-api-tests README; Vulkan spirvenv.adoc; the OpenCL CTS math_brute_force README; OpenJDK Math.java; the C++ draft's numerics.tex; the PyTorch and rocBLAS notes.
- **Where a reference implementation acts as the specification, edge-case meaning changes when the reference changes, and vendors catch up at different times.** Examples: the reference ?GEMM's NaN behaviour (issue #1077), the i?amax NaN fix in 2026 (PRs #1116 and #1416), LAPACK PR #471 reaching OpenBLAS 0.3.15 and MKL 2022.0 in different releases (numpy #18914), and ONNX Resize gaining framework-named coordinate modes after version 10 (Changelog.md).
- **The suites are incomplete, and the real record of conformance is each project's list of known failures.** That record runs from 34 to 178 xfailed test IDs per library for the Array API, from 100% to about 9% on WASI preview 1 Rust tests, 88–90% on the ONNX scoreboard, and 881 MSVC STL entries against libc++'s suite, of which 87 MSVC judges to be tests that encode libc++'s own choices. Sources: the array-api-compat, NumPy and JAX lists; wasi-testsuite results; backend-scoreboard; MSVC STL expected_results.txt; Vulkan CTS waivers.
- **Interfaces that sit on a host system say openly that they do not aim for identical behaviour.** wasi-filesystem calls its semantics "host-dependent" and non-deterministic. WASI tests accept either the POSIX or the Linux pwrite result. The SibylFS model needs separate Linux, POSIX, Mac OS X and FreeBSD variants to describe real systems. Sources: wasi-filesystem README; pwrite-with-append.c and pread(2); the sibylfs_src spec.
- **Who controls the test suite shapes the ecosystem as much as the specification text does.** The JCK is licensed and private (the Harmony dispute, OCTLA). The Eclipse process requires an open-source TCK and at least one open implementation. Khronos requires formal submission packages with waivers. The Array API and WASI suites are open, and MSVC STL uses libc++'s tests in its own conformance testing. Sources: the ASF open letter and FAQ; the Adoptium aqa-tests README; EFSP 1.4.1; the VK-GL-CTS README; the MSVC STL README.
