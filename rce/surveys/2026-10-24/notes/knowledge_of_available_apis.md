**API learning obstacles**
- More than 440 professional Microsoft developers were surveyed and interviewed about learning new APIs. The most severe obstacles concerned documentation and other learning resources, and the study names five documentation factors: intent, code examples, matching APIs to scenarios, penetrability, and format [self-reported]. Robillard, M. P., and DeLine, R., "A field study of API learning obstacles," Empirical Software Engineering 16:703–732, Dec 2011. DOI 10.1007/s10664-010-9150-8 (abstract read at https://www.microsoft.com/en-us/research/publication/field-study-api-learning-obstacles/).
- Robillard concluded that a main obstacle to learning an API is the lack of information on how to use it for a specific task [secondhand, as summarized by Nadi et al. 2016; no figures verified]. Robillard, M. P., "What Makes APIs Hard to Learn? Answers from Developers," IEEE Software 26(6):27–34, 2009 (citation details from Nadi et al.'s reference list).

**Duplicated functionality and lag behind the platform**
- Two surveys at Microsoft (187 follow-up responses) plus 11 interviews identified six forms of code duplication. In one form, "repeated work," separate developers implement the same functionality without knowing it. In the survey, 24% had made repeated changes because of such clones in one week, and 42% agreed this clone type made their code base harder to maintain [self-reported]. LaToza, T. D., Venolia, G., and DeLine, R., "Maintaining mental models: a study of developer work habits," ICSE 2006. DOI 10.1145/1134285.1134355 (PDF: https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/p492-latoza.pdf).
- Android averaged 115 API updates per month, yet 28% of API references in client apps were outdated, with a median lag of 16 months. Of those outdated usages, 22% were eventually upgraded, taking about 14 months against a roughly 3-month API release interval. McDonnell, T., Ray, B., and Kim, M., "An Empirical Study of API Stability and Adoption in the Android Ecosystem," ICSM 2013. https://github.com/baishakhir/baishakhir.github.io/blob/master/uploads/icsm2013-apiecosystem.pdf

**General API misuse**
- The MUBench dataset holds 90 real and hand-crafted misuses gathered by reviewing more than 1,200 bug reports, extended to 100. The most common violations are:
  - missing conditions: 48 (25 null checks, 21 value or state checks)
  - missing method calls: 30
  - redundant method calls: 13
  - missing exception handling: 10

  Four static detectors (Jadet, GrouMiner, DMMC, Tikanga) were tested. On their top-20 findings across 5 projects, precision was 11.4%, 10.3%, 9.9% and 0%. Recall against 53 real misuses was at most 20.8% (DMMC), with Tikanga at 13.2%, Jadet at 5.7% and GrouMiner at 0%. Amann, S., Nguyen, H. A., Nadi, S., Nguyen, T. N., and Mezini, M., "A Systematic Evaluation of Static API-Misuse Detectors," IEEE TSE, accepted 2018, published 2019, arXiv:1712.00242. https://github.com/snadi/snadi.github.io/blob/master/assets/pdf/pubs/AmannTSE18.pdf
- The same paper reports that 57% of the top 5% of 2,854 StackOverflow threads about ConcurrentModificationException ask for a fix to a misuse whose rules are thoroughly documented [secondhand]. In the current MUBench repository I counted 280 misuse records across 67 projects (my count of `data/*/misuses/*/misuse.yml`, 2026-10-24). https://github.com/stg-tud/MUBench
- A study of five data-centric Python libraries found misuses in about 8% of the StackOverflow posts and 5% of the GitHub commits it analyzed: 49 misuses of 45 APIs. Of these, 39% were data-conversion errors, 51% involved API parameters, and 35% produced wrong output with no runtime error. 39% violated a rule that the documentation states, so documentation existed but did not prevent the misuse. Galappaththi, A., Nadi, S., and Treude, C., "An Empirical Study of API Misuses of Data-Centric Libraries," ESEM 2024. DOI 10.1145/3674805.3686685

**Cryptographic API misuse**
- The study combined 100 StackOverflow posts, 100 GitHub repositories and 48 surveyed developers (11 in a pilot, 37 in the main survey).
  - Of 93 relevant StackOverflow questions, 57% came from posters who had some domain knowledge but whom the API's complexity kept from using it correctly. 28% lacked domain knowledge or could not identify a suitable library, and 7% did not know which Java library to use.
  - 65% of survey participants found their crypto API hard to use [self-reported]. Of the 21 who named obstacles, 48% said the API is not high-level enough and 43% cited poor documentation [self-reported].

  Nadi, S., Krüger, S., Mezini, M., and Bodden, E., "'Jumping Through Hoops': Why do Java Developers Struggle With Cryptography APIs?," ICSE 2016. DOI 10.1145/2884781.2884790
- Egele et al. statically analyzed 11,748 Android apps and found that 88% violated at least one of six basic crypto rules [secondhand, via Nadi et al. 2016]. The six rules, as restated in the LICMA tool's README: no ECB mode, no non-random IV for CBC, no constant keys, no constant PBE salts, at least 1,000 PBE iterations, no static seeds for SecureRandom. Egele, M., Brumley, D., Fratantonio, Y., and Kruegel, C., "An empirical study of cryptographic misuse in Android applications," CCS 2013, pp. 73–84 (LICMA README: https://github.com/stg-tud/licma).
- The CogniCrypt tool paper cites Lazar et al.: of 269 crypto vulnerabilities, 17% came from faulty algorithm implementations and 83% from developers misusing crypto APIs. It also cites other work putting crypto misuse at about 90% of apps that use these APIs [secondhand]. Krüger, S., Nadi, S., Reif, M., Ali, K., Mezini, M., Bodden, E., et al., "CogniCrypt: Supporting Developers in using Cryptography," ASE 2017 (tool demo). https://github.com/snadi/snadi.github.io/blob/master/assets/pdf/pubs/KrugerASE17.pdf
- In a controlled experiment with 24 Java developers, CogniCrypt significantly improved functionality and security scores and completion times. More than 80% of CogniCrypt users finished their task, while most plain-Eclipse users did not. Krüger, S., Reif, M., Wickert, A.-K., Nadi, S., Ali, K., Bodden, E., Acar, Y., Mezini, M., and Fahl, S., "Securing Your Crypto-API Usage Through Tool Support – A Usability Study," IEEE SecDev 2023 (venue taken from the file name; the PDF has no venue line). https://github.com/snadi/snadi.github.io/blob/master/assets/pdf/pubs/KrugerSecDev23.pdf

**Standard library and platform usage**
- In the scope of this study, the Python standard library has 341 modules and 8,795 APIs, and 1,841 of those APIs (21%) are platform-specific. Across 100 popular projects there were 19,288 usages of 683 platform-specific APIs, so about 37% of them are used at all (my arithmetic). 52.6% of the usages were in production code and 47.4% in tests. Job, R., and Hora, A., "Availability and Usage of Platform-Specific APIs: A First Empirical Study," MSR 2024. DOI 10.1145/3643991.3644925

**AI code assistants**
- 16 LLMs generated 576,000 code samples in Python and JavaScript. 19.7% of the packages they recommended do not exist, giving 205,474 unique made-up package names. Per-model Python rates ran from 3.35% (GPT-4 Turbo) and 5.49% (GPT-3.5) up to 26.28% (CodeLlama 7B). JavaScript rates ran from 5.64% to 37.80%. These figures come from the authors' README and `Plots/Data/figure_2.csv`; the paper PDF host was unreachable. Spracklen, J., Wijewickrama, R., Sakib, A. H. M. N., Maiti, A., Viswanath, B., and Jadliwala, M., "We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs," USENIX Security 2025. https://github.com/Spracks/PackageHallucination ; data DOI 10.5281/zenodo.14676377
- Copilot produced 132 solutions to 33 LeetCode problems, with correctness ranging from 57% (Java) to 27% (JavaScript). Some suggestions call helper methods that do not exist (for example, `dfs` is called but never defined in the Python and JavaScript solutions). This concerns undefined helper functions, not library APIs. Nguyen, N., and Nadi, S., "An Empirical Evaluation of GitHub Copilot's Code Suggestions," MSR 2022. DOI 10.1145/3524842.3528470

**What this establishes**
- **Developers name missing knowledge as the main barrier.** When asked, they put knowledge and documentation gaps first: documentation and learning resources as the most severe obstacle (Robillard and DeLine 2011), and API complexity (57%) or missing domain or library knowledge (28%) behind crypto questions (Nadi et al. 2016). This evidence is mostly self-reported.
- **Misuse of platform APIs is widespread and survives documentation.** Reported figures are 88% of 11,748 Android apps (Egele, secondhand) and 83% of 269 crypto vulnerabilities (Lazar, secondhand via Krüger 2017). 39% of data-library misuses violated documented rules (Galappaththi 2024), and the documented ConcurrentModificationException rule is still widely misused (Amann, secondhand). Static detectors catch little after the fact: precision under 12% and recall of 20.8% or less (Amann et al. 2019).
- **Unknowing reimplementation is documented only inside organizations.** LaToza et al. 2006 shows developers unknowingly duplicating each other's work, and McDonnell et al. 2013 shows client apps lagging platform APIs by a median 16 months. I verified no study showing reimplementation of standard-library functions (including Kawrykow and Robillard 2009).
- **Task-level tooling reduced crypto misuse in one small experiment.** CogniCrypt improved security scores and completion rates for 24 developers (Krüger et al. 2023).
- **LLMs invent dependencies at measurable rates, but standard-library use by LLMs is unmeasured here.** Package hallucination ran 19.7% overall and 3.35% to 26.28% per model in Python (Spracklen et al. 2025), and Copilot called undefined helpers (Nguyen and Nadi 2022). No verified source here measures whether assistants know or reuse the standard library rather than reimplementing it.
