**StarPU**
- StarPU's default scheduler is `lws` (work stealing), which uses no performance model. The `dm` and `dmda` schedulers are "HEFT-similar", and `heft` is a deprecated alias for `dmda`. `dmda` minimises `alpha*T_execution + beta*T_data_transfer`, and the transfer term comes from bus calibration on an idle machine with no contention. The docs suggest raising beta to 2 because contention makes real transfers slower, and they claim "a rough estimation already gives the good results that a precise estimation would give" [self-reported]. Tasks whose model is not yet calibrated fall back to the `eager` policy. Source: StarPU developers (Univ. Bordeaux, CNRS, Inria), StarPU Handbook source `doc/doxygen/chapters/starpu_basics/scheduling.doxy`, starpu-runtime/starpu commit 5d217c3, 2026. https://github.com/starpu-runtime/starpu/blob/master/doc/doxygen/chapters/starpu_basics/scheduling.doxy
- The history-based model averages past run times, keyed on a hash of the data sizes. The docs say this is "very true for regular kernels on GPUs (<0.1% error)" and "~1% error" on CPUs, with no method given [self-reported]. A size needs 10 measurements before StarPU trusts it. The regression models (`a*n^b` and `a*n^b+c`) need at least a 10% spread in input sizes, and the non-linear fit is only computed when the program ends, so the first run uses history alone. Source: same handbook, `starpu_performances/online_performance_tools.doxy`, same commit. https://github.com/starpu-runtime/starpu/blob/master/doc/doxygen/chapters/starpu_performances/online_performance_tools.doxy
- **Energy-aware placement.** With an energy model, `dmda` adds a `gamma*Consumption` term in joules. You must also set the machine's idle power, otherwise "the scheduler would simply tend to run all computations on the most energy-conservative processing unit". Live per-task energy measurement on CUDA works only on V100 and later, and "only works for quite long tasks, since the measurement granularity is about 10ms". CPU energy comes from RAPL counters (Intel's hardware energy counters, read through PAPI) for the whole socket, so per-task cost is found by running batches of tasks and dividing [self-reported]. Source: same handbook, `starpu_extensions/advanced_scheduling.doxy`. https://github.com/starpu-runtime/starpu/blob/master/doc/doxygen/chapters/starpu_extensions/advanced_scheduling.doxy
- **Deterministic replay by simulation.** In SimGrid mode, kernel execution and data transfers are replaced by virtual sleeps taken from the performance models, while the real scheduler and application still run. The docs describe the resulting timing as deterministic, which lets you break at an exact virtual time. Turning on `STARPU_SIMGRID_SCHED_COST` gives more accurate predictions "however, it also makes simulation non-deterministic". Source: same handbook, `starpu_extensions/simgrid.doxy` and `starpu_installation/environment_variables.doxy`. https://github.com/starpu-runtime/starpu/blob/master/doc/doxygen/chapters/starpu_extensions/simgrid.doxy
- The StarPU paper itself was not retrieved. Its citation is confirmed second-hand from reference lists [secondhand]: C. Augonnet, S. Thibault, R. Namyst, P.-A. Wacrenier, "StarPU: A unified platform for task scheduling on heterogeneous multicore architectures," Concurrency and Computation: Practice and Experience 23:187–198, Feb. 2011. It is cited as ref. [18] in Task Bench (SC20) and ref. [6] in Regent (SC15).

**Legion and Regent**
- Legion's mapping interface has ten methods. "Program correctness is unaffected by mapper decisions, which can only impact performance." The default mapper uses Cilk-like work stealing. Reported results: circuit simulation speedups of 39.0X on 48 GPUs and 62.5X on 96 GPUs, within 5% of a hand-coded single-GPU version, and AMR (adaptive mesh refinement) up to 2.6X faster than BoxLib on one node, rising to 5.4X at 16 nodes [self-reported]. Source: M. Bauer, S. Treichler, E. Slaughter, A. Aiken, "Legion: Expressing Locality and Independence with Logical Regions," SC12, 2012. https://raw.githubusercontent.com/StanfordLegion/StanfordLegion.github.io/master/pdfs/sc2012.pdf
- Regent's type system "guarantees that a program with correct serial execution produces identical results on parallel and distributed machines". The paper reports performance comparable to hand-tuned Legion [self-reported]. Source: E. Slaughter, W. Lee, S. Treichler, M. Bauer, A. Aiken, "Regent: A High-Productivity Programming Language for HPC with Logical Regions," SC '15, 2015. https://raw.githubusercontent.com/StanfordLegion/StanfordLegion.github.io/master/pdfs/regent2015.pdf
- **Replayable placement in Legion.**
  - `ReplayMapper` "can take as input a replay file generated LegionSpy and use it to replay all the mapping decisions made in a previous run".
  - Under control replication, a mapper "must return the same sharding functor for all copies of the task", but the runtime checks this "in debug mode but not in release mode".
  - Source: StanfordLegion/legion (branch `stable`, commit aea587e, 2026), files `runtime/mappers/replay_mapper.h` and `runtime/legion/api/mapping.h`. https://github.com/StanfordLegion/legion/blob/stable/runtime/mappers/replay_mapper.h
- Dynamic tracing records the dependence analysis for a repeated trace (including the effect of mapping changes) and replays it. The paper reports strong scaling improved "by an average of 4.9× and up to 7.0×" [self-reported]. Source: W. Lee, E. Slaughter, M. Bauer, S. Treichler, T. Warszawski, M. Garland, A. Aiken, "Dynamic Tracing: Memoization of Task Graphs for Dynamic Task-Based Runtimes," SC18, 2018. https://raw.githubusercontent.com/StanfordLegion/StanfordLegion.github.io/master/pdfs/trace2018.pdf
- AutoMap tunes mappings from measured runs instead of static estimates. It finds that "individual mappings can have significant variation in performance from run to run, necessitating multiple executions". Its mappings are up to 2.41× faster than hand-written mappers, and up to 50× faster when the input is only 1.3% larger than GPU framebuffer memory [self-reported]. Its related-work section says HEFT, MCT and FCP "assume a single memory" [secondhand on HEFT]. Source: T. Teixeira, A. Henzinger, R. Yadav, A. Aiken, "Automated Mapping of Task-Based Programs onto Distributed and Heterogeneous Machines," SC '23, 2023. https://doi.org/10.1145/3581784.3607079

**Charm++**
- Charm++ load balancing is measurement-based and relies on the "principle of persistence": "the recent past is a good predictor of the near future". The load database is cleared after each balancing step. "Seed balancers" are offered where persistence does not hold. The GPU section (GPU Manager and HAPI) covers asynchronous offload and callbacks; it does not describe automatic CPU/GPU placement. Source: Charm++ manual, `doc/charm++/manual.rst`, charmplusplus/charm (branch `recharm`, commit b0126ef, 2026). https://github.com/charmplusplus/charm/blob/recharm/doc/charm++/manual.rst. The original paper, L. V. Kalé and S. Krishnan, "CHARM++," OOPSLA 1993, pp. 91–108, is cited from Task Bench [secondhand].
- `+record` and `+replay` record message-processing order and replay it deterministically; production and tracing-disabled builds turn this off. The debugger manual warns that record-replay "does not work well with spontaneous events. Load balancing is the most common form of spontaneous event." A randomized message queue can be repeated with `+randomized_seed <N>`. Source: same manual, plus `doc/debugger/manual.rst`, same commit. https://github.com/charmplusplus/charm/blob/recharm/doc/debugger/manual.rst

**OmpSs**
- The Nanos++ "versioning" scheduler keeps elapsed time per (task type, parameter size) for each implementation and processing element. It needs at least 3 records (`MIN_RECORDS 3`) before it trusts the statistics, discards the first run on each processing element as unrepresentative, and then sends the task to the worker that would finish it earliest. Source: BSC, Nanos++ `src/plugins/sched/versioning_sched.cpp`, bsc-pm/nanox commit a9df693, 2021. https://github.com/bsc-pm/nanox/blob/master/src/plugins/sched/versioning_sched.cpp. Paper citation [secondhand, from Task Bench]: A. Duran et al., "OmpSs: A proposal for programming heterogeneous multi-core architectures," Parallel Processing Letters 21(2):173–193, 2011.
- **Runtime overhead across these systems.** Task Bench tested 15 systems, including StarPU, OmpSs, Charm++, Regent and Realm, on up to 256 Cori nodes. Its metric is METG (minimum effective task granularity: the smallest task size at which a system still achieves 50% efficiency). Some systems reach under 1 µs in the best case, but at scale about 100 µs is "a realistic bound". Going from 0 to 3 dependencies per task changes METG by 0.82× to 250× (mean 21×) [self-reported]. Source: E. Slaughter, W. Wu et al., "Task Bench: A Parameterized Benchmark for Evaluating Parallel Runtime Performance," SC20, 2020. https://raw.githubusercontent.com/StanfordLegion/StanfordLegion.github.io/master/pdfs/taskbench2020.pdf

**HEFT and list scheduling**
- Citation [secondhand, from AutoMap ref. 38]: H. Topcuoglu, S. Hariri, M.-Y. Wu, "Performance-effective and low-complexity task scheduling for heterogeneous computing," IEEE TPDS 13(3):260–274, 2002, https://doi.org/10.1109/71.993206. The paper's own results were not retrieved.
- A widely used reference implementation ranks tasks by "upward rank", built from the average compute cost and the average transfer cost over device pairs. It then places each task, in rank order, on the device with the earliest finish time, filling idle gaps where possible. Source: M. Rocklin, `heft` package, `heft/core.py`. https://github.com/mrocklin/heft
- **Experiment I ran on that implementation [measured in this run].** Setup: a fork-join graph (root, four identical tasks, sink) on three devices with equal costs.
  - Across 20 values of `PYTHONHASHSEED` I got 15 distinct placements, all with the same makespan of 4.0.
  - Equal-rank tasks and equal-finish-time devices are tie-broken by Python set and dict order, which depends on that hash seed.
  - A fixed seed gave the same placement in 10 of 10 runs.
  - Passing the devices as an ordered list still gave 11 distinct placements, because ties between tasks remain.

**Halide autoscheduler (Adams 2019)**
- The paper (Adams et al., SIGGRAPH 2019) was not retrieved. From the code:
  - The cost model is trained with "L2 on relative throughput", not absolute time, and retraining reports a pairwise "correct ordering rate".
  - Defaults are beam size 32 and random dropout 100 (off).
  - The search RNG is `std::mt19937` seeded with the seed parameter as given. A header comment says seed 0 means "use time()", but the code does not do this.
  - Weights are randomised from `time(nullptr)` only when no weights file is loaded.
  - Source: halide/Halide commit fc30f3a, 2026, files `src/autoschedulers/adams2019/{AutoSchedule.cpp, CostModel.h, cost_model_generator.cpp, retrain_cost_model.cpp, DefaultCostModel.cpp}`. https://github.com/halide/Halide/tree/main/src/autoschedulers/adams2019
- The GPU autoscheduler weights (`anderson2021`) were trained leave-one-app-out on a V100 and "may not perform the same on other GPUs" [self-reported]. The li2018 README gives measured times for its heuristic, model-free autoscheduler: local_laplacian on GPU 14.30 ms vs 0.81 ms hand-written, and conv_layer on CPU 6.89 ms vs 15.46 ms hand-written [self-reported]. Source: same repo, `src/autoschedulers/anderson2021/weights/README.md` and `src/autoschedulers/li2018/README.md`.

**TVM learned cost models**
- The paper (Chen et al., 2018) was not retrieved. From the code:
  - AutoTVM's XGBoost model either regresses normalised FLOPS (`reg:linear`) or learns a pairwise ranking (`rank:pairwise`).
  - Ansor's XGBModel predicts normalised throughput with a "pack-sum-rmse" loss.
  - With fewer than `num_warmup_sample=100` samples, Ansor's model "outputs random predictions".
  - Source: Apache TVM v0.12.0, `python/tvm/autotvm/tuner/xgboost_cost_model.py` and `python/tvm/auto_scheduler/cost_model/xgb_model.py`. https://github.com/apache/tvm/blob/v0.12.0/python/tvm/auto_scheduler/cost_model/xgb_model.py
- TenSet holds 51,577,248 measurement records over 13,848 tasks, 120 networks and 6 hardware platforms [self-reported]. Its example record lists 8 repeated timings: the first is 0.991 ms and the other seven are 0.826–0.854 ms. By my arithmetic the first is about 20% above the minimum and the rest are within 3.4% of it. Source: tlc-pack, TenSet README. https://github.com/tlc-pack/tenset
- The TLP slides state that a cost model trained on one machine performs poorly on another ("cross-hardware unavailability"). The accuracy numbers are in images I could not extract. Source: Y. Zhai et al., "TLP: A Deep Learning-Based Cost Model for Tensor Program Tuning," ASPLOS 2023 slides. https://github.com/zhaiyi000/tlp

**Predicted vs measured error for GPU kernels**
- Accel-Sim was evaluated on 140 workloads against a QV100 GPU. Cycle error fell from 94% mean absolute error (GPGPU-Sim 3.x, correlation 0.87) to 15% (correlation 1.0) [self-reported].
  - Per-suite error in its SASS (native-ISA) mode: CUDA SDK 9%, Rodinia 8%, Parboil 20%, Polybench 4%, microbenchmarks 9%, CUTLASS wmma 12%, CUTLASS sgemm 2%, Deepbench 33%.
  - Across GPU generations in SASS mode: Kepler 25%, Pascal 30%, Volta 15%, Turing 25%, all with correlation ≥ 0.97. PTX (virtual-ISA) mode gave 28%, 53%, 34% and 32%.
  - Source: M. Khairy, Z. Shen, T. M. Aamodt, T. G. Rogers, "Accel-Sim: An Extensible Simulation Framework for Validated GPU Modeling," ISCA 2020, presentation slides 30 and 32–34. https://github.com/accel-sim/accel-sim.github.io/blob/master/ISCA2020-presentation-v3.0.pptx
- The Accel-Sim 2.0 site claims a "99% Pearson correlation and 13.4% mean absolute cycle error over 34,000+ kernel instances from 22 benchmark suites" against real H100 hardware [self-reported]. Source: Accel-Sim project site (commit a7d075a, 2026), https://github.com/accel-sim/accel-sim.github.io/blob/master/index.html; the paper it links is arXiv 2608.22602 (not retrieved).
- FlexFlow's execution simulator was tested on six DNNs and two GPU clusters. For every measured run, "the relative difference between the real and simulated execution time is less than 30%", and the simulated times kept the same ranking of strategies as the measured ones [self-reported]. Source: Z. Jia, "Automated Discovery of Machine Learning Optimizations," PhD dissertation, Stanford, 2020, ch. 3. https://raw.githubusercontent.com/StanfordLegion/StanfordLegion.github.io/master/pdfs/jia_thesis.pdf
- AccelWattch models GPU power as an analytic constant and static part plus a dynamic part tuned by quadratic programming against measured hardware power. Its accuracy numbers were not retrieved. Source: V. Kandiah et al., "AccelWattch: A Power Modeling Framework for Modern GPUs," MICRO-54, 2021. https://github.com/accel-sim/accel-sim.github.io/blob/master/accelwattch.html

**Deterministic execution and record/replay**
- rr's site reports recording slowdowns "down to ≤ 1.2x" on Firefox test suites. It "emulates a single-core machine", so parallel programs pay the cost of running on one core [self-reported]. Source: rr project website source. https://github.com/rr-debugger/rr/blob/gh-pages/index.html
- The rr wiki says to "expect around a 1.2x to 1.4x slowdown", 1.1–1.2x for CPU-bound programs, and "4x slowdown or more" for programs that make syscalls in a tight loop. A laptop CPU frequency governor can add "up to 2x", and running in a VM raises overhead from about 1.2x to about 1.4x [self-reported]. Traces only replay on machines that support the CPU features used at recording time. The rr paper (O'Callahan et al., arXiv 1705.05937) was not retrieved. Source: rr wiki, Usage, Recording-Firefox and Trace-Portability pages. https://github.com/rr-debugger/rr/wiki/Usage
- Kendo: the rr wiki calls it the "first paper to use performance counters for async event timing" and says its counter observations are out of date [secondhand]. Its overhead numbers were not verified. https://github.com/rr-debugger/rr/wiki/Related-work
- CoreDet: the GitHub repo only hosts the code releases used in its ASPLOS 2010 and 2011 papers (Bergan, Devietti, Anderson, Ceze, Grossman). It contains no overhead figures. https://github.com/uwsampa/coredet
- DPJ: described in the Legion and Regent papers as a fully static region system that guarantees determinism and is more restrictive than Legion [secondhand]. Citation: R. Bocchino, V. Adve, D. Dig, S. Adve, S. Heumann, R. Komuravelli, J. Overbey, P. Simmons, H. Sung, M. Vakilian, "A type and effect system for deterministic parallel Java," OOPSLA 2009, pp. 97–116 [secondhand]. DPJ overheads were not verified, and DMP (Devietti et al., ASPLOS 2009) was not verified at all.

**What this establishes**
- **Production runtimes predict cost by measuring, not by analysis.** StarPU, OmpSs (Nanos++) and Charm++ all record past run times per kernel, per data size and per device, and need a few to ten samples before trusting them. The only figures they give are their own (StarPU: <0.1% for GPU, ~1% for CPU). Transfer-cost estimates are admitted to be rough because calibration ignores contention. Sources: StarPU Handbook, Nanos++ versioning scheduler, Charm++ manual.
- **Prediction error for GPU kernels and learned compiler models.** Independent predicted-vs-measured figures put the best GPU simulator at 2–33% cycle error per suite (15% average on QV100, 13.4% claimed on H100), against 94% for the older GPGPU-Sim 3.x. A whole-strategy simulator stays under 30%. The Halide and TVM learned models are trained for ranking or relative throughput, not absolute time, and are tied to the hardware they were trained on. Sources: Accel-Sim ISCA 2020 slides and site, Jia thesis (FlexFlow), Halide autoscheduler source, TVM v0.12.0 source, TLP slides.
- **Placement is non-deterministic by default.** Decisions depend on timing and on models that change as measurements arrive. Determinism comes from recording and replaying decisions (Legion ReplayMapper and dynamic tracing, Charm++ `+record`/`+replay`) or from virtual-time simulation (StarPU SimGrid). Both are in tension with adaptivity: Charm++ load balancing "does not work well" with record-replay, adding scheduling cost makes StarPU's simulation non-deterministic, and AutoMap needs repeated runs because of run-to-run variance. Sources: StarPU SimGrid documentation, Legion sources, Charm++ manuals, AutoMap (SC '23).
- **Static list scheduling is only deterministic up to tie-breaking.** In my run of the HEFT reference implementation, equal-makespan ties gave 15 different placements across 20 hash seeds and a single placement under a fixed seed. Legion's requirement that replicated mappers make identical choices is only checked in debug builds. Sources: mrocklin/heft (measured in this run), Legion `mapping.h`.
- **Overheads of determinism and energy-aware placement: only rr is quantified here.** rr reports about 1.1–1.4x typical, 4x or more for syscall-heavy programs, plus the loss of multicore parallelism [self-reported]. DMP, Kendo, CoreDet and DPJ overheads could not be verified in this run. Energy-aware placement exists in StarPU, but it needs the machine's idle power, and per-task GPU energy measurement is limited by roughly 10 ms granularity. Sources: rr site and wiki, StarPU Handbook.

The HEFT tie experiment is `../scripts/heft_ties.py`: it takes the path of a clone of mrocklin/heft and `list` or `set` for the agent collection; run it under different `PYTHONHASHSEED` values.
